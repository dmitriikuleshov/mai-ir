# Лемматизатор: нормализация словоформ в техническом корпусе

## 1. Что такое лемматизация

Лемматизация — это приведение разных грамматических форм слова к одной нормальной форме, которая называется леммой. Например, английские формы `query` и `queries` должны соответствовать лемме `query`, формы `retrieve`, `retrieved` и `retrieving` — лемме `retrieve`, а неправильные формы `is`, `are`, `was`, `were` и `been` — лемме `be`.

Для поисковой системы это необходимо потому, что пользователь и автор документа могут употребить одно понятие в разных грамматических формах. Если хранить формы независимо, запрос `database query` не обязательно найдёт документ, содержащий `databases` и `queries`. После лемматизации и документ, и запрос используют ключи `database` и `query`, поэтому грамматическое различие перестаёт мешать поиску.

Лемматизацию следует отличать от стемминга. Стеммер обычно механически отрезает окончание и может получить основу, которая не является настоящим словом. Например, простое удаление `-ing` превращает `coding` в `cod`, а `storing` — в `stor`. Лемматизатор старается вернуть существующую словарную форму: `coding → code`, `storing → store`. В моей реализации используются и словари, и морфологические правила, но результат правила принимается только после проверки по словарю допустимых лемм. Поэтому это гибридный лемматизатор, а не алгоритм простого отсечения суффиксов.

Общая роль компонента выглядит так:

```text
текст документа
      │
      ▼
токенизатор
      │
      ▼
["queries", "retrieved", "c++", "databases"]
      │
      ▼
лемматизатор
      │
      ▼
["query", "retrieve", "c++", "database"]
      │
      ▼
частоты лемм и поисковый индекс
```

Лемматизатор не читает HTML и не выделяет слова из текста. Он получает уже готовый список токенов от токенизатора. Это важное разделение обязанностей: токенизатор определяет границы термов и приводит английские буквы к нижнему регистру, а лемматизатор определяет нормальную форму каждого полученного терма.

## 2. Где находится реализация

Основная реализация находится в двух файлах каталога `src/linguistics/language`:

- `lemmatizer.hpp` объявляет публичный интерфейс, структуру результата и непрозрачный тип словаря;
- `lemmatizer.cpp` загружает словари, применяет правила и измеряет время обработки.

Связь с остальным лингвистическим этапом находится в `pipeline.cpp`. Эта функция сначала запускает токенизатор, передаёт полученные токены лемматизатору, а затем отдельно подсчитывает частоты токенов и лемм.

Публичный интерфейс лемматизатора небольшой:

```cpp
struct LemmaDictionary;

struct LemmatizationResult {
    TokenList lemmas;
    uint64_t changed_token_count = 0;
    uint64_t elapsed_nanoseconds = 0;
};

LemmaDictionary *lemma_dictionary_load(
    const char *exceptions_path,
    const char *lemmas_path = nullptr,
    const char *overrides_path = nullptr);

void lemma_dictionary_destroy(LemmaDictionary *dictionary);

LemmatizationResult lemmatize_tokens(
    const TokenList *tokens,
    const LemmaDictionary *dictionary);
```

Тип `LemmaDictionary` объявлен, но его внутреннее устройство скрыто из заголовочного файла. Остальной код может загрузить словарь, передать его лемматизатору и освободить, но не зависит от конкретного способа хранения. Такое сокрытие позволяет менять внутренние структуры без изменения вызывающего кода.

Отдельной консольной программы только для лемматизации в проекте нет. Лемматизатор собран как часть библиотеки `linguistics_pipeline` и используется тремя компонентами:

- основным лингвистическим пайплайном при обработке корпуса;
- булевым поиском при нормализации термов запроса;
- поиском TF-IDF при нормализации запроса перед вычислением весов.

Благодаря этому документы и запросы проходят одну и ту же реализацию. Если документ индексируется по лемме `retrieve`, запрос `retrieving` также будет преобразован в `retrieve` и обратится к правильному ключу индекса.

## 3. Вход и выход лемматизатора

На вход `lemmatize_tokens` получает `TokenList`, который является псевдонимом для `std::vector<std::string>`:

```cpp
using TokenList = std::vector<std::string>;
```

Каждый элемент входного вектора обрабатывается независимо. На каждый входной токен создаётся ровно одна выходная лемма. Порядок и количество элементов сохраняются:

```text
вход:  ["query", "queries", "c++", "children"]
выход: ["query", "query",   "c++", "child"]
```

Исходный вектор не изменяется. Функция создаёт новый `TokenList`, заранее резервирует в нём место и последовательно добавляет результаты:

```cpp
LemmatizationResult result;
result.lemmas.reserve(tokens->size());

for (const std::string &token : *tokens) {
    std::string lemma = lemmatize_token(token, dictionary);
    if (lemma != token) ++result.changed_token_count;
    result.lemmas.push_back(std::move(lemma));
}
```

Кроме списка лемм возвращаются две метрики:

- `changed_token_count` показывает, сколько конкретных вхождений изменилось, а не сколько различных словоформ было найдено;
- `elapsed_nanoseconds` содержит продолжительность обработки всего входного списка в наносекундах.

Например, для входа `queries queries query` результатом будет `query query query`, а `changed_token_count` будет равен двум. Каждое повторение учитывается отдельно, потому что эта метрика показывает долю реально нормализованных токенов корпуса.

Время измеряется с помощью `std::chrono::steady_clock`. Монотонные часы не зависят от ручной или автоматической коррекции системного времени и поэтому подходят для измерения продолжительности алгоритма.

## 4. Какие данные использует лемматизатор

В конфигурации указаны три файла:

```yaml
linguistics:
  lemma_dictionary: resources/wordnet_exceptions.tsv
  lemma_vocabulary: resources/wordnet_lemmas.txt
  lemma_overrides: resources/technical_lemma_overrides.tsv
```

Эти файлы выполняют разные задачи и не дублируют друг друга.

### 4.1. Исключения WordNet

`wordnet_exceptions.tsv` содержит пары «словоформа — лемма», разделённые символом табуляции. В текущем файле находится 5941 строка. Он нужен для форм, которые невозможно надёжно получить простым удалением окончания:

```text
abaci      abacus
accompanied accompany
am         be
applied    apply
indices    index
```

Например, форма `abaci` превращается в `abacus`, а `am` — в `be`. Правило `-s` или `-ed` само по себе таких соответствий не определит.

### 4.2. Словарь допустимых лемм

`wordnet_lemmas.txt` содержит по одной базовой форме в строке. В текущей версии это 77505 строк до удаления возможных повторов. Этот файл используется не как таблица готовых замен, а как проверка кандидата, построенного морфологическим правилом.

Например, у формы `coding` сначала удаляется `-ing`, после чего получается основа `cod`. Лемматизатор рассматривает варианты `cod` и `code`. В словаре присутствует `code`, поэтому выбирается существующая форма:

```text
coding → cod → проверка словаря → code
```

То же происходит для `computing → compute`, `storing → store`, `moving → move` и `hoped → hope`. Если ни один кандидат не присутствует в словаре, исходный токен сохраняется. Это защищает корпус от появления искусственных обрезков.

### 4.3. Исключения технического корпуса

`technical_lemma_overrides.tsv` содержит дополнительные соответствия, специфичные для собранного технического корпуса. В текущем файле находится 45 правил, не считая строки комментария. Они нужны в двух ситуациях.

Первая ситуация — нормализация технических сокращений и терминов во множественном числе:

```text
apis      api
cpus      cpu
gpus      gpu
jsons     json
llms      llm
sdks      sdk
urls      url
uuids     uuid
vms       vm
xmls      xml
```

Вторая ситуация — защита названий технологий, дисциплин и устойчивых терминов от ошибочного удаления конечной `s`:

```text
analytics    analytics
devops       devops
kubernetes   kubernetes
mathematics  mathematics
physics      physics
statistics   statistics
windows      windows
```

Отдельно разрешается неоднозначная форма `axes`. В общем английском языке она может соответствовать `axe`, `ax` или `axis` в зависимости от контекста. Для технического корпуса, в котором часто встречаются координатные оси и оси графиков, задано правило:

```text
axes    axis
```

Именно поэтому доменные переопределения имеют наивысший приоритет. Встроенная таблица содержит вариант `axes → axe`, а WordNet — вариант `axes → ax`, но технический файл намеренно выбирает `axis`.

## 5. Как словари хранятся в памяти

Условия курса разрешают применять строки и векторы, но не позволяют использовать готовые хеш-таблицы и деревья в качестве ключевой структуры поисковой системы. Поэтому словарь не реализован через `std::unordered_map` или `std::map`.

Внутри используется следующая структура:

```cpp
using LemmaEntries =
    std::vector<std::pair<std::string, std::string>>;

struct LemmaDictionary {
    LemmaEntries exceptions;
    LemmaEntries overrides;
    std::vector<std::string> lemmas;
};
```

`exceptions` и `overrides` являются векторами пар «форма — лемма». `lemmas` является вектором допустимых базовых форм. После загрузки каждый вектор сортируется, а полные дубликаты удаляются.

Поиск соответствия выполняется двоичным поиском через `std::lower_bound`:

```cpp
const auto position = std::lower_bound(
    entries.begin(), entries.end(), form,
    [](const auto &entry, const std::string &value) {
        return entry.first < value;
    });
```

Проверка наличия кандидата в словаре выполняется через `std::binary_search`. Для отсортированного вектора обе операции требуют порядка `O(log N)` сравнений. Загрузка и сортировка выполняются один раз при запуске процесса, после чего тот же `LemmaDictionary` используется для всех документов или запросов.

Такое решение является компромиссом между требованиями курса и скоростью. Линейный просмотр словаря из десятков тысяч лемм для каждого токена был бы слишком дорогим, а готовая хеш-таблица нарушала бы оговорённое ограничение. Отсортированный вектор даёт быстрый поиск, компактно располагается в памяти и использует только разрешённые контейнеры.

## 6. Общий алгоритм лемматизации одного токена

Вся логика выбора находится в функции `lemmatize_token`. Для каждого токена выполняется одна и та же последовательность:

```text
1. Токен состоит только из английских букв ASCII?
   └─ нет → оставить без изменений

2. Есть правило в technical_lemma_overrides.tsv?
   └─ да → вернуть техническую лемму

3. Есть форма во встроенной таблице неправильных слов?
   └─ да → вернуть встроенную лемму

4. Есть форма в wordnet_exceptions.tsv?
   └─ да → вернуть словарную лемму

5. Загружен словарь допустимых лемм?
   ├─ нет → применить осторожные автономные правила
   └─ да → построить кандидаты по суффиксу и проверить их в словаре

6. Подтверждённый кандидат найден?
   ├─ да → вернуть кандидата
   └─ нет → оставить исходный токен
```

Порядок является частью алгоритма. Если сначала применить общие суффиксные правила, `statistics` можно ошибочно превратить в `statistic`, `windows` — в `window`, а `axes` — разрешить не в том значении. Если применять WordNet раньше технических переопределений, доменная настройка `axes → axis` не сработает.

Соответствующий фрагмент кода выглядит так:

```cpp
if (!ascii_word(word)) return word;

if (const std::string *lemma =
        mapping_find(dictionary->overrides, word)) {
    return *lemma;
}

for (const LemmaPair &pair : IRREGULAR_LEMMAS) {
    if (word == pair.form) return pair.lemma;
}

if (const std::string *lemma =
        mapping_find(dictionary->exceptions, word)) {
    return *lemma;
}

const std::string candidate =
    validated_suffix_lemma(word, dictionary);
return candidate.empty() ? word : candidate;
```

## 7. Почему технические и неанглийские токены не изменяются

Перед словарями и правилами вызывается `ascii_word`. Функция возвращает `true`, только если каждый байт токена является английской буквой ASCII. Если присутствует цифра, знак пунктуации, подчёркивание, символ другого алфавита или технический разделитель, токен возвращается без изменений.

Благодаря этому не искажаются:

```text
C++        → c++
C#         → c#
.NET       → .net
Node.js    → node.js
SHA-256    → sha-256
3.14       → 3.14
192.168.1.1 → 192.168.1.1
v2.1       → v2.1
x86_64     → x86_64
```

Преобразование регистра в этих примерах уже выполнил токенизатор. Лемматизатор только видит, что внутри токена есть не буквенные символы, и не применяет к нему английские суффиксные правила.

По той же причине без изменений сохраняются слова на кириллице, китайские и японские термы. Текущая реализация выполняет морфологическую нормализацию только для английского языка. Она не выдаёт неправильную английскую основу для неизвестного алфавита, а безопасно сохраняет исходный токен.

Это правило не означает, что все технические термы обязательно содержат знаки. Термы `windows`, `kubernetes`, `devops` и `statistics` состоят только из букв, поэтому для них используются явные доменные переопределения.

## 8. Встроенные неправильные формы

Для небольшого набора частых неправильных форм существует встроенная таблица `IRREGULAR_LEMMAS`. Она позволяет выполнить важные преобразования независимо от внешнего файла:

```text
children → child
men      → man
women    → woman
mice     → mouse
feet     → foot
teeth    → tooth
went     → go
gone     → go
ran      → run
saw      → see
better   → good
best     → good
worse    → bad
worst    → bad
is       → be
are      → be
was      → be
were     → be
been     → be
```

Часть этих форм также присутствует во внешних ресурсах, но небольшой встроенный слой даёт предсказуемое ядро поведения и используется даже в тесте с пустым внешним словарём. Например, без внешних файлов всё равно выполняется `children → child`.

Встроенная таблица не должна разрастаться до полного словаря. Массовые данные вынесены в ресурсы, потому что их удобнее проверять и дополнять отдельно от C++-кода. В коде остаются только наиболее частые и принципиальные случаи.

## 9. Правила регулярных окончаний

После проверки исключений лемматизатор рассматривает несколько групп английских окончаний. Правила расположены от более специфичных к более общим.

### 9.1. Множественное число на `-ies`

Для формы на `-ies` рассматриваются два варианта:

```text
policies → policie или policy
queries  → querie или query
```

Кандидаты проверяются в словаре, поэтому выбираются существующие `policy` и `query`.

### 9.2. Формы на `-ing`

У формы удаляется `-ing`, после чего рассматриваются:

- полученная основа без изменений;
- основа без одной из двух одинаковых конечных согласных;
- основа с восстановленной немой `e`.

Примеры:

```text
running    → runn → run
stopping   → stopp → stop
coding     → cod  → code
making     → mak  → make
retrieving → retriev → retrieve
singing    → sing → sing
filling    → fill → fill
```

Проверка словаря позволяет различить случаи, когда удвоенная согласная является частью самой основы. Если полная основа уже существует в словаре, она не сокращается без необходимости.

### 9.3. Формы на `-ed`

Для `-ed` применяется та же идея: удаляется окончание, проверяется удвоенная согласная и возможность восстановить `e`.

```text
stopped    → stopp → stop
retrieved  → retriev → retrieve
normalized → normaliz → normalize
computed   → comput → compute
filled     → fill → fill
```

### 9.4. Множественное число на `-es`

Отдельно поддерживаются окончания `-sses`, `-shes`, `-ches`, `-xes`, `-zes` и `-oes`. В этих случаях удаляются последние две буквы, а результат проверяется по словарю:

```text
classes  → class
wishes   → wish
churches → church
boxes    → box
buzzes   → buzz
heroes   → hero
```

### 9.5. Обычное окончание `-s`

Для слова длиной больше трёх символов может быть удалена последняя `s`. Однако окончания `-ss`, `-us` и `-is` защищены, чтобы не превращать `glass`, `status` или `analysis` в ошибочные формы.

Даже после этой проверки кандидат принимается только при наличии в словаре лемм. Поэтому неизвестное `qzxys` не превращается автоматически в `qzxy`.

## 10. Режим без словаря допустимых лемм

Функция загрузки допускает отсутствие внешних файлов. Этот режим используется в тестах и делает библиотеку работоспособной в минимальной конфигурации. Если список допустимых лемм пуст, применяется отдельная функция `lemmatize_without_vocabulary`.

Она поддерживает те же основные окончания, но не может проверить результат по словарю. Поэтому правила сделаны более консервативными и используют небольшие эвристики для удвоенных согласных и немой `e`.

Например, с полностью пустым внешним словарём по-прежнему получаются:

```text
children → child  // встроенное исключение
queries  → query  // правило -ies
running  → run    // удаление -ing и удвоенной согласной
c++      → c++    // защищённый технический токен
```

Однако специфичное исключение `abaci → abacus` без WordNet применить невозможно, поэтому `abaci` останется без изменений. В рабочем запуске проекта этот резервный режим не используется: все три ресурса указаны в `config.yaml` и загружаются при старте.

## 11. Защита от несуществующих основ

Главная практическая проблема простого правилового алгоритма состоит в избыточной нормализации. Если без проверки удалить суффикс, могут появиться термы `cod`, `comput`, `stor` и другие обрезки. Такие ключи ухудшают индекс: пользователь вводит настоящее слово `code`, а документ хранится под искусственным ключом `cod`.

В этой реализации функция `validated_verb_stem` строит несколько осмысленных кандидатов и проверяет каждый через `lemma_exists`. Упрощённо логика выглядит так:

```text
stem = форма без -ing или -ed

если stem заканчивается удвоенной согласной:
    проверить stem
    проверить stem без одной согласной

проверить stem + "e", если окончание похоже на немую e
проверить stem
ещё раз проверить stem + "e" как запасной вариант

если ни один кандидат не существует:
    не изменять исходное слово
```

Например:

```text
qzxying → qzxy → в словаре нет → qzxying
qzxyed  → qzxy → в словаре нет → qzxyed
coding  → cod / code → code есть → code
```

Стратегия «лучше оставить неизвестную форму, чем создать заведомо несуществующую лемму» особенно важна для технического корпуса. В нём часто встречаются новые названия библиотек, продуктов, команд и аббревиатур, которых может не быть в общем английском словаре.

## 12. Как лемматизатор включён в общий pipeline

Функция `linguistics_process` задаёт строгую последовательность:

```cpp
TokenizationResult tokenization =
    tokenize_text(text, text_size, maximum_token_length);

LemmatizationResult lemmatization =
    lemmatize_tokens(&tokenization.tokens, dictionary);
```

Затем исходные токены и леммы независимо преобразуются в частотные массивы:

```cpp
result.tokens = make_frequencies(std::move(tokenization.tokens));
result.lemmas = make_frequencies(std::move(lemmatization.lemmas));
```

`make_frequencies` сортирует список и сворачивает одинаковые строки. Поэтому несколько форм могут объединиться в один ключ:

```text
исходные токены:
query, queries, retrieve, retrieved, retrieving

частоты токенов:
query      → 1
queries    → 1
retrieve   → 1
retrieved  → 1
retrieving → 1

частоты лемм:
query    → 2
retrieve → 3
```

Лемматизатор сам не считает частоты и не сортирует результат. Его ответственность заканчивается на соответствии «один входной токен — одна выходная лемма». Подсчёт частот является обязанностью общего pipeline.

## 13. Куда сохраняется результат

Для понимания лемматизатора достаточно знать три места сохранения; детали доступа к MongoDB здесь несущественны.

Во-первых, частоты лемм каждого принятого документа сохраняются в поле `document_terms.lemmas`:

```javascript
{
  _id: ObjectId("..."),
  lemmas: [
    ["database", 8],
    ["query", 14],
    ["retrieve", 5]
  ]
}
```

Это основной результат для последующего индексатора. По умолчанию булев индекс строится именно по полю `lemmas`, а не по исходным словоформам.

Во-вторых, в `processed_documents` сохраняются `changed_token_count` и `lemmatization_seconds`. Они позволяют определить, сколько токенов было нормализовано и сколько времени заняла лемматизация конкретного документа.

В-третьих, суммарные частоты по всему корпусу находятся в `lemma_frequencies`:

```javascript
{ _id: "query", count: 284153 }
```

Глобальные частоты используются для анализа словаря, вывода наиболее частых лемм и построения графика Ципфа. Полный последовательный список лемм не сохраняется, потому что для индексации и статистики достаточно частот внутри документа.

## 14. Использование при поиске

Нормализация выполняется не только при подготовке документов. Булевый и TF-IDF-поиск загружают те же три словарных ресурса и вызывают тот же `linguistics_process` для пользовательского запроса.

Например, индекс содержит лемму `index`, полученную из форм `index`, `indexes`, `indices`, `indexed` и `indexing`. Запрос пользователя `indexed systems` нормализуется до `index system`, после чего поиск обращается к тем же ключам, которые были созданы при обработке корпуса.

Использование одной функции для обеих сторон принципиально. Если документы и запросы обрабатывались бы разными правилами, даже корректная лемматизация по отдельности могла бы создавать несовместимые ключи.

## 15. Как собрать и проверить лемматизатор

Из корня проекта выполняется обычная сборка C++-части:

```bash
cmake -S . -B .build -DCMAKE_BUILD_TYPE=Release
cmake --build .build --parallel
```

Отдельный набор Google Test запускается напрямую:

```bash
./.build/lemmatization_unit_tests
```

Тот же набор можно запустить через CTest:

```bash
ctest --test-dir .build -R 'unit\.lemmatization\.' --output-on-failure
```

Тесты проверяют не только единичные примеры, но и группы случаев:

- обычные формы на `-s`, `-ies`, `-es`, `-ing` и `-ed`;
- повторяющиеся словоформы и точный счётчик изменений;
- неправильные существительные, глаголы и степени сравнения;
- исключения WordNet;
- восстановление немой `e` и удаление удвоенной согласной;
- защиту от несуществующих обрезанных основ;
- приоритет технических переопределений;
- сохранение `C++`, `.NET`, `node.js`, версий, IP-адресов и идентификаторов;
- сохранение неанглийских слов;
- пустой вход и работу без внешнего словаря;
- большой список из повторяющихся форм.

Чтобы увидеть работу лемматизатора на всём корпусе, запускается общий pipeline:

```bash
./.build/linguistics config.yaml
```

Однако для демонстрации именно алгоритма удобнее сначала показать тесты: они дают контролируемые входы и ожидаемые выходы, а затем открыть результат реального документа в поле `document_terms.lemmas`.

## 16. Сложность алгоритма

Пусть `T` — число входных токенов, `E` — число словарных исключений, `O` — число технических переопределений, а `V` — число допустимых лемм.

Для одного английского токена выполняются:

- проверка символов за `O(L)`, где `L` — длина токена;
- двоичный поиск в технических переопределениях за `O(log O)`;
- линейный просмотр маленькой встроенной таблицы фиксированного размера;
- двоичный поиск в исключениях за `O(log E)`;
- несколько двоичных поисков кандидатов в словаре за `O(log V)`.

Следовательно, обработка всего списка имеет приблизительную сложность:

```text
O(T · (L + log E + log V))
```

Число кандидатов для одного окончания ограничено небольшой константой. Память результата линейна по числу токенов, потому что для каждого входного элемента создаётся одна строка леммы. Словари загружаются один раз и не копируются для каждого документа.

## 17. Ограничения текущего решения

Лемматизатор рассчитан прежде всего на англоязычный технический корпус. Он не выполняет морфологический анализ русского, китайского или других языков, а сохраняет такие токены без изменений.

Алгоритм не определяет часть речи по контексту предложения. Неоднозначная словоформа выбирается по приоритетам словарей и настройке домена. Например, `axes` всегда становится `axis`, потому что это предпочтительный смысл для текущего технического корпуса, хотя в общем тексте возможны другие значения.

Правила покрывают наиболее полезные английские окончания, но не являются полным академическим морфологическим анализатором. Неизвестное слово может остаться в исходной форме даже тогда, когда теоретически существует корректная лемма. Это осознанный выбор в пользу точности: ошибочное объединение разных терминов способно ухудшить поиск сильнее, чем сохранение редкой формы отдельно.

Технические переопределения требуют поддержки. Если в корпусе появляется распространённый термин, который систематически нормализуется неверно, его можно добавить в `technical_lemma_overrides.tsv`, после чего необходимо увеличить `parser_version` и повторно обработать корпус. Увеличение версии обязательно, потому что иначе документы с прежним хэшем будут считаться уже актуальными.

## 18. Краткое объяснение для защиты

Лемматизатор можно объяснить преподавателю следующим образом:

> Лемматизация приводит разные словоформы к единому поисковому ключу. В моей реализации это гибрид словаря и правил. Сначала проверяются исключения технического корпуса, затем встроенные неправильные формы и исключения WordNet. Для регулярных окончаний строится несколько кандидатов, но кандидат принимается только тогда, когда он присутствует в словаре допустимых лемм. Поэтому `coding` превращается в `code`, а неизвестное слово не превращается в обрезанную несуществующую основу. Технические термы со знаками и цифрами, например `C++`, `.NET` и `SHA-256`, сохраняются без изменения. Словари хранятся в отсортированных векторах, а поиск выполняется двоичным поиском, поэтому готовые хеш-таблицы и деревья не используются. Для каждого токена создаётся ровно одна лемма, после чего pipeline считает частоты. Частоты лемм каждого документа сохраняются в `document_terms.lemmas` и используются при построении индекса. Запрос проходит тот же лемматизатор, поэтому формы документа и запроса совпадают.

Главная последовательность, которую нужно помнить:

```text
техническое переопределение
→ встроенное исключение
→ исключение WordNet
→ словарно проверенное правило окончания
→ исходный токен, если безопасной замены нет
```

Именно приоритет правил, проверка кандидата по словарю и защита технических терминов являются главными особенностями этой реализации.
