# Булев индекс: построение, бинарный формат и дальнейшее использование

## 1. Что такое булев индекс

Булев поиск должен быстро отвечать на запросы вида:

```text
database AND security
cloud OR distributed
retrieval AND NOT neural
(database OR storage) AND replication
```

Просматривать полный текст каждого документа при каждом запросе невозможно: для корпуса из сотен тысяч документов это потребовало бы повторно читать и анализировать весь корпус. Поэтому заранее строится инвертированный индекс.

До индексирования данные организованы по документам:

```text
документ 0 → database, query, retrieval
документ 1 → cloud, database, security
документ 2 → query, ranking, retrieval
```

Инвертированный индекс меняет направление связи и организует данные по термам:

```text
cloud     → [1]
database  → [0, 1]
query     → [0, 2]
ranking   → [2]
retrieval → [0, 2]
security  → [1]
```

Список документов одного терма называется posting list. Для `database` posting list равен `[0, 1]`, потому что терм встречается в документах 0 и 1. Списки отсортированы по числовому идентификатору документа, поэтому операции `AND` и `OR` выполняются линейным слиянием двух списков без повторного просмотра текста.

В моей реализации posting дополнительно содержит частоту терма в документе:

```text
database → [(doc=0, tf=3), (doc=1, tf=1)]
```

Булевому поиску достаточно `docID`, но поле `tf` позволяет использовать тот же индекс для ранжирования TF-IDF. Поэтому результат этого этапа является общим дисковым индексом сразу для двух видов поиска.

## 2. Место индекса в общей системе

Булев индекс строится не по сырому HTML и не по полному тексту. Его входом служит результат лингвистического пайплайна — коллекция `document_terms` в MongoDB.

Полная последовательность выглядит так:

```text
crawler
    │
    ▼
MongoDB: documents с raw_html
    │
    ▼
извлечение текста → токенизация → лемматизация
    │
    ▼
MongoDB: document_terms
документ → [(терм, частота), ...]
    │
    ▼
boolean_index
внешняя сортировка и инвертирование
    │
    ▼
results/boolean_index/*.bin
    │
    ├──► boolean_search: AND, OR, NOT
    │
    └──► tfidf_search: веса и ранжирование
```

Таким образом, индексатор не занимается HTML, токенизацией или лемматизацией. Он получает уже подготовленные термы и решает другую задачу: превращает отображение «документ → термы» в отображение «терм → документы», компактно сохраняет его на диск и создаёт возможность быстрого поиска.

## 3. Где находится реализация

Код разделён на несколько частей внутри `src/boolean_index`.

| Часть | Ответственность |
|---|---|
| `app` | Загрузка конфигурации и запуск индексатора. |
| `building` | Чтение документов, назначение `docID`, формирование и внешняя сортировка блоков. |
| `compression` | Кодирование и декодирование целых чисел Variable Byte. |
| `storage` | Бинарный формат, пути файлов и запись окончательного индекса. |

Точка входа минимальна:

```cpp
int main(int argc, char **argv) {
    if (argc != 2) {
        std::fprintf(stderr, "Использование: %s config.yaml\n", argv[0]);
        return EXIT_FAILURE;
    }
    const BooleanIndexConfig config =
        load_boolean_index_config(argv[1]);
    mongoc_init();
    build_boolean_index(config);
    mongoc_cleanup();
    return EXIT_SUCCESS;
}
```

Основной алгоритм начинается в `build_boolean_index`, временные блоки создаются в `blocks.cpp`, а окончательное слияние и бинарные файлы формируются в `index_writer.cpp`. Точное описание структур на диске находится в `storage/format.hpp`. Читатель индекса расположен уже в `src/boolean_search/index`, потому что он используется поисковыми компонентами.

## 4. Как запустить построение индекса

Перед индексированием должны быть выполнены два условия:

1. MongoDB должна быть запущена;
2. лингвистический пайплайн должен заполнить `document_terms`.

Запуск базы:

```bash
docker compose up -d
```

Сборка C++-компонентов:

```bash
cmake -S . -B .build -DCMAKE_BUILD_TYPE=Release
cmake --build .build --parallel
```

Если корпус ещё не проходил лингвистическую обработку, сначала запускается:

```bash
./.build/linguistics config.yaml
```

Затем строится индекс:

```bash
./.build/boolean_index config.yaml
```

Во время работы программа сообщает число прочитанных документов, запись временных блоков, промежуточные слияния и итоговые размеры:

```text
Индекс: прочитано документов 1000
Индекс: записан блок 1
...
Индекс готов: документов ..., терминов ..., пар термин-документ ...
Сжатие postings: ... байт вместо ... байт для docID+TF (...% экономии)
```

Построение выполняется заново. Индексатор не дописывает новые документы в старые posting lists, потому что полное блочное построение проще проверить и оно гарантирует согласованную сортировку всех термов. Старые основные файлы заменяются готовыми временными файлами после успешной записи новой версии.

## 5. Параметры конфигурации

Индексатор читает параметры подключения из секции `db` и собственные параметры из секции `boolean_index`:

```yaml
db:
  uri: mongodb://localhost:27017
  database: mai_ir
  document_terms_collection: document_terms

boolean_index:
  output_directory: results/boolean_index
  term_field: lemmas
  block_postings: 500000
  progress_every_documents: 1000
```

| Параметр | Назначение |
|---|---|
| `uri` | Адрес MongoDB. |
| `database` | Имя базы с результатами лингвистического пайплайна. |
| `document_terms_collection` | Коллекция, из которой читаются термы документов. |
| `output_directory` | Каталог пяти готовых бинарных файлов. |
| `term_field` | Поле `lemmas` или `tokens`, по которому строится индекс. |
| `block_postings` | Максимальное число пар «терм — документ» в оперативном буфере перед сбросом на диск. |
| `progress_every_documents` | Период вывода прогресса. |

По умолчанию используется `term_field: lemmas`. Это означает, что формы `query` и `queries`, уже приведённые лемматизатором к `query`, попадут в один posting list. Если выбрать `tokens`, разные словоформы будут отдельными ключами.

После изменения лингвистических правил сначала необходимо повторно заполнить `document_terms`, а затем перестроить индекс. Бинарные файлы являются снимком состояния коллекции на момент запуска и автоматически не отслеживают последующие изменения MongoDB.

## 6. Формат входных данных

Одна запись `document_terms` имеет тот же MongoDB `_id`, что и исходный документ, и содержит частотные массивы:

```javascript
{
  _id: ObjectId("..."),
  source: "wikipedia",
  source_id: 123456,
  content_hash: "...",
  tokens: [
    ["databases", 2],
    ["queries", 3]
  ],
  lemmas: [
    ["database", 2],
    ["query", 3]
  ]
}
```

Индексатор запрашивает только `_id` и поле, указанное в `term_field`. Каждый элемент выбранного массива должен иметь вид:

```text
[строка_терма, положительная_целая_частота]
```

Частота должна помещаться в `uint32_t`. Пустые термы пропускаются. Отсутствующее поле, неправильный тип массива, нулевая, отрицательная или слишком большая частота считаются повреждением входных данных и останавливают построение, чтобы некорректный документ не попал в индекс незаметно.

Коллекция `document_terms` содержит только принятые лингвистическим пайплайном документы. Слишком короткие страницы не имеют записи с термами и поэтому в индекс не входят.

## 7. Зачем нужен внутренний числовой docID

MongoDB идентифицирует документ 12-байтовым `ObjectId`. Сохранять такой идентификатор в каждом posting было бы невыгодно. Кроме того, для булевых операций удобнее возрастающая последовательность небольших целых чисел.

Поэтому индексатор сортирует входные документы по `_id` MongoDB и назначает им последовательные внутренние идентификаторы:

```text
первый ObjectId  → docID 0
второй ObjectId  → docID 1
третий ObjectId  → docID 2
...
```

`docID` имеет тип `uint32_t`, поэтому текущий формат допускает до `2^32 - 1` документов. Сортировка по ObjectId делает назначение воспроизводимым: если состав и идентификаторы коллекции не изменились, повторное построение назначит те же внутренние номера.

Связь не теряется. Каждый ObjectId один раз записывается в `documents.bin` в позиции своего `docID`. После поиска внутренний номер переводится обратно в ObjectId, по которому из `processed_documents` загружаются заголовок, URL и источник.

Такое разделение позволяет использовать компактные числовые posting lists и при этом показывать пользователю реальные документы.

## 8. Пара «терм — документ»

В оперативной памяти одна запись представлена структурой:

```cpp
struct PostingPair {
    std::string term;
    uint32_t document_id;
    uint32_t term_frequency;
};
```

Для входного документа

```text
docID = 7
lemmas = [["database", 3], ["cloud", 2], ["security", 1]]
```

в буфер добавляются:

```text
(database, 7, 3)
(cloud,    7, 2)
(security, 7, 1)
```

Именно эти записи затем сортируются сначала по строке терма, а внутри одного терма — по `docID`. После сортировки все postings одного терма располагаются рядом и образуют возрастающий список документов.

Одновременно для каждого документа вычисляется L2-норма его вектора логарифмических TF-весов:

```text
weight(tf) = 1 + log10(tf)

norm(document) = sqrt(Σ weight(tf)^2)
```

Эта величина не нужна для чистых `AND`, `OR`, `NOT`, но используется последующим TF-IDF-поиском. Её выгодно вычислять во время того же прохода, потому что все частоты документа уже находятся в памяти.

## 9. Почему нельзя отсортировать весь индекс в памяти

В текущем корпусе число пар «терм — документ» измеряется десятками миллионов. Каждая пара в оперативной памяти содержит не только два целых числа, но и объект `std::string`. Попытка накопить весь корпус в одном `std::vector` потребовала бы очень большой объём памяти и сделала бы построение зависимым от размера RAM.

Поэтому используется блочная внешняя сортировка, близкая к алгоритму BSBI — Blocked Sort-Based Indexing:

```text
MongoDB
  │
  ▼
буфер до block_postings пар
  │
  ▼
сортировка в памяти
  │
  ▼
временный отсортированный block_000000.bin

следующий буфер → следующий блок

все отсортированные блоки
  │
  ▼
k-way merge
  │
  ▼
готовый инвертированный индекс
```

При текущем значении `block_postings: 500000` одновременно хранится примерно до пятисот тысяч записей. После достижения лимита буфер сортируется, записывается во временный файл и очищается. Поэтому объём памяти ограничен размером одного блока, а не размером всего корпуса.

## 10. Формирование временного блока

Буфер сортируется по паре ключей:

```text
(term по возрастанию, document_id по возрастанию)
```

После сортировки одинаковые пары `(term, document_id)` оказываются соседними и удаляются через `std::unique`. Обычно лингвистический pipeline уже хранит один элемент на терм документа, но эта проверка не позволяет случайному дубликату создать два одинаковых posting.

Временный блок имеет простой последовательный формат:

```text
uint32 term_length
byte[term_length] term_utf8
uint32 document_id
uint32 term_frequency

uint32 term_length
byte[term_length] term_utf8
uint32 document_id
uint32 term_frequency
...
```

Временные блоки являются внутренним промежуточным представлением. Они находятся в каталоге вида `results/boolean_index/blocks-XXXXXX` и удаляются после успешного завершения. Поисковая утилита их не читает.

## 11. Многоходовое слияние блоков

Для финального инвертирования нужно слить отсортированные блоки в один глобально отсортированный поток. Для каждого открытого блока в памяти хранится только текущая запись. Индексы читателей находятся в собственной минимальной куче.

Корень кучи всегда указывает на минимальную пару `(term, docID)`. Алгоритм выполняет следующие действия:

1. берёт запись из корня;
2. передаёт её в выходной поток;
3. читает следующую запись того же блока;
4. восстанавливает свойство кучи операцией `heap_sift_down`;
5. повторяет действия, пока все блоки не закончатся.

Если блоков слишком много, невозможно одновременно открыть все файлы. Константа `MERGE_FAN_IN = 128` ограничивает одно слияние 128 входами. При большем количестве выполняются промежуточные проходы: каждая группа до 128 блоков превращается в новый отсортированный блок, старые файлы удаляются, после чего процесс повторяется.

Таким образом, индексатор работает и при очень большом числе блоков, не превышая разумный лимит открытых файлов.

Готовая `std::priority_queue` не используется. Минимальная куча реализована явно поверх `std::vector<size_t>` и хранит индексы читателей, а не копии строк. Это уменьшает копирование термов и делает алгоритм понятным для объяснения.

## 12. Что происходит во время финального слияния

Пока минимальная куча выдаёт записи в порядке `(term, docID)`, индексатор формирует сразу три основных файла:

- текст нового терма добавляется в `terms.bin`;
- его postings последовательно кодируются в `postings.bin`;
- после завершения списка в `lexicon.bin` записываются смещения, длина терма и число postings.

При переходе от одного терма к следующему завершается запись предыдущего `LexiconEntry`. Благодаря глобальной сортировке все документы одного терма идут подряд, а `docID` внутри списка строго возрастают.

Заголовок `lexicon.bin` сначала записывается с нулевым числом термов и postings. После полного слияния программа возвращается в начало и перезаписывает его точными итоговыми значениями.

Файлы создаются с суффиксом `.tmp`. После успешной записи и закрытия они переименовываются в `lexicon.bin`, `terms.bin` и `postings.bin`. Это не позволяет обычному поисковому запуску открыть наполовину записанный файл под окончательным именем.

Таблицы `documents.bin` и `norms.bin` также сначала создаются как `.tmp`. Заголовки с точным числом документов записываются только после чтения всей коллекции. При открытии поисковый код сверяет magic, версию и `document_count`, поэтому смешение файлов разных построений обнаруживается как ошибка формата.

## 13. Какие файлы образуют готовый индекс

В каталоге `results/boolean_index` находятся пять файлов:

| Файл | Содержимое | Кто использует |
|---|---|---|
| `lexicon.bin` | Заголовок и по одной фиксированной записи на терм. | Булевый и TF-IDF-поиск. |
| `terms.bin` | UTF-8-байты всех термов без разделителей. | Поиск терма через лексикон. |
| `postings.bin` | Сжатые списки `(docID-gap, term_frequency)`. | Булевый и TF-IDF-поиск. |
| `documents.bin` | Соответствие внутреннего `docID` и MongoDB ObjectId. | Вывод метаданных найденного документа. |
| `norms.bin` | L2-норма каждого документа. | Только TF-IDF-ранжирование. |

Индекс разделён на файлы, потому что данные имеют разные режимы доступа. Лексикон содержит записи фиксированного размера и допускает двоичный поиск. Термы имеют переменную длину и поэтому вынесены отдельно. Posting lists читаются последовательными диапазонами. Таблица ObjectId адресуется напрямую по номеру документа, а нормы TF-IDF можно целиком загрузить в `std::vector<double>`.

## 14. Версия, magic и упаковка структур

Текущая версия бинарного формата равна трём:

```cpp
constexpr uint32_t VERSION = 3;
```

Каждый файл с заголовком начинается с восьмибайтовой сигнатуры:

```text
lexicon.bin   → MAIIRIDX
documents.bin → MAIIRDOC
norms.bin     → MAIIRNRM
```

Сигнатура позволяет отличить индекс от случайного файла, а версия запрещает читать старый несовместимый формат новым кодом.

Структуры заголовков и лексикона объявлены внутри `#pragma pack(push, 1)`. Упаковка убирает зависимые от компилятора выравнивающие байты. Размеры закреплены проверками времени компиляции:

```cpp
static_assert(sizeof(IndexHeader) == 32);
static_assert(sizeof(LexiconEntry) == 24);
static_assert(sizeof(DocumentHeader) == 16);
static_assert(sizeof(DocumentNormHeader) == 16);
```

Эти проверки не позволяют случайно добавить поле или изменить тип и незаметно сдвинуть все последующие данные.

Числа и значения `double` записываются в нативном бинарном представлении машины. В текущей среде x86-64 это little-endian. Следовательно, формат стабилен для используемой архитектуры и версии программы, но не заявлен как универсальный сетевой формат между машинами с разным порядком байтов или другим представлением `double`. Для учебной системы, которая строит и читает индекс в одной среде, это допустимое ограничение.

## 15. Точный формат `lexicon.bin`

Первые 32 байта занимает `IndexHeader`:

| Смещение | Размер | Тип | Значение |
|---:|---:|---|---|
| 0 | 8 | `char[8]` | Magic `MAIIRIDX`. |
| 8 | 4 | `uint32_t` | Версия формата. |
| 12 | 4 | `uint32_t` | Число документов. |
| 16 | 8 | `uint64_t` | Число различных термов. |
| 24 | 8 | `uint64_t` | Общее число пар «терм — документ». |

После заголовка идут `term_count` записей `LexiconEntry` по 24 байта:

| Относительное смещение | Размер | Тип | Значение |
|---:|---:|---|---|
| 0 | 8 | `uint64_t` | `term_offset` — позиция UTF-8-байтов терма в `terms.bin`. |
| 8 | 8 | `uint64_t` | `postings_offset` — позиция списка в `postings.bin`. |
| 16 | 4 | `uint32_t` | `term_length` — длина терма в байтах UTF-8. |
| 20 | 4 | `uint32_t` | `postings_count` — число документов в списке, то есть document frequency. |

Термы представлены в лексиконе в лексикографическом порядке. Запись с номером `i` начинается по адресу:

```text
32 + i × 24
```

Фиксированный размер позволяет двоичному поиску сразу перейти к средней записи, не читая весь словарь в память.

## 16. Точный формат `terms.bin`

`terms.bin` не имеет заголовка и разделителей. Он содержит склеенные UTF-8-представления термов:

```text
clouddatabasequeryretrievalsecurity...
```

Сам по себе этот файл невозможно однозначно разделить на строки. Границы каждого терма определяются полями `term_offset` и `term_length` соответствующей записи лексикона:

```text
term_bytes = terms.bin[term_offset : term_offset + term_length]
```

Отсутствие нулевых байтов, переводов строк и повторных длин уменьшает размер. Длина уже хранится в лексиконе, поэтому добавлять её в `terms.bin` не требуется.

Важно объяснять, что `terms.bin` — это не самостоятельный текстовый словарь, хотя утилита `file` может распознать его как UTF-8. Он имеет смысл только вместе с `lexicon.bin`.

## 17. Точный формат `postings.bin`

`postings.bin` также не имеет общего заголовка. Для каждого терма он последовательно хранит пары:

```text
VariableByte(docID-gap)
VariableByte(term_frequency)
```

Абсолютный `docID` заменяется разностью с предыдущим документом того же posting list:

```text
docID:  [2, 10, 11, 40]
gaps:   [2,  8,  1, 29]
```

Для первого элемента gap равен самому `docID`. При чтении абсолютное значение восстанавливается накоплением:

```text
docID[0] = gap[0]
docID[i] = docID[i - 1] + gap[i]
```

Списки отсортированы, поэтому gaps неотрицательны, а после первого элемента строго положительны. Разности обычно значительно меньше абсолютных идентификаторов и поэтому хорошо сжимаются Variable Byte.

Начало списка берётся из `postings_offset`, а число пар — из `postings_count`. Отдельный маркер конца списка в файле не нужен.

## 18. Как работает Variable Byte

Variable Byte разбивает `uint32_t` на группы по семь значащих бит. Старший бит каждого сохранённого байта служит признаком конца числа. В этой реализации он равен единице у последнего байта.

Примеры:

| Число | Бинарные группы | Байты в hex |
|---:|---|---|
| 0 | `0` | `80` |
| 1 | `1` | `81` |
| 127 | `1111111` | `FF` |
| 128 | `1`, `0000000` | `01 80` |

Одно значение `uint32_t` занимает от одного до пяти байтов. Маленькие gaps и небольшие частоты чаще всего занимают один байт вместо четырёх.

Например, posting list

```text
[(doc=2, tf=3), (doc=10, tf=1), (doc=11, tf=5)]
```

превращается в gaps `[2, 8, 1]` и записывается как чередование:

```text
gap 2 → 82    tf 3 → 83
gap 8 → 88    tf 1 → 81
gap 1 → 81    tf 5 → 85
```

Итоговый поток занимает шесть байтов. Несжатые три пары двух `uint32_t` заняли бы 24 байта.

`term_frequency` сохраняется рядом с gap. Булевый поиск после декодирования отбрасывает частоту и оставляет только `docID`, а TF-IDF использует оба поля.

## 19. Точный формат `documents.bin`

Первые 16 байт занимает `DocumentHeader`:

| Смещение | Размер | Тип | Значение |
|---:|---:|---|---|
| 0 | 8 | `char[8]` | Magic `MAIIRDOC`. |
| 8 | 4 | `uint32_t` | Версия формата. |
| 12 | 4 | `uint32_t` | Число документов. |

Затем идут MongoDB ObjectId ровно по 12 байт каждый. Позиция соответствует внутреннему `docID`:

```text
offset(ObjectId) = 16 + docID × 12
```

Например, ObjectId документа 1000 начинается по смещению `16 + 1000 × 12 = 12016`.

В файле нет повторных `docID`, потому что номер определяется позицией. Это экономит четыре байта на запись и обеспечивает прямой доступ `O(1)`.

## 20. Точный формат `norms.bin`

Файл начинается с 16-байтового `DocumentNormHeader`:

| Смещение | Размер | Тип | Значение |
|---:|---:|---|---|
| 0 | 8 | `char[8]` | Magic `MAIIRNRM`. |
| 8 | 4 | `uint32_t` | Версия формата. |
| 12 | 4 | `uint32_t` | Число документов. |

После заголовка находится по одному `double` на документ:

```text
offset(norm) = 16 + docID × sizeof(double)
```

В текущей среде `sizeof(double) == 8`, поэтому файл имеет размер:

```text
16 + document_count × 8 байт
```

Норма вычисляется из логарифмических частот `1 + log10(tf)` и используется для нормализации вектора документа в схеме TF-IDF `lnc.ltc`. Булевый поиск `norms.bin` не открывает.

## 21. Как находится терм в индексе

Поисковая часть открывает четыре базовых файла и проверяет заголовки. Для поиска терма выполняется двоичный поиск по `lexicon.bin`.

На каждом шаге:

1. вычисляется номер средней `LexiconEntry`;
2. выполняется прямой переход на `32 + middle × 24`;
3. из записи читаются `term_offset` и `term_length`;
4. соответствующие байты читаются из `terms.bin`;
5. строка сравнивается с искомым термом;
6. выбирается левая или правая половина лексикона.

Сложность поиска одного терма составляет `O(log V)` сравнений, где `V` — размер словаря. Весь словарь не загружается в `std::map`, `std::unordered_map` или память целиком.

После нахождения записи reader переходит к `postings_offset`, декодирует ровно `postings_count` пар и восстанавливает абсолютные `docID` накоплением gaps.

## 22. Как индекс используется булевым поиском

Для терма булевый reader возвращает отсортированный `std::vector<uint32_t>` с `docID`. Частоты при этом отбрасываются.

Операции выполняются над упорядоченными списками:

- `A AND B` — пересечение двумя указателями;
- `A OR B` — объединение двумя указателями без повторов;
- `NOT A` — дополнение относительно диапазона всех документов `[0, document_count)`.

Пример:

```text
database → [0, 1, 4, 8]
security → [1, 2, 4, 9]

database AND security → [1, 4]
database OR security  → [0, 1, 2, 4, 8, 9]
```

Каждый список читается слева направо один раз. Пересечение имеет сложность `O(|A| + |B|)`, а не требует проверки каждого документа корпуса.

После вычисления выражения найденные `docID` переводятся через `documents.bin` в ObjectId. По ObjectId из `processed_documents` читаются только метаданные для вывода: заголовок, URL и источник. Само решение, какие документы подходят запросу, принимает бинарный индекс; MongoDB нужна на этом этапе только для человекочитаемого представления результата.

## 23. Как индекс используется TF-IDF

Ранжированный поиск повторно использует:

- `lexicon.bin` для document frequency `df = postings_count`;
- `postings.bin` для `docID` и частоты `tf`;
- `documents.bin` для вывода метаданных;
- `norms.bin` для заранее рассчитанной длины вектора документа.

На стороне запроса вычисляется:

```text
(1 + log10(tf_query)) × log10(N / df)
```

На стороне документа используется:

```text
(1 + log10(tf_document)) / document_norm
```

Вклад терма добавляется только документам его posting list. Поэтому ранжирование также не просматривает документы, в которых нет термов запроса.

Сохранение TF и норм во время построения булева индекса является промежуточным решением между лабораторными: базовая структура остаётся инвертированным индексом, но её не приходится перестраивать для последующего TF-IDF.

## 24. Текущий готовый индекс как конкретный пример

На момент подготовки документа заголовок существующего `results/boolean_index/lexicon.bin` содержит:

```text
version       = 3
documents     = 151182
terms         = 3565769
postings      = 73536673
```

Фактические размеры файлов:

| Файл | Размер в байтах | Приблизительный размер |
|---|---:|---:|
| `documents.bin` | 1 814 200 | 1,73 MiB |
| `lexicon.bin` | 85 578 488 | 81,61 MiB |
| `norms.bin` | 1 209 472 | 1,15 MiB |
| `postings.bin` | 165 766 719 | 158,09 MiB |
| `terms.bin` | 44 756 576 | 42,68 MiB |
| Всего | 299 125 455 | 285,27 MiB |

Если хранить для каждой из 73 536 673 пар абсолютный `docID` и TF как два несжатых `uint32_t`, только postings заняли бы 588 293 384 байта. Фактический `postings.bin` занимает 165 766 719 байт, то есть Variable Byte и gaps дают примерно 71,8% экономии для этой части.

Эти числа являются снимком текущей сборки. После изменения корпуса или лингвистических правил они изменятся, но структура файлов останется той же, пока `VERSION` равен трём.

## 25. Как самостоятельно посмотреть формат

Размеры файлов:

```bash
ls -lh results/boolean_index
```

Первые 32 байта заголовка лексикона в hex:

```bash
xxd -g 1 -l 32 results/boolean_index/lexicon.bin
```

Ожидаемое начало:

```text
4d 41 49 49 52 49 44 58
```

Это ASCII-байты строки `MAIIRIDX`.

Отдельные значения заголовка в текущей little-endian среде можно вывести так:

```bash
od -An -j8  -N4 -t u4 results/boolean_index/lexicon.bin
od -An -j12 -N4 -t u4 results/boolean_index/lexicon.bin
od -An -j16 -N8 -t u8 results/boolean_index/lexicon.bin
od -An -j24 -N8 -t u8 results/boolean_index/lexicon.bin
```

Команды выводят соответственно версию, число документов, число термов и число postings.

Проверить заголовки таблиц документов и норм:

```bash
xxd -g 1 -l 16 results/boolean_index/documents.bin
xxd -g 1 -l 16 results/boolean_index/norms.bin
```

`terms.bin` не следует интерпретировать как файл с одной строкой на термин. В нём нет разделителей; правильные границы можно получить только через записи `lexicon.bin`.

## 26. Согласованность и обнаружение повреждений

Reader не начинает поиск сразу после открытия файлов. Сначала он проверяет:

- magic `MAIIRIDX`;
- версию индекса;
- magic и версию `documents.bin`;
- совпадение `document_count` в лексиконе и таблице документов.

TF-IDF-reader дополнительно проверяет magic, версию и число документов `norms.bin`, а затем убеждается, что каждая норма конечна и неотрицательна.

Во время декодирования posting list проверяются:

- корректное завершение каждого Variable Byte-числа не более чем за пять байтов;
- отсутствие переполнения `uint32_t`;
- положительная term frequency;
- отсутствие нулевого gap после первого документа;
- отсутствие переполнения при восстановлении абсолютного `docID`.

Это не заменяет контрольную сумму всего файла, но позволяет обнаружить несовместимую версию, обрезанный файл и множество структурных повреждений вместо возврата случайных результатов.

## 27. Использование STL и соблюдение ограничений

При построении используются разрешённые строки и векторы:

- `std::vector<PostingPair>` для ограниченного блока;
- `std::vector<std::string>` для путей временных файлов;
- `std::vector<BlockReader>` и `std::vector<size_t>` для собственного heap;
- `std::sort` для сортировки одного блока.

`std::map`, `std::unordered_map`, `std::set` и `std::unordered_set` не используются. Ключевой словарь на диске реализован как отсортированный массив фиксированных записей и отдельный массив строк. Поиск выполняется собственным двоичным проходом по файлу.

Это соответствует ограничениям курса: разрешённые контейнеры помогают безопасно управлять последовательными данными, но готовая хеш-таблица или дерево не заменяет реализацию структуры индекса.

## 28. Сложность построения и поиска

Пусть `P` — число пар «терм — документ», `B` — размер одного блока, `K` — число одновременно сливаемых блоков, а `V` — число различных термов.

Сортировка каждого блока требует `O(B log B)`. Для всех блоков суммарно это можно оценить как `O(P log B)`. Финальное k-way merge обрабатывает каждую пару один раз и выполняет операции кучи порядка `O(log K)`, поэтому требует `O(P log K)` на один проход слияния.

Оперативная память ограничена примерно `O(B + K)`: один блок пар плюс текущая запись и состояние каждого читателя. Основной объём полного корпуса находится во временных файлах на диске.

Поиск одного терма в словаре требует `O(log V)` сравнений, после чего чтение его posting list линейно по числу документов этого терма. Булева операция над двумя списками также линейна по их суммарной длине.

## 31. Краткое объяснение для защиты

Булев индекс можно объяснить преподавателю следующим образом:

> Входом индексатора является коллекция `document_terms`, где для каждого принятого документа уже сохранены пары «лемма — частота». Индексатор сортирует документы по ObjectId и назначает им компактные последовательные `uint32_t docID`. Для каждой пары создаётся запись «терм, docID, TF». Поскольку таких пар десятки миллионов, используется блочная внешняя сортировка: ограниченный буфер сортируется по терму и docID, сбрасывается во временный файл, а блоки затем сливаются собственной минимальной кучей. Готовый индекс состоит из пяти файлов. `lexicon.bin` хранит фиксированные указатели на строки и posting lists, `terms.bin` хранит UTF-8-байты термов, `postings.bin` хранит сжатые пары docID-gap и TF, `documents.bin` связывает docID с MongoDB ObjectId, а `norms.bin` хранит нормы для TF-IDF. Термы находятся двоичным поиском по лексикону. Posting lists отсортированы, поэтому AND и OR выполняются линейным слиянием. Частота сохраняется вместе с docID, поэтому тот же индекс затем используется ранжированным поиском.

Главную последовательность следует запомнить так:

```text
document_terms
→ пары (term, docID, TF)
→ сортируемые блоки ограниченного размера
→ k-way merge
→ lexicon + terms + compressed postings
→ булев поиск и TF-IDF
```

Основные особенности реализации — внешняя сортировка без загрузки корпуса целиком, собственная куча, двоичный поиск по дисковому лексикону, gap-кодирование, Variable Byte и явная таблица перехода от внутреннего номера к MongoDB ObjectId.
