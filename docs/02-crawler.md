# Поисковый робот: устройство crawler и хранение корпуса в MongoDB

## 1. Что реализовано и какую задачу решает поисковый робот

Поисковый робот является первым рабочим компонентом поисковой системы. Его задача состоит не в извлечении чистого текста, токенизации или построении индекса, а в надёжном получении исходных документов из внешних источников и сохранении их в таком виде, чтобы последующие компоненты могли многократно обрабатывать один и тот же корпус. В моей реализации робот собирает англоязычные технические материалы из Wikipedia, arXiv и Microsoft Learn. Эти источники дополняют друг друга: Wikipedia содержит обзорные энциклопедические статьи, arXiv — научные публикации, а Microsoft Learn — прикладную техническую документацию и учебные материалы.

Результатом работы crawler является коллекция сырых HTML-документов в MongoDB. На этом этапе HTML намеренно не очищается от навигации, библиографии и служебных блоков. Выделение содержательного текста выполняется следующим компонентом системы, поэтому исходный HTML остаётся доступным для повторной обработки при изменении правил парсинга. Такое разделение обязанностей позволяет не скачивать весь корпус заново после каждой доработки HTML-парсера, токенизатора или лемматизатора.

Общий поток данных выглядит следующим образом:

```text
API, sitemap и категории источников
                ↓
        обнаружение документов
                ↓
нормализация URL и определение source_id
                ↓
 robots.txt → задержка → HTTP-запрос → проверка размера
                ↓
      SHA-256 сырого HTML-документа
                ↓
 MongoDB: documents + crawl_state + crawl_queue
                ↓
 последующее извлечение текста и лингвистическая обработка
```

Задание преподавателя разрешает использовать для выкачки интерпретируемый язык программирования, поэтому crawler написан на Python. Программа запускается как консольная утилита и получает ровно один позиционный аргумент — путь к YAML-конфигурации. Это соответствует формату задания: сведения о базе находятся в секции `db`, сетевые ограничения и стратегия повторной обработки находятся в секции `logic`, а параметры отдельных источников вынесены в секцию `sources`.

## 2. Общая архитектура crawler

Три источника обрабатываются асинхронно в рамках одного процесса. Для каждого включённого источника создаётся отдельный объект crawler и отдельный ограничитель частоты запросов, однако все они используют одну HTTP-сессию и одно подключение к MongoDB. Благодаря этому медленный ответ arXiv не останавливает обход Wikipedia или Microsoft Learn, но каждый конкретный сайт всё равно получает запросы последовательно с заданной задержкой.

Общая часть реализации отвечает за сетевую безопасность, повторные попытки, проверку `robots.txt`, нормализацию URL, сохранение документа и периодическую перепроверку. Классы отдельных источников отвечают только за обнаружение URL и источник устойчивого идентификатора документа. Такое разделение важно, потому что механизмы перечисления документов у сайтов разные, а правила хранения, вычисления хэша и обновления должны оставаться едиными.

Для каждого источника используется собственный механизм обнаружения:

- Wikipedia обходится через MediaWiki API, начиная с тематических категорий из конфигурации. Категории и страницы сохраняются в постоянной очереди MongoDB, поэтому обход можно продолжить после остановки процесса.
- arXiv перечисляется через Atom API по категориям и календарным месяцам. Разбиение по месяцам позволяет не использовать огромный глобальный `offset`, который становится медленным и нестабильным на большом корпусе.
- Microsoft Learn перечисляется через официальный индекс sitemap. Робот сохраняет текущую sitemap и позицию URL внутри неё, поэтому повторный запуск продолжает обход с сохранённого места.

Сетевые ошибки одного документа не должны уничтожать уже собранный корпус. Для временных HTTP-статусов `429`, `500`, `502`, `503` и `504` выполняются повторные запросы с экспоненциальной задержкой и небольшим случайным отклонением. Заголовок `Retry-After`, если он присутствует, имеет приоритет над локальным расчётом задержки. Слишком большой ответ пропускается отдельно и не останавливает весь источник.

## 3. Почему в проекте используется MongoDB

MongoDB подходит для crawler, потому что получаемые документы имеют общую основу, но различающиеся метаданные. У всех источников есть URL, HTML, заголовок, время загрузки и хэш, однако у arXiv дополнительно присутствуют авторы, категории, аннотация и номер версии, у Wikipedia — `page_id`, а у Microsoft Learn — сведения из sitemap. В документной базе эти данные можно хранить в одном поле `metadata` без создания большого числа разреженных таблиц и без преобразования вложенных списков авторов и категорий в отдельные отношения.

База запускается контейнером MongoDB 8.0 из `compose.yaml`. Порт публикуется только на локальном адресе `127.0.0.1:27017`, поэтому база доступна crawler, MongoDB Compass и локальным утилитам, но не открывается во внешнюю сеть. Данные находятся в именованном Docker volume `mongodb_data`, поэтому остановка или пересоздание контейнера не удаляет корпус.

```yaml
services:
  mongodb:
    image: mongo:8.0
    ports:
      - "127.0.0.1:27017:27017"
    volumes:
      - mongodb_data:/data/db
```

Имя базы задаётся параметром `db.database`; в текущей конфигурации используется база `mai_ir`. Crawler непосредственно работает с тремя коллекциями: `documents`, `crawl_state` и `crawl_queue`. Остальные коллекции из секции `db`, например `processed_documents` и `document_terms`, относятся к следующим этапам поисковой системы и crawler их не заполняет.

| Коллекция | Назначение |
|---|---|
| `documents` | Сырые HTML-документы, метаданные, хэши и время проверки. |
| `crawl_state` | Контрольные точки последовательного обхода arXiv и Microsoft Learn. |
| `crawl_queue` | Постоянная очередь категорий и страниц Wikipedia. |

Такое разделение не является избыточным. Документ корпуса описывает содержимое страницы, состояние обхода описывает позицию алгоритма перечисления, а очередь описывает отдельные задания, которые могут находиться в состояниях `pending`, `processing` и `done`. Если хранить всё это в одной коллекции, поля с разной семантикой пришлось бы смешать, а уникальные индексы и выборка следующей задачи стали бы сложнее.

## 4. Коллекция `documents`

### 4.1. Общая схема документа

MongoDB не требует жёсткой схемы, однако crawler формирует документы с устойчивым набором полей. Упрощённый пример записи выглядит так:

```javascript
{
  _id: ObjectId("..."),
  source: "arxiv",
  source_id: "2601.00001",
  url: "https://arxiv.org/html/2601.00001v2",
  title: "Example technical paper",
  raw_html: "<!doctype html>...",
  metadata: {
    arxiv_id: "2601.00001v2",
    authors: ["First Author", "Second Author"],
    categories: ["cs.IR", "cs.AI"],
    published: "2026-01-01T00:00:00Z",
    updated: "2026-01-02T00:00:00Z"
  },
  content_hash: "64 hexadecimal SHA-256 characters",
  etag: "...",
  last_modified: "...",
  raw_size: 184532,
  first_fetched_at: 1790000000,
  fetched_at: 1790000000,
  checked_at: 1790000000
}
```

В реальной записи значения зависят от ответа источника. Поля `etag` и `last_modified` могут быть равны `null`, если сервер не прислал соответствующие HTTP-заголовки. Поле `metadata` также различается между источниками, но остальные поля имеют одинаковый смысл для всего корпуса.

### 4.2. Назначение полей

| Поле | Вид данных | Назначение |
|---|---|---|
| `_id` | `ObjectId` | Внутренний идентификатор MongoDB. Он создаётся базой при первой вставке и сохраняется при последующих обновлениях через `upsert`. |
| `source` | строка | Имя источника: `wikipedia`, `arxiv` или `microsoft_learn`. |
| `source_id` | строка | Устойчивый идентификатор документа внутри источника. Он не зависит от случайных параметров URL. |
| `url` | строка | Канонический нормализованный URL, с которого получен документ. |
| `title` | строка | Заголовок страницы или публикации. |
| `raw_html` | строка UTF-8 | Полный сырой HTML, передаваемый следующему этапу обработки. |
| `metadata` | вложенный BSON-документ | Специфичные для источника сведения, необходимые для обновления и анализа. |
| `content_hash` | строка | SHA-256 сырого HTML в виде 64 шестнадцатеричных символов. |
| `etag` | строка или `null` | Значение HTTP `ETag`, используемое для условной перепроверки. |
| `last_modified` | строка или `null` | Значение HTTP `Last-Modified`, используемое в заголовке `If-Modified-Since`. |
| `raw_size` | целое число байтов | Размер сохранённого HTML после кодирования в UTF-8. |
| `first_fetched_at` | Unix time | Время первой успешной вставки документа. В дальнейшем это поле не изменяется. |
| `fetched_at` | Unix time | Время последнего получения новой или изменённой версии HTML. |
| `checked_at` | Unix time | Время последней успешной проверки, даже если содержимое не изменилось. |

Различие между `fetched_at` и `checked_at` принципиально. Если сервер подтвердил отсутствие изменений через HTTP `304` или SHA-256 нового ответа совпал с сохранённым хэшем, поле `checked_at` обновляется, а `fetched_at` остаётся прежним. Поэтому по `fetched_at` можно определить возраст текущей версии содержимого, а по `checked_at` — насколько недавно робот убедился в её актуальности.

### 4.3. Метаданные трёх источников

Для Wikipedia устойчивым идентификатором служит числовой `page_id`, полученный через MediaWiki API. Он сохраняется одновременно в `source_id` и в `metadata.page_id`. Название страницы может измениться, но `page_id` продолжает обозначать ту же страницу, поэтому переименование не создаёт дубликат.

Для arXiv поле `source_id` содержит номер публикации без суффикса версии, например `2601.00001`, а `metadata.arxiv_id` содержит конкретную версию, например `2601.00001v2`. За счёт этого новая версия статьи обновляет существующую запись, а не создаёт второй логический документ. В `metadata` также сохраняются заголовок, аннотация, авторы, категории, даты `published` и `updated`, лицензия и категория, через которую запись была обнаружена.

Для Microsoft Learn устойчивым идентификатором служит нормализованный URL. В `metadata` сохраняются URL sitemap и значение `lastmod`. При следующем обходе совпадение `sitemap_lastmod` позволяет отметить страницу проверенной без повторной загрузки HTML.

### 4.4. Индексы MongoDB и защита от дубликатов

При запуске crawler автоматически создаёт индексы коллекции `documents`:

```python
await self.documents.create_index(
    [("source", ASCENDING), ("source_id", ASCENDING)],
    unique=True,
)
await self.documents.create_index(
    [("source", ASCENDING), ("url", ASCENDING)],
    unique=True,
)
await self.documents.create_index(
    [("source", ASCENDING), ("checked_at", ASCENDING)]
)
```

Первый уникальный составной индекс запрещает две записи с одинаковой парой `(source, source_id)`. Один и тот же текст теоретически может присутствовать в разных источниках, поэтому `source` является частью ключа. Второй уникальный индекс запрещает сохранить один канонический URL дважды внутри источника. Третий индекс не является уникальным: он ускоряет выборку давно не проверявшихся документов для периодического обновления.

Сохранение выполняется операцией `update_one(..., upsert=True)` по паре `(source, source_id)`. Слово `upsert` означает, что MongoDB обновляет найденную запись, а при её отсутствии вставляет новую. Благодаря этому повторный запуск одной и той же операции идемпотентен и не создаёт новую строку корпуса.

## 5. Нормализация URL и идентичность документа

До сохранения URL приводится к устойчивой форме. Схема и имя хоста переводятся в нижний регистр, стандартные порты `80` и `443` удаляются, повторяющиеся косые черты пути объединяются, завершающий `/` удаляется, а фрагмент после `#` отбрасывается. Tracking-параметры `utm_*`, `fbclid`, `gclid`, `mc_cid`, `mc_eid` и `wt.mc_id` удаляются, остальные query-параметры сортируются.

Например, адрес

```text
HTTPS://Learn.Microsoft.com:443/en-us/test/?b=2&utm_source=x&a=1#part
```

превращается в

```text
https://learn.microsoft.com/en-us/test?a=1&b=2
```

Это устраняет технические дубликаты, при которых одна страница встречается с разным регистром хоста, рекламными параметрами или фрагментами. Однако URL не используется как единственная универсальная идентичность. Для Wikipedia более устойчив `page_id`, а для arXiv — номер статьи без версии. Поэтому в проекте разделены понятия `source_id`, канонического `url` и `content_hash`.

Важно правильно объяснять преподавателю назначение этих трёх величин:

- `source_id` отвечает на вопрос: «Это тот же логический документ данного источника?»;
- нормализованный `url` отвечает на вопрос: «Не встречался ли уже этот сетевой адрес в эквивалентной форме?»;
- `content_hash` отвечает на вопрос: «Изменился ли сырой HTML уже известного документа?».

Хэш не является первичным ключом и не используется для объединения разных документов с одинаковым содержимым. Такое объединение было бы опасно: например, две разные страницы-заглушки могли бы временно вернуть одинаковый HTML, хотя логически это разные документы.

## 6. Как вычисляется и используется SHA-256

Хэш строится по полному сырому HTML после декодирования HTTP-ответа в строку. Перед вычислением строка снова кодируется в UTF-8, после чего применяется SHA-256:

```python
def sha256_text(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()
```

Алгоритм SHA-256 формирует 256-битное значение. Метод `hexdigest()` представляет его как 64 шестнадцатеричных символа, потому что каждый символ кодирует четыре бита. Для одинаковой последовательности UTF-8-байтов результат всегда одинаков, а изменение хотя бы одного байта с очень высокой вероятностью полностью меняет хэш.

Последовательность сохранения документа имеет следующий вид:

1. URL нормализуется, а HTML кодируется в UTF-8.
2. По HTML вычисляется новый SHA-256.
3. Из MongoDB читается существующая запись с той же парой `(source, source_id)`.
4. Если старый и новый `content_hash` совпадают, большой `raw_html` повторно не записывается. Обновляются только URL, заголовок, метаданные, HTTP-валидаторы и `checked_at`.
5. Если хэш отличается, новый HTML, его размер, хэш и время `fetched_at` записываются в существующую запись.
6. Если записи ещё не было, `upsert` создаёт её и дополнительно устанавливает `first_fetched_at`.

Фрагмент проверки выглядит так:

```python
digest = sha256_text(raw_html)
existing = await self.get_document(source, source_id)

if existing and existing.get("content_hash") == digest:
    # Содержимое не изменилось: обновляется только факт успешной проверки.
    ...
    return "unchanged"
```

Практическая вероятность случайной коллизии SHA-256 для учебного корпуса пренебрежимо мала. При этом хэш сравнивает именно сырой HTML, а не извлечённый текст. Это означает, что изменение служебной части страницы тоже может привести к обновлению записи. Недостаток осознанный: crawler не должен знать правила выделения текста, а неизменный оригинал необходим для воспроизводимой повторной обработки.

## 7. Коллекция `crawl_state`

Коллекция `crawl_state` хранит контрольные точки алгоритмов, которые последовательно перебирают большой внешний список. Идентификатор состояния имеет форму `<source>:<key>`. Операция записи также использует `upsert`, поэтому для каждой логической контрольной точки существует одна запись.

Для arXiv ключом служит категория, например `_id: "arxiv:cs.IR"`. Запись содержит текущий месяц, смещение страницы API, индекс записи внутри полученного пакета, направление сортировки и отметку полного прохода:

```javascript
{
  _id: "arxiv:cs.IR",
  discovery_mode: "monthly",
  month: "2024-08",
  start: 300,
  entry_index: 27,
  sort_order: "descending",
  caught_up_at: null,
  updated_at: 1790000000
}
```

Состояние обновляется после каждой обработанной записи. Если процесс остановить между двумя документами, при следующем запуске будут восстановлены месяц, пакет и `entry_index`, а не начат новый проход с текущей даты.

Для Microsoft Learn используется запись `_id: "microsoft_learn:main"`. В ней находятся текущая sitemap, индекс URL внутри неё и время завершения полного прохода:

```javascript
{
  _id: "microsoft_learn:main",
  sitemap_url: "https://learn.microsoft.com/...xml",
  url_index: 1842,
  completed_at: 1790000000,
  updated_at: 1790000000
}
```

После каждой страницы сохраняется следующий `url_index`. По завершении одной sitemap состояние переключается на следующую. После полного прохода `sitemap_url` сбрасывается, а `completed_at` не позволяет сразу же повторять дорогое перечисление всех URL.

Wikipedia не использует один линейный указатель, потому что категории образуют граф, а не последовательность. Для неё предназначена отдельная постоянная очередь.

## 8. Коллекция `crawl_queue`

В `crawl_queue` находятся задания Wikipedia двух видов: `category` и `page`. Категория после обработки порождает задания для страниц и дочерних категорий. У страницы сохраняются `page_id` и заголовок, у категории — глубина обхода. Поле `priority` позволяет сначала обрабатывать страницы, а затем расширять граф категорий.

Типичное задание имеет следующие поля:

```javascript
{
  _id: ObjectId("..."),
  source: "wikipedia",
  kind: "page",
  key: "230834",
  page_id: "230834",
  title: "CAPTCHA",
  priority: 10,
  status: "processing",
  attempts: 1,
  next_attempt_at: 1790000000,
  worker_id: "wikipedia-1790000000",
  lease_until: 1790000300,
  created_at: 1790000000,
  started_at: 1790000001
}
```

Уникальный индекс `(source, kind, key)` не позволяет многократно поставить одну категорию или страницу в очередь. Второй индекс `(source, status, next_attempt_at)` ускоряет поиск задания, готового к обработке.

Получение задания выполняется атомарной операцией `find_one_and_update`. Робот выбирает либо готовое задание `pending`, либо задание `processing` с истёкшей арендой `lease_until`. Затем он одновременно переводит его в `processing`, записывает `worker_id`, увеличивает число попыток и устанавливает новую аренду. Поэтому аварийное завершение процесса не оставляет задание потерянным навсегда: после истечения `logic.lease_seconds` его может забрать следующий запуск.

При успешном выполнении задание получает статус `done`. При временной ошибке оно возвращается в `pending`, сохраняет краткое описание `last_error` и новое время `next_attempt_at`. При штатном нажатии `Ctrl+C` текущее задание возвращается в очередь без длительной задержки.

## 9. Периодическая перепроверка документов

Период перепроверки задаётся параметром `logic.recrawl_after_seconds`. В текущей конфигурации он равен `7 776 000` секунд, то есть 90 суткам. Документ считается требующим проверки, если его `checked_at` не больше текущего Unix time минус этот период. Для старых записей, в которых `checked_at` отсутствует, используется `fetched_at`.

Общая схема перепроверки состоит из нескольких уровней, расположенных от самого дешёвого к более дорогому:

1. Если документ проверялся недавно, сетевой запрос вообще не выполняется и возвращается состояние `fresh`.
2. Если сохранены `ETag` или `Last-Modified`, crawler отправляет `If-None-Match` и `If-Modified-Since`.
3. Ответ `304 Not Modified` приводит только к обновлению `checked_at`.
4. Для ответа `200 OK` вычисляется SHA-256. Если хэш совпал, HTML повторно не записывается.
5. Только при различии хэша обновляются `raw_html`, `content_hash`, `raw_size` и `fetched_at`.

У arXiv перед запросом HTML выполняется ещё более дешёвая пакетная проверка Atom-метаданных. Если поле `updated` не изменилось, документ только помечается проверенным. Если API arXiv возвращает ошибку для пакета идентификаторов, пакет рекурсивно делится пополам. Это позволяет локализовать проблемный ID и не отбрасывать целую сотню документов.

У Microsoft Learn аналогичную роль играет `lastmod` из sitemap. Совпадение с `metadata.sitemap_lastmod` означает, что HTML повторно получать не требуется. Для Wikipedia используются стандартные HTTP-валидаторы и итоговое сравнение SHA-256.

Параметр `logic.recrawl_batch_size` ограничивает число старых документов, проверяемых за один запуск. Значение `0` передаётся в MongoDB как отсутствие лимита, поэтому текущая конфигурация разрешает проверить все документы, срок которых наступил. Если перепроверку нужно распределить между запусками, следует указать положительное значение, например `1000`.

### 10.4. Секция `sources.arxiv`

`categories` задаёт тематические разделы, включая `cs.IR`, `cs.AI`, `cs.CL`, `cs.DB`, `cs.DC`, `cs.CR`, `cs.LG` и `cs.SE`. `batch_size: 100` задаёт размер страницы при первичном обнаружении, а `metadata_batch_size: 100` — число уже сохранённых статей в одном запросе перепроверки. `sort_order: descending` означает движение от новых публикаций к старым, а `earliest_month: 1993-01` ограничивает историческую глубину. Состояние обхода сохраняется отдельно для каждой категории, поэтому категории можно продолжать независимо.

Из корпуса исключаются ответы сообщества, видеошоу, события, пользовательские страницы, устаревшие версии и другие разделы, которые хуже подходят для корпуса цельных технических статей. `discovery_interval_seconds` задаёт период полного повторного прохода sitemap и сейчас также равен 90 суткам.

## 11. Как обеспечивается корректная остановка и продолжение

Crawler устанавливает обработчики `SIGINT` и `SIGTERM`. При нажатии `Ctrl+C` общий объект `asyncio.Event` переводится в установленное состояние. Сетевые задержки, циклы источников и ожидания повторных попыток регулярно проверяют этот объект и прекращают работу без принудительного разрушения процесса.

Продолжение реализовано не через один общий номер последнего документа, потому что каждый источник имеет собственную структуру перечисления. Для Wikipedia сохраняется очередь заданий с арендой, для arXiv — месяц, смещение и позиция в пакете по каждой категории, для Microsoft Learn — sitemap и индекс URL. Благодаря этому формулировка «продолжить с места остановки» означает восстановление реального состояния конкретного алгоритма, а не приблизительный повтор всего обхода.

После завершения, включая остановку по сигналу, crawler выполняет агрегацию по `documents` и печатает число документов, суммарный, средний, минимальный и максимальный размер HTML для каждого источника. Статистика выводится в KiB и MiB, что позволяет сразу проверить рост корпуса и обнаружить источник с подозрительно маленькими документами.

## 12. Ограничение нагрузки на внешние сайты

Эффективный crawler не должен означать агрессивный crawler. В реализации используются следующие меры:

1. Перед обходом каждого источника загружается и применяется `robots.txt`. Если правила получить и проверить невозможно, источник не обходится вслепую.
2. `User-Agent` содержит название учебного проекта и контактный email.
3. Для каждого источника задана минимальная задержка, причём для arXiv она увеличена до трёх секунд.
4. Одновременно разрешено только одно соединение к одному хосту.
5. Временные ошибки обрабатываются backoff, а не немедленным циклом повторов.
6. Условные HTTP-запросы, `updated` arXiv и `lastmod` sitemap уменьшают объём повторной загрузки.
7. Размер ответа ограничен до его полного накопления в памяти.
8. Для XML API используются пакеты, а не отдельный запрос метаданных для каждой статьи.

Таким образом, асинхронность применяется между независимыми источниками, а не для создания большого числа конкурентных запросов к одному сайту. Это ускоряет общий сбор корпуса, не нарушая выбранную политику вежливого обхода.

## 13. Связь сырых документов со следующими этапами системы

Crawler записывает оригинал в `documents`, после чего лингвистический обработчик читает поля `_id`, `source`, `source_id`, `url`, `title`, `raw_html` и `content_hash`. По значению `source` выбираются правила извлечения текста для Wikipedia, arXiv или Microsoft Learn. Извлечённый текст и результаты лингвистики записываются уже в другие коллекции.

`content_hash` используется и на следующем этапе. Обработанный документ хранит хэш исходной версии и номер `parser_version`. Если оба значения совпадают, повторная обработка не нужна. Если crawler сохранил изменившийся HTML, его `content_hash` меняется, и лингвистический компонент автоматически понимает, что документ требуется разобрать заново. Поэтому хэш связывает получение документа и последующую обработку, не связывая сами компоненты прямыми вызовами.

## 16. Последовательность рассказа на защите

Рассказ удобно начать с назначения компонента:

> Поисковый робот у меня отделён от лингвистической обработки. Он получает документы из трёх технических источников и сохраняет полный сырой HTML в MongoDB. Это позволяет повторно извлекать текст и менять правила парсинга без повторного скачивания корпуса.

Затем нужно открыть `config.yaml` и сказать:

> Программа получает единственный аргумент — путь к YAML. Секция `db` задаёт подключение и имена коллекций, секция `logic` управляет сетевыми ограничениями и периодом перепроверки, а секция `sources` описывает способ и тематические границы обхода каждого источника.

После этого следует открыть документ в MongoDB Compass:

> Основная коллекция называется `documents`. В ней я храню источник, устойчивый `source_id`, нормализованный URL, заголовок, сырой HTML, метаданные источника, SHA-256, HTTP-валидаторы, размер и три времени. `first_fetched_at` показывает первую загрузку, `fetched_at` — получение текущей версии HTML, а `checked_at` — последнюю проверку независимо от наличия изменений.

При показе индексов нужно продолжить:

> Дубликаты предотвращаются в несколько уровней. URL канонизируется, документ получает устойчивый идентификатор источника, MongoDB имеет уникальные индексы по `(source, source_id)` и `(source, url)`, а запись выполняется через upsert. Хэш не определяет личность документа; он используется только для проверки изменения содержимого.

При объяснении хэша формулировка может быть такой:

> SHA-256 вычисляется по UTF-8-байтам полного сырого HTML и сохраняется как 64 шестнадцатеричных символа. При совпадении хэша я не перезаписываю большой HTML, а обновляю только время проверки и метаданные. При различии заменяются HTML, размер, хэш и время получения новой версии.

После этого нужно показать `crawl_state` и `crawl_queue`:

> Для продолжения после остановки используется не один общий счётчик. arXiv сохраняет месяц, смещение и позицию записи по каждой категории; Microsoft Learn сохраняет sitemap и индекс URL; Wikipedia использует постоянную очередь заданий с арендой. Если процесс аварийно завершится, задание Wikipedia станет доступно после истечения `lease_until`.

Завершить рассказ следует эффективностью и корректностью:

> Три источника работают асинхронно, но на один хост разрешено только одно соединение и задана задержка. Перед обходом проверяется robots.txt, User-Agent содержит контакт, временные ошибки используют backoff, а повторная загрузка сокращается через ETag, Last-Modified, метаданные arXiv и lastmod sitemap. Поэтому общий корпус собирается параллельно по независимым источникам, но каждый сайт обходится осторожно.

## 17. Вопросы, которые может задать преподаватель

### Почему хэш не используется вместо `source_id`?

Хэш описывает текущее содержимое, а не логическую идентичность документа. Содержимое одной статьи меняется при выходе новой версии, но статья должна остаться одной записью. Кроме того, две разные страницы могут временно вернуть одинаковую заглушку. Поэтому идентичность задаётся парой `(source, source_id)`, а SHA-256 только определяет изменение HTML.

### Почему в базе сохраняется сырой HTML, а не только чистый текст?

Правила извлечения текста развиваются независимо от crawler. Сырой HTML позволяет повторить парсинг всего корпуса локально, не нагружая внешние сайты и не теряя элементы документа, которые могут понадобиться позднее. Чистый текст создаётся следующим компонентом и хранится отдельно.

### Как гарантируется отсутствие повторов?

Сначала URL приводится к канонической форме. Затем для каждого источника выбирается устойчивый `source_id`. Уникальные индексы MongoDB запрещают повтор пары `(source, source_id)` и пары `(source, url)`. Наконец, запись выполняется через `upsert`, поэтому повтор той же операции обновляет существующий BSON-документ.

### Что происходит при повторном запуске?

Wikipedia продолжает постоянную очередь, включая задания с истёкшей арендой. arXiv читает контрольную точку отдельной категории и продолжает с сохранённого месяца, пакета и элемента. Microsoft Learn продолжает с сохранённой sitemap и позиции URL. Уже свежие документы не скачиваются повторно.

### Как робот понимает, что страница изменилась?

Сначала используются дешёвые признаки: `updated` arXiv, `lastmod` sitemap, `ETag` и `Last-Modified`. Если всё-таки получен новый HTTP `200`, окончательное решение принимается сравнением SHA-256 сырого HTML.

### Зачем нужны `checked_at` и `fetched_at` одновременно?

Проверка документа не обязательно означает получение новой версии. `checked_at` изменяется после подтверждения актуальности, а `fetched_at` — только после сохранения нового или изменившегося HTML. Один момент нужен планировщику перепроверки, второй описывает возраст содержимого.

### Что произойдёт после HTTP 500?

Для временных статусов выполняются повторы с экспоненциальной задержкой и jitter. Если источник всё равно не отвечает, ошибка этого источника журналируется, другие источники завершают свою работу, после чего процесс печатает статистику и возвращает ненулевой код. Для пакетной перепроверки arXiv проблемный пакет дополнительно делится пополам.

### Почему crawler асинхронный, если на хост разрешено одно соединение?

Асинхронность нужна между независимыми источниками. Пока arXiv выдерживает трёхсекундную задержку или ожидает ответ, Wikipedia и Microsoft Learn могут выполнять свою работу. Ограничение одного соединения на хост предотвращает агрессивный параллелизм внутри одного сайта.

### Как ограничивается использование памяти?

HTTP-ответ читается частями по 64 KiB и прекращается при превышении `max_response_bytes`. Документы сразу сохраняются в MongoDB, а не накапливаются всем корпусом в списке Python. API и sitemap обрабатываются пакетами, а состояние сохраняется по мере продвижения.

### Как crawler связан с последующей обработкой?

Лингвистический компонент читает `raw_html` и выбирает правила извлечения по полю `source`. Он переносит `content_hash` в обработанный документ. Если crawler изменит HTML и хэш, прежний обработанный результат перестанет считаться актуальным и будет построен заново.

## 18. Ограничения и возможные улучшения

SHA-256 вычисляется по сырому HTML, поэтому изменение рекламы, навигации или служебного блока может вызвать повторную обработку даже при неизменном основном тексте. Это можно было бы уменьшить дополнительным хэшем извлечённого содержательного текста, но такой хэш относится уже к HTML-парсеру, а не к crawler.

Текущая очередь с арендой позволяет безопасно восстанавливать задания, однако crawler запускает по одному обработчику каждого источника. При дальнейшем росте корпуса очередь Wikipedia можно обрабатывать несколькими процессами, сохранив атомарный `claim_task`, но тогда потребуется особенно строго контролировать суммарную частоту запросов.

MongoDB хранит только текущую версию HTML. Для аудита изменений можно было бы создать отдельную коллекцию версий, но это существенно увеличило бы объём базы. Для учебной поисковой системы достаточно текущего состояния, времени первой загрузки, времени изменения и хэша.

Главный результат реализации состоит в том, что корпус хранится не как набор случайно скачанных файлов, а как управляемая коллекция документов с устойчивой идентичностью, контролем дублей, проверкой изменений и сохранённым состоянием обхода. Именно эти свойства позволяют безопасно наращивать большой корпус и использовать его в последующих лабораторных работах.
