# Сжатие инвертированного индекса: docID gaps и Variable Byte

## 1. Что именно сжимается

Основной объём инвертированного индекса занимают posting lists — списки документов, в которых встречается каждый терм. В моей реализации один posting содержит две величины:

```text
docID — внутренний числовой идентификатор документа;
TF    — число вхождений терма в этом документе.
```

Без сжатия обе величины можно хранить как `uint32_t`. Тогда одна пара занимает восемь байт:

```text
sizeof(uint32_t docID) + sizeof(uint32_t TF) = 4 + 4 = 8 байт
```

Для десятков миллионов postings это становится основной частью размера индекса. Поэтому при финальной записи применяются два связанных преобразования:

1. абсолютные `docID` заменяются разностями между соседними идентификаторами — gaps;
2. каждый gap и каждая TF кодируются переменным числом байтов алгоритмом Variable Byte.

Общая схема выглядит так:

```text
отсортированные postings одного терма
[(2, 3), (10, 1), (11, 5), (40, 2)]
                │
                ▼
замена docID на gaps
[(2, 3), (8, 1), (1, 5), (29, 2)]
                │
                ▼
Variable Byte для каждого числа
82 83 88 81 81 85 9D 82
```

Сжатие применяется именно к содержимому `postings.bin`. Остальные файлы индекса тоже организованы компактно, но Variable Byte к ним не применяется:

- `lexicon.bin` содержит записи фиксированного размера;
- `terms.bin` содержит непрерывные UTF-8-байты термов;
- `documents.bin` содержит 12-байтовые ObjectId;
- `norms.bin` содержит значения `double`.

Поэтому процент экономии, который печатает индексатор, относится к postings, а не ко всему каталогу `results/boolean_index`.

## 2. Зачем сжимать postings

Сжатие уменьшает не только занимаемое место. Posting lists постоянно читаются при поиске, поэтому меньший файл означает меньше данных, передаваемых с диска и через файловый кэш операционной системы. В информационном поиске затраты на чтение часто важнее нескольких простых побитовых операций декодирования.

При этом нельзя просто сжать весь индекс архиватором. Поисковая система должна быстро перейти к posting list конкретного терма по смещению из лексикона. Если `postings.bin` был бы одним gzip-архивом, для доступа к произвольному участку пришлось бы распаковывать предшествующий поток или поддерживать дополнительную сложную структуру блоков.

Variable Byte сохраняет возможность произвольного доступа:

```text
LexiconEntry.postings_offset
          │
          ▼
прямой seek в postings.bin
          │
          ▼
декодирование postings_count пар
```

Каждый posting list остаётся самостоятельным последовательным диапазоном. Его начало и число элементов известны из `lexicon.bin`, поэтому отдельный маркер конца списка не нужен.

## 3. Где находится реализация

Сам алгоритм находится в двух файлах:

- `src/boolean_index/compression/variable_byte.hpp` объявляет четыре публичные функции и максимальный размер числа;
- `src/boolean_index/compression/variable_byte.cpp` реализует кодирование, декодирование, запись и чтение.

Связь со всем индексом находится в двух местах:

- `src/boolean_index/storage/index_writer.cpp` вычисляет docID gaps и записывает сжатые пары;
- `src/boolean_search/index/index_reader.cpp` читает Variable Byte, восстанавливает абсолютные `docID` и возвращает postings поисковому алгоритму.

Публичный интерфейс небольшой:

```cpp
constexpr size_t VARIABLE_BYTE_MAX_SIZE = 5;

size_t variable_byte_encode(
    uint32_t value,
    uint8_t output[VARIABLE_BYTE_MAX_SIZE]);

bool variable_byte_decode(
    const uint8_t *data,
    size_t size,
    size_t *consumed,
    uint32_t *value);

bool variable_byte_write(FILE *file, uint32_t value);

bool variable_byte_read(FILE *file, uint32_t *value);
```

Первые две функции работают с памятью и удобны для тестирования. Вторые две являются тонкой файловой обвязкой и используются writer и reader индекса.

## 4. Первый этап: gap-кодирование docID

Posting list всегда отсортирован по возрастанию `docID`. Это свойство создаётся ещё во время внешней сортировки индекса. Благодаря сортировке вместо абсолютных идентификаторов можно хранить разности.

Пусть терм встречается в документах:

```text
[2, 10, 11, 40]
```

Первое значение сохраняется относительно нуля, остальные — относительно предыдущего документа:

```text
gap[0] = 2
gap[1] = 10 - 2  = 8
gap[2] = 11 - 10 = 1
gap[3] = 40 - 11 = 29
```

Результат:

```text
абсолютные docID: [2, 10, 11, 40]
gaps:             [2,  8,  1, 29]
```

Код writer делает это непосредственно во время финального слияния:

```cpp
const uint32_t document_gap =
    has_last_document
        ? reader->document_id - last_document
        : reader->document_id;
```

При переходе к новому терму состояние сбрасывается. Поэтому первый gap каждого posting list снова равен первому абсолютному `docID`, а не разности с последним документом предыдущего терма.

## 5. Почему gaps лучше абсолютных docID

Variable Byte особенно хорошо сжимает маленькие числа. Абсолютные `docID` растут вместе с корпусом и могут достигать сотен тысяч или миллионов. Разность между соседними документами конкретного частого терма обычно значительно меньше.

Например, при абсолютных идентификаторах

```text
[100000, 100003, 100010, 100011]
```

gaps равны:

```text
[100000, 3, 7, 1]
```

Только первое число остаётся большим, а остальные помещаются в один байт Variable Byte. Чем чаще терм встречается в корпусе, тем плотнее обычно его posting list и тем меньше средний gap.

Для редкого терма gaps могут быть большими, но алгоритм всё равно корректен: Variable Byte использует до пяти байтов и способен представить любое значение `uint32_t`.

## 6. Восстановление абсолютных docID

Reader выполняет обратную операцию накоплением:

```cpp
uint32_t document_id = 0;

for (...) {
    uint32_t document_gap = 0;
    variable_byte_read(postings, &document_gap);
    document_id += document_gap;
    result.push_back({document_id, term_frequency});
}
```

Для gaps `[2, 8, 1, 29]` восстановление происходит так:

```text
0 + 2  = 2
2 + 8  = 10
10 + 1 = 11
11 + 29 = 40
```

Первый gap может быть равен нулю, потому что первый внутренний документ имеет `docID = 0`. Все следующие gaps одного posting list должны быть строго положительными. Нулевой последующий gap означал бы повтор одного и того же документа и считается повреждением файла.

Перед сложением reader проверяет переполнение:

```cpp
document_gap > UINT32_MAX - document_id
```

Если сумма не помещается в `uint32_t`, posting list отклоняется.

## 7. Второй этап: идея Variable Byte

Обычный `uint32_t` всегда занимает четыре байта, даже если хранит число 1. Variable Byte использует переменное число байтов: маленькое значение занимает один байт, большее — два, три, четыре или пять.

Каждый байт делится на две части:

```text
старший бит     — признак завершения числа;
младшие 7 бит  — полезные данные.
```

В данной реализации старший бит равен:

- `0`, если после текущего байта идут следующие группы того же числа;
- `1`, если текущий байт является последним.

Схематично:

```text
0xxxxxxx 0xxxxxxx 1xxxxxxx
│        │        │
│        │        └─ последняя группа
│        └────────── промежуточная группа
└─────────────────── промежуточная группа
```

Семь полезных бит дают основание 128. Поэтому Variable Byte можно рассматривать как запись числа в системе счисления по основанию 128, где последний разряд дополнительно помечается старшим битом.

## 8. Диапазоны размеров

Количество байтов определяется значением:

| Размер | Диапазон значений | Число полезных бит |
|---:|---:|---:|
| 1 байт | 0–127 | 7 |
| 2 байта | 128–16 383 | 14 |
| 3 байта | 16 384–2 097 151 | 21 |
| 4 байта | 2 097 152–268 435 455 | 28 |
| 5 байт | 268 435 456–4 294 967 295 | до 32 |

Для `uint32_t` достаточно пяти байтов, потому что:

```text
ceil(32 / 7) = 5
```

Пятый байт используется только для старших четырёх значащих бит, так как полные пять групп могли бы представить 35 бит.

## 9. Алгоритм кодирования

Функция `variable_byte_encode` сначала выделяет группы по семь младших бит:

```cpp
do {
    reversed[size++] =
        static_cast<uint8_t>(value & 0x7FU);
    value >>= 7U;
} while (value != 0);
```

Маска `0x7F` в двоичном виде равна `01111111`, поэтому оставляет только семь младших бит. Сдвиг вправо на семь удаляет уже обработанную группу.

Группы извлекаются от младшей к старшей, но в файл записываются от старшей к младшей. Поэтому они временно находятся в массиве `reversed`, а затем копируются в обратном порядке:

```cpp
for (size_t index = 0; index < size; ++index) {
    output[index] = reversed[size - index - 1];
}
```

У последнего байта устанавливается старший бит:

```cpp
output[size - 1] |= 0x80U;
```

Цикл `do ... while` принципиален для числа ноль. Даже ноль должен создать одну группу и кодируется одним байтом `0x80`.

## 10. Пример кодирования числа 128

Число 128 в двоичном виде:

```text
10000000₂
```

Оно разбивается на семибитные группы:

```text
0000001 | 0000000
```

Первая группа не является последней, поэтому её старший бит остаётся нулём:

```text
00000001 = 0x01
```

Вторая группа завершает число, поэтому получает старший бит `1`:

```text
10000000 = 0x80
```

Итог:

```text
128 → 01 80
```

## 11. Граничные примеры

Реализация и тесты фиксируют следующие точные представления:

| Значение | Variable Byte в hex | Размер |
|---:|---|---:|
| 0 | `80` | 1 байт |
| 1 | `81` | 1 байт |
| 127 | `FF` | 1 байт |
| 128 | `01 80` | 2 байта |
| 129 | `01 81` | 2 байта |
| 16 383 | `7F FF` | 2 байта |
| 16 384 | `01 00 80` | 3 байта |
| `UINT32_MAX` | `0F 7F 7F 7F FF` | 5 байт |

На границах `127 → 128` и `16 383 → 16 384` добавляется новый байт. Это нормальное свойство кодирования переменной длины.

## 12. Алгоритм декодирования

Декодер читает байты слева направо. Для каждого байта удаляется старший служебный бит:

```cpp
const uint32_t payload = data[index] & 0x7FU;
```

Накопленное значение умножается на 128 и к нему добавляется новая группа:

```cpp
result = result * 128U + payload;
```

Если старший бит текущего байта установлен, число закончено:

```cpp
if ((data[index] & 0x80U) != 0) {
    *consumed = index + 1;
    *value = result;
    return true;
}
```

Например, для `01 80`:

```text
начало: result = 0

байт 01:
payload = 1
result = 0 × 128 + 1 = 1
маркер конца отсутствует

байт 80:
payload = 0
result = 1 × 128 + 0 = 128
маркер конца установлен
```

Параметр `consumed` сообщает, сколько байтов принадлежало первому числу. Это позволяет декодировать последовательность значений из общего буфера без дополнительного разделителя.

## 13. Проверка переполнения

Операция

```text
result × 128 + payload
```

может переполнить `uint32_t`, если вход содержит повреждённую или намеренно неправильную последовательность. Проверка выполняется до умножения:

```cpp
if (result > (UINT32_MAX - payload) / 128U) {
    return false;
}
```

Неравенство проверяет, что итог не превысит `UINT32_MAX`. Выполнение проверки заранее важно: если сначала допустить переполнение unsigned-числа, результат циклически уменьшится и декодер может принять повреждённые данные за корректное значение.

Декодер обрабатывает не более пяти байтов. Если завершающий старший бит не встретился за это время, код считается некорректным.

## 14. Файловая запись

`variable_byte_write` является небольшой обвязкой:

```cpp
bool variable_byte_write(FILE *file, uint32_t value) {
    uint8_t encoded[VARIABLE_BYTE_MAX_SIZE];
    const size_t size =
        variable_byte_encode(value, encoded);
    return std::fwrite(encoded, 1, size, file) == size;
}
```

Буфер имеет фиксированный максимальный размер пять байтов и находится на стеке. Динамическая память и контейнеры не требуются.

Функция возвращает `false`, если `fwrite` не смог записать все байты. Решение о завершении построения принимает вызывающий writer индекса.

## 15. Файловое чтение

`variable_byte_read` читает по одному байту до установленного старшего бита:

```cpp
for (size_t size = 0;
     size < VARIABLE_BYTE_MAX_SIZE;
     ++size) {
    if (std::fread(&encoded[size], 1, 1, file) != 1) {
        return false;
    }
    if ((encoded[size] & 0x80U) != 0) {
        ...
    }
}
```

После обнаружения конца накопленные байты передаются общему `variable_byte_decode`. Благодаря этому логика проверки значения не дублируется между файловым и буферным интерфейсом.

Функция возвращает `false` при неожиданном конце файла, отсутствии завершающего байта, переполнении или коде длиннее пяти байтов.

## 16. Как writer записывает posting list

Финальное слияние выдаёт postings в порядке терма и возрастающего `docID`. При первом posting нового терма сохраняется текущее смещение в `postings.bin`:

```cpp
current_postings_offset =
    static_cast<uint64_t>(ftello(postings));
```

Затем каждая пара записывается так:

```cpp
if (!variable_byte_write(postings, document_gap) ||
    !variable_byte_write(postings, reader->term_frequency)) {
    fail("ошибка записи сжатого списка документов");
}
```

Физический поток не содержит структуры C++ и не зависит от выравнивания полей. Это просто последовательность Variable Byte-чисел:

```text
gap, TF, gap, TF, gap, TF, ...
```

В `LexiconEntry` сохраняются:

- `postings_offset` — байтовая позиция начала списка;
- `postings_count` — число пар.

Именно эти два поля позволяют reader прочитать правильный диапазон без заголовка и без маркера конца в `postings.bin`.

## 17. Как reader декодирует posting list

Читатель сначала находит терм в лексиконе и получает его `LexiconEntry`. Затем выполняет `seek` к `postings_offset`, резервирует память на `postings_count` элементов и повторяет чтение указанное число раз.

Для каждой позиции читаются два Variable Byte-числа:

```cpp
uint32_t document_gap = 0;
uint32_t term_frequency = 0;

variable_byte_read(postings, &document_gap);
variable_byte_read(postings, &term_frequency);
```

После проверок восстанавливается абсолютный номер:

```cpp
document_id += document_gap;
result.push_back({document_id, term_frequency});
```

Булев поиск преобразует этот результат в список одних `docID`, а TF-IDF сохраняет `term_frequency` и использует её в весе `1 + log10(tf)`.

Таким образом, один сжатый формат обслуживает оба вида поиска.

## 18. Полный пример одного posting list

Предположим, терм `database` встречается в четырёх документах:

```text
docID: [0, 3, 10, 11]
TF:    [2, 1,  5,  1]
```

### Шаг 1. Вычисление gaps

```text
gap[0] = 0
gap[1] = 3 - 0  = 3
gap[2] = 10 - 3 = 7
gap[3] = 11 - 10 = 1
```

Получается:

```text
gaps: [0, 3, 7, 1]
TF:   [2, 1, 5, 1]
```

### Шаг 2. Variable Byte

Все числа меньше 128 и занимают по одному байту:

```text
0 → 80    2 → 82
3 → 83    1 → 81
7 → 87    5 → 85
1 → 81    1 → 81
```

Файл содержит:

```text
80 82 83 81 87 85 81 81
```

Четыре несжатые пары заняли бы:

```text
4 × 8 = 32 байта
```

Сжатый список занимает восемь байтов, то есть в этом примере экономится 75%.

### Шаг 3. Декодирование

Reader попарно получает:

```text
(gap=0, TF=2)
(gap=3, TF=1)
(gap=7, TF=5)
(gap=1, TF=1)
```

Накопление gap восстанавливает `[0, 3, 10, 11]`, после чего исходные postings полностью получены.

## 19. Почему сжимается и term frequency

TF обычно является небольшим числом. Большинство термов встречается в конкретном документе один или несколько раз, поэтому значение чаще всего помещается в один байт Variable Byte.

Если оставить TF несжатой, каждая запись независимо от частоты занимала бы дополнительные четыре байта. Кодирование TF тем же алгоритмом не требует отдельного формата и значительно уменьшает поток.

В редком случае очень большой частоты Variable Byte займёт больше байтов, но поддерживает весь диапазон `uint32_t`. Лингвистический pipeline и индексатор дополнительно требуют, чтобы частота была положительной.

## 20. Фактическая экономия на текущем корпусе

Текущий заголовок индекса содержит:

```text
posting_count = 73 536 673
```

Несжатая оценка для пары `uint32_t docID + uint32_t TF`:

```text
73 536 673 × 2 × 4 = 588 293 384 байта
```

Фактический размер:

```text
postings.bin = 165 766 719 байт
```

Экономия:

```text
1 - 165 766 719 / 588 293 384 ≈ 0,718
```

То есть postings занимают примерно на 71,8% меньше несжатого представления двух `uint32_t`.

Средний размер одной пары:

```text
165 766 719 / 73 536 673 ≈ 2,25 байта
```

В несжатом виде одна пара занимала бы восемь байтов. Средние 2,25 байта означают, что большинство gaps и TF действительно кодируются одним или двумя байтами.

Эта оценка не включает `lexicon.bin`, `terms.bin`, `documents.bin` и `norms.bin`. Она характеризует только эффективность алгоритма хранения postings.

## 21. Как индексатор считает процент экономии

После закрытия `postings.bin` writer получает его фактический размер через `ftello`. Несжатый базовый размер вычисляется так:

> **Именно следующий фрагмент `index_writer.cpp` вычисляет фактический процент сжатия после создания индекса.**

```cpp
// Фактический размер уже записанного postings.bin в байтах.
const off_t compressed_postings_size = ftello(postings);
if (compressed_postings_size < 0) {
    fail("не удалось определить размер сжатого индекса");
}

// Без сжатия каждый posting содержал бы два uint32_t:
// абсолютный docID и term frequency, то есть 8 байт на пару.
const uint64_t uncompressed_size =
    header.posting_count * 2U * sizeof(uint32_t);

// Экономия = доля байтов, отсутствующих в сжатом представлении.
const double saved_percent =
    uncompressed_size == 0
        ? 0.0
        : 100.0 *
              (1.0 - static_cast<double>(compressed_postings_size) /
                         static_cast<double>(uncompressed_size));

std::fprintf(
    stderr,
    "Сжатие postings: %lld байт вместо %llu байт "
    "для docID+TF (%.1f%% экономии)\n",
    static_cast<long long>(compressed_postings_size),
    static_cast<unsigned long long>(uncompressed_size),
    saved_percent);
```

В коде реализована формула:

```text
экономия, % =
    (1 − compressed_postings_size / uncompressed_size) × 100
```

Здесь `compressed_postings_size` — реальный размер `postings.bin`, а `uncompressed_size` — теоретический размер тех же пар при хранении каждого `docID` и каждой TF отдельными четырёхбайтовыми `uint32_t`.

Результат печатается сразу после построения:

```text
Сжатие postings: 165766719 байт вместо 588293384 байт
для docID+TF (71.8% экономии)
```

Если индекс пуст, деления на ноль нет: процент принимается равным нулю.

## 22. Почему выбран Variable Byte

Variable Byte не является самым плотным теоретически возможным кодом. Гамма-кодирование, дельта-кодирование или блочные SIMD-кодеки могут использовать меньше бит или декодировать группы чисел быстрее. Однако Variable Byte хорошо подходит учебной поисковой системе по нескольким причинам.

Алгоритм прост для реализации и проверки. Его можно объяснить через семь полезных бит и один бит завершения без сложной битовой адресации.

Код остаётся байтово выровненным. Reader может читать обычные байты и начинать декодирование непосредственно по `postings_offset`.

Маленькие числа занимают один байт, что хорошо соответствует распределению gaps и TF.

Декодирование выполняется простым циклом и не требует динамической памяти, таблиц или сторонней библиотеки.

Формат поддерживает весь диапазон `uint32_t` и поэтому не вводит специальное ограничение поверх формата `docID`.

Для текущего корпуса практическая экономия более 70% показывает, что простого алгоритма достаточно.

## 23. Почему порядок групп старший к младшему

Код сначала извлекает младшие группы, но записывает их в обратном порядке. Поэтому декодирование напоминает чтение обычного числа слева направо:

```text
result = result × 128 + next_payload
```

Например, группы числа 16 384 равны `[1, 0, 0]`:

```text
((1 × 128 + 0) × 128 + 0) = 16 384
```

Физические байты:

```text
01 00 80
```

Последний нулевой payload получает бит завершения и становится `0x80`.

## 24. Обработка повреждённых данных

На уровне Variable Byte проверяются следующие ошибки:

- неожиданный конец файла до завершающего байта;
- последовательность без маркера конца;
- длина более пяти байтов;
- значение, не помещающееся в `uint32_t`;
- неполная запись в файл.

На уровне posting reader дополнительно проверяются:

- `term_frequency != 0`;
- отсутствие нулевого gap после первого posting;
- отсутствие переполнения при накоплении docID.

Например, последовательность

```text
01 02
```

не содержит байта со старшим битом `1`, поэтому считается оборванной. Последовательность

```text
7F 7F 7F 7F FF
```

имеет формально правильный маркер конца, но описывает значение больше `UINT32_MAX`, поэтому отклоняется проверкой переполнения.

Декодер не проверяет каноничность представления, если значение укладывается в диапазон. Например, число теоретически можно записать с лишней ведущей нулевой группой. Собственный encoder всегда создаёт кратчайшее каноническое представление, поэтому в корректном индексе такой случай не возникает. Для задачи важнее безопасно ограничить длину и исключить переполнение.

## 25. Независимость от порядка байтов машины

В отличие от заголовков и фиксированных структур индекса, Variable Byte определяется отдельными байтами и побитовыми масками. Его представление не зависит от little-endian или big-endian порядка многобайтовых целых чисел.

Например, число 128 всегда записывается как:

```text
01 80
```

Encoder не выполняет `fwrite` объекта `uint32_t`; он явно формирует массив `uint8_t`. Поэтому сам `postings.bin` в части Variable Byte переносим между архитектурами с разным порядком байтов.

Полный индекс всё равно использует нативное представление в `lexicon.bin`, `documents.bin` и `norms.bin`, поэтому переносимость всего каталога определяется не только postings. Но выбранный код сжатия сам по себе от endian не зависит.

## 26. Сложность алгоритма

Кодирование и декодирование одного `uint32_t` обрабатывает не более пяти байтов. Формально это `O(log128 value)`, но для фиксированного 32-битного типа верхняя граница является константой.

Для posting list из `D` документов:

```text
время кодирования:   O(D)
время декодирования: O(D)
дополнительная память writer: O(1) на один posting
```

Writer кодирует данные потоково во время k-way merge. Ему не нужно сначала создавать несжатый posting list целиком.

Reader резервирует `std::vector` на `postings_count`, потому что последующие булевы операции работают с восстановленным отсортированным списком. Сам Variable Byte-декодер динамической памяти не использует.

## 27. Использование STL и ограничения курса

Внутри алгоритма Variable Byte применяются только фиксированные массивы, целочисленные типы и функции файлового ввода-вывода:

```cpp
uint8_t reversed[5];
uint8_t encoded[5];
```

Хеш-таблицы, деревья, ассоциативные контейнеры и готовые библиотеки сжатия не используются. Алгоритм реализован вручную на C++ и является частью основной поисковой системы.

`std::vector` используется выше уровнем для результата декодированного posting list, но не для внутреннего Variable Byte-кода. Это соответствует разрешению преподавателя на строки и векторы и не подменяет реализацию ключевой структуры готовым контейнером.

## 28. Как собрать и проверить реализацию

Сборка проекта:

```bash
cmake -S . -B .build -DCMAKE_BUILD_TYPE=Release
cmake --build .build --parallel
```

Отдельные Google Test для Variable Byte:

```bash
./.build/variable_byte_unit_tests
```

Через CTest:

```bash
ctest --test-dir .build -R 'unit\.variable_byte\.' --output-on-failure
```

В наборе шесть тестов. Они проверяют:

- точные байты граничных значений;
- обратимость `encode → decode` для малых и больших чисел;
- последовательную запись и чтение нескольких значений из файла;
- отказ для оборванного кода без последнего байта;
- отказ при переполнении `uint32_t`;
- правильное значение `consumed` при нескольких числах в одном буфере.

Интеграция с индексом дополнительно проверяется тестами `boolean_index_unit_tests`: они создают posting lists, выполняют слияние блоков, читают gaps и TF обратно и сравнивают восстановленные документы и частоты.

Полное реальное построение:

```bash
./.build/boolean_index config.yaml
```

Именно в конце этой команды выводится фактический размер сжатых postings и процент экономии.

## 29. Что показать преподавателю

Сначала следует показать исходный posting list как возрастающий список `docID` и объяснить gap-кодирование:

```text
[2, 10, 11, 40] → [2, 8, 1, 29]
```

Главная мысль состоит в том, что маленькие gaps кодируются лучше больших абсолютных номеров.

Затем в `variable_byte.cpp` нужно показать три операции encoder:

1. `value & 0x7F` выделяет семь младших бит;
2. `value >>= 7` переходит к следующей группе;
3. `output[last] |= 0x80` помечает конец числа.

После этого на примере `128 → 01 80` следует объяснить значение старшего бита.

Далее нужно показать decoder:

```text
result = result × 128 + payload
```

и предварительную проверку переполнения.

В `index_writer.cpp` следует показать, что writer сначала вычисляет `document_gap`, а затем дважды вызывает `variable_byte_write`: для gap и TF.

В `index_reader.cpp` следует показать обратный путь: чтение двух чисел, проверку и `document_id += document_gap`.

Наконец, при реальном построении индекса нужно обратить внимание преподавателя на строку:

```text
Сжатие postings: ... байт вместо ... байт для docID+TF (...% экономии)
```

Для текущего индекса это около 71,8% экономии именно в `postings.bin`.

## 30. Краткое объяснение для защиты

Сжатие можно объяснить преподавателю следующим образом:

> Posting list отсортирован по внутреннему docID, поэтому я не храню каждый абсолютный номер. Первый номер сохраняется относительно нуля, а дальше записываются разности между соседними документами. Эти gaps обычно значительно меньше абсолютных docID. Затем каждый gap и частота терма кодируются Variable Byte. Число делится на группы по семь полезных бит, а старший бит байта служит маркером конца: ноль означает продолжение, единица — последний байт. Значения до 127 занимают один байт, любой uint32_t — не более пяти. Writer кодирует пары gap и TF непосредственно во время финального слияния индекса. Lexicon хранит смещение начала и количество postings. Reader переходит по смещению, декодирует указанное число пар и восстанавливает абсолютные docID накоплением gaps. Для текущего корпуса postings уменьшились примерно с 588 миллионов до 166 миллионов байт, то есть на 71,8%. Алгоритм написан вручную на C++, не использует готовую библиотеку сжатия и сохраняет возможность произвольного доступа к списку отдельного терма.

Главную последовательность удобно запомнить так:

```text
sorted docID
→ gaps
→ группы по 7 бит
→ бит конца в последнем байте
→ postings.bin
→ Variable Byte decode
→ накопление gaps
→ исходные docID и TF
```

Основные особенности реализации — сочетание gap-кодирования с Variable Byte, потоковая запись без несжатого промежуточного списка, безопасная проверка переполнения и общий формат для булева и TF-IDF-поиска.
