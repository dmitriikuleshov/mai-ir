# Структура индекса простыми словами

Главная идея: индекс — это не один сложный файл, а справочник, который позволяет по слову быстро найти документы, где оно встречается.

## 1. Что было до построения индекса

После лингвистической обработки информация организована по документам:

```text
Документ A:
    database — 2 раза
    cloud    — 1 раз

Документ B:
    security — 3 раза
    cloud    — 2 раза

Документ C:
    database — 1 раз
    query    — 4 раза
```

Для поиска слова `database` пришлось бы проверять каждый документ. Индексатор переворачивает эту структуру:

```text
cloud    → документы A и B
database → документы A и C
query    → документ C
security → документ B
```

Поэтому он называется инвертированным индексом.

## 2. Зачем появляются внутренние `docID`

В MongoDB документы имеют длинные идентификаторы:

```text
ObjectId("671a9f...")
ObjectId("671aa2...")
ObjectId("671ab8...")
```

Хранить такой ObjectId возле каждого терма слишком дорого. Поэтому индексатор назначает документам компактные номера:

```text
docID 0 → ObjectId документа A
docID 1 → ObjectId документа B
docID 2 → ObjectId документа C
```

Теперь инвертированный индекс выглядит компактнее:

```text
cloud    → [(0, 1), (1, 2)]
database → [(0, 2), (2, 1)]
query    → [(2, 4)]
security → [(1, 3)]
```

Каждая пара имеет формат:

```text
(docID, частота терма в документе)
```

Например, запись

```text
database → [(0, 2), (2, 1)]
```

означает, что в документе `0` слово `database` встречается два раза, а в документе `2` — один раз.

## 3. Почему индекс разделён на пять файлов

Логически это один индекс. Физически он разделён на пять файлов, потому что разные части данных читаются по-разному:

```text
Запрос: database
        │
        ▼
  lexicon.bin ─────► где лежит строка и список документов?
        │
        ├──────────► terms.bin: действительно ли это database?
        │
        └──────────► postings.bin: [docID 0, docID 2]
                              │
                              ▼
                       documents.bin
                              │
                              ▼
                    ObjectId документов
                              │
                              ▼
                          MongoDB
                 заголовок, URL, источник
```

Для TF-IDF дополнительно используется `norms.bin`.

## 4. `lexicon.bin` — оглавление индекса

Это аналог содержания книги. Для каждого терма здесь хранится не сама строка и не полный список документов, а адреса, по которым их можно найти:

```text
database:
    term_offset     = 5
    term_length     = 8
    postings_offset = 4
    postings_count  = 2
```

Это означает:

- строка терма находится в `terms.bin`, начиная с байта `5`;
- её длина равна `8` байтам;
- список документов начинается с позиции `4` в `postings.bin`;
- в списке находятся два документа.

Упрощённо файл можно представить так:

| Терм | Где строка | Длина | Где список | Документов |
|---|---:|---:|---:|---:|
| `cloud` | 0 | 5 | 0 | 2 |
| `database` | 5 | 8 | 4 | 2 |
| `query` | 13 | 5 | 8 | 1 |
| `security` | 18 | 8 | 10 | 1 |

В настоящем `lexicon.bin` самих строк нет. Они показаны в таблице только для наглядности.

Записи расположены в алфавитном порядке. Поэтому нужный терм находится двоичным поиском, а не последовательным просмотром всего словаря.

## 5. `terms.bin` — все строки термов

Здесь термы записаны подряд без разделителей:

```text
clouddatabasequerysecurity
```

Файл не содержит пробелов, переводов строк или нулевых байтов. Самостоятельно определить границы термов невозможно: они берутся из `lexicon.bin`.

Например:

```text
term_offset = 5
term_length = 8
```

Из файла читаются восемь байт начиная с пятого, и получается строка `database`.

Таким образом, `lexicon.bin` сообщает, где искать, а `terms.bin` хранит фактический текст. Такое разделение нужно потому, что записи лексикона имеют фиксированный размер, а строки термов — разную длину.

## 6. `postings.bin` — списки документов

Это основная содержательная часть индекса. Для `database` логический список выглядит так:

```text
[(docID=0, tf=2), (docID=2, tf=1)]
```

Но абсолютные `docID` не записываются напрямую. Вместо них записываются разности:

```text
docID: [0, 2]
gaps:  [0, 2]
```

Более наглядный пример:

```text
docID: [10, 11, 20, 100]
gaps:  [10,  1,  9,  80]
```

При чтении номера восстанавливаются накоплением:

```text
10
10 + 1  = 11
11 + 9  = 20
20 + 80 = 100
```

Маленькие числа занимают меньше места при кодировании Variable Byte. Частота терма записывается рядом:

```text
gap, tf, gap, tf, gap, tf...
```

Поэтому один и тот же файл подходит для двух задач:

- булевому поиску нужны `docID`;
- TF-IDF нужны и `docID`, и частоты `tf`.

## 7. `documents.bin` — перевод `docID` обратно в ObjectId

После поиска получается, например:

```text
database → docID [0, 2]
```

Но пользователю номера `0` и `2` ничего не говорят. Нужно получить настоящие документы из MongoDB.

В `documents.bin` ObjectId записаны в порядке `docID`:

```text
позиция 0 → ObjectId документа A
позиция 1 → ObjectId документа B
позиция 2 → ObjectId документа C
```

Поэтому программа напрямую получает ObjectId нужного документа. Затем по ObjectId из MongoDB загружаются заголовок, URL, источник и другие данные для показа результата.

MongoDB не определяет, какие документы подходят запросу. Это уже решил бинарный индекс. База используется для получения человекочитаемой информации.

## 8. `norms.bin` — поправка на длину документа

Этот файл нужен только TF-IDF-поиску.

Если один документ содержит 500 слов, а другой — 10 000, в длинном документе почти любое слово может встретиться больше раз просто из-за его размера. Чтобы длинные документы не получали несправедливое преимущество, веса нормализуются.

Для каждого документа заранее вычисляется одно число — норма:

```text
docID 0 → 8.42
docID 1 → 15.71
docID 2 → 6.38
```

Эти числа хранятся в `norms.bin` в порядке `docID`. Булевому поиску нормы не нужны: для него документ либо соответствует выражению, либо нет.

## 9. Как выполняется запрос `database`

Поиск проходит по следующим шагам:

1. Запрос токенизируется и лемматизируется: `databases` превращается в `database`.
2. В `lexicon.bin` двоичным поиском находится запись `database`.
3. По `term_offset` и `term_length` из `terms.bin` читается строка и проверяется совпадение.
4. По `postings_offset` программа переходит в `postings.bin`.
5. По `postings_count` декодируется нужное количество пар: `[(docID=0, tf=2), (docID=2, tf=1)]`.
6. Для булева поиска остаются номера `[0, 2]`.
7. Через `documents.bin` они преобразуются в MongoDB ObjectId.
8. Из MongoDB загружаются названия и URL документов.

При TF-IDF дополнительно используются частоты из `postings.bin` и нормы из `norms.bin`.

## 10. Как выполняется `database AND cloud`

Из индекса читаются два отсортированных списка:

```text
database → [0, 2]
cloud    → [0, 1]
```

Операция `AND` оставляет документы, находящиеся в обоих списках:

```text
[0, 2] AND [0, 1] → [0]
```

То есть подходит только документ `0`.

Для `OR` списки объединяются:

```text
[0, 2] OR [0, 1] → [0, 1, 2]
```

Повторно читать тексты документов не требуется.

## Самое короткое объяснение

> Индекс представляет собой перевёрнутое отображение «терм → список документов». `lexicon.bin` служит оглавлением и хранит смещения, `terms.bin` хранит строки термов, `postings.bin` — сжатые номера документов и частоты, `documents.bin` переводит внутренние номера обратно в MongoDB ObjectId, а `norms.bin` содержит нормы документов для TF-IDF. Файлы вместе образуют один логический индекс.
