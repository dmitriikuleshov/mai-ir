# TF-IDF: ранжированный поиск по косинусной близости

## 1. Зачем нужен TF-IDF

Булев поиск отвечает на вопрос: «Какие документы удовлетворяют точному логическому условию?». Например, запрос `database AND security` возвращает все документы, в которых присутствуют оба терма. Все найденные документы для булевой модели равноправны: у них нет численной степени соответствия запросу.

Пользователь обычной поисковой системы чаще вводит не логическое выражение, а несколько слов:

```text
distributed database replication
```

В этом случае требуется:

1. найти документы, содержащие хотя бы часть запроса;
2. оценить важность совпавших термов;
3. учесть, сколько раз терм встречается в документе;
4. не позволить очень длинным документам автоматически получать высокий результат;
5. расположить документы от наиболее соответствующего к наименее соответствующему.

TF-IDF решает эту задачу с помощью числовых весов термов. Затем документ и запрос рассматриваются как векторы, а степень их похожести вычисляется через cosine similarity.

Результат ранжированного поиска выглядит так:

```text
doc 124 → score 0.812347
doc 983 → score 0.643920
doc  17 → score 0.401105
```

Чем больше score, тем ближе направление вектора документа к направлению вектора запроса и тем выше документ показывается в выдаче.

## 2. Разница между булевым и TF-IDF-поиском

| Свойство | Булев поиск | TF-IDF |
|---|---|---|
| Форма запроса | `term AND term`, `OR`, `NOT`, скобки | Обычная строка из слов |
| Условие совпадения | Точное логическое выражение | Наличие хотя бы одного терма с положительным весом |
| Результат | Множество документов | Упорядоченный список документов |
| Численная оценка | Нет | Cosine score |
| Частота терма | Для результата не используется | Влияет на вес |
| Редкость терма | Не влияет | Учитывается через IDF |
| Длина документа | Не влияет | Компенсируется нормализацией |

Оба вида поиска используют один и тот же инвертированный индекс. Булев поиск читает только `docID`, а TF-IDF дополнительно использует сохранённую term frequency и таблицу норм документов.

## 3. Общий путь данных

TF-IDF не строится непосредственно по HTML или MongoDB при каждом запросе. Подготовка выполняется заранее:

```text
MongoDB: document_terms
документ → [(лемма, TF), ...]
            │
            ▼
boolean_index
            │
            ├── lexicon.bin: N, df и смещения
            ├── terms.bin: строки термов
            ├── postings.bin: docID + TF
            ├── documents.bin: docID → ObjectId
            └── norms.bin: L2-норма документа
                         │
                         ▼
                    tfidf_search
                         │
                         ▼
              [(docID, cosine score), ...]
                         │
                         ▼
MongoDB: processed_documents
title + source + url для верхних результатов
```

При поиске полный текст документов не читается. Все значения, необходимые для вычисления score, уже находятся в бинарном индексе.

## 4. Где находится реализация

Код расположен в `src/tfidf_search`.

| Часть | Назначение |
|---|---|
| `ranking/weights.cpp` | Формулы логарифмического TF и IDF. |
| `index/ranking_index.cpp` | Открытие общего индекса и загрузка `norms.bin`. |
| `ranking/search.cpp` | Нормализация запроса, вычисление весов и ранжирование. |
| `app/console.cpp` | Чтение запросов, измерение времени и вывод документов. |
| `app/main.cpp` | Сборка всех ресурсов в консольную утилиту. |

Часть чтения лексикона и postings не дублируется. TF-IDF использует общий `boolean_search/index/index_reader.cpp`, который умеет находить терм и возвращать `WeightedPostingList`:

```cpp
struct WeightedPosting {
    uint32_t document_id;
    uint32_t term_frequency;
};
```

Это важная особенность структуры проекта: индекс не делится на «булевый» и «TF-IDF». Один общий инвертированный индекс предоставляет разный объём данных двум поисковым алгоритмам.

## 5. Как запустить TF-IDF-поиск

Перед запуском должны существовать результаты лингвистического pipeline и готовый индекс:

```bash
docker compose up -d
cmake -S . -B .build -DCMAKE_BUILD_TYPE=Release
cmake --build .build --parallel
./.build/linguistics config.yaml
./.build/boolean_index config.yaml
./.build/tfidf_search config.yaml
```

Если корпус и индекс уже подготовлены, достаточно:

```bash
docker compose up -d
./.build/tfidf_search config.yaml
```

В интерактивном режиме программа выводит:

```text
Введите запрос на естественном языке. Ctrl+D — выход.
>
```

Вводить `AND`, `OR` и `NOT` не требуется. Запрос является обычным техническим текстом:

```text
distributed database replication
```

Один запрос можно передать через стандартный ввод:

```bash
echo 'distributed database replication' | ./.build/tfidf_search config.yaml
```

Несколько запросов можно записать по одному в строке:

```bash
./.build/tfidf_search config.yaml < queries.txt
```

## 6. Настройки

Поиск читает настройки из общего `config.yaml`:

```yaml
db:
  uri: mongodb://localhost:27017
  database: mai_ir
  processed_collection: processed_documents

linguistics:
  maximum_token_length: 100
  lemma_dictionary: resources/wordnet_exceptions.tsv
  lemma_vocabulary: resources/wordnet_lemmas.txt
  lemma_overrides: resources/technical_lemma_overrides.tsv

boolean_index:
  output_directory: results/boolean_index
  term_field: lemmas

tfidf_search:
  result_limit: 20
```

| Параметр | Назначение |
|---|---|
| `processed_collection` | Коллекция метаданных найденных документов. |
| `maximum_token_length` | Ограничение токенов запроса. |
| Файлы лемматизатора | Те же ресурсы, которые применялись к корпусу. |
| `output_directory` | Каталог общего бинарного индекса. |
| `result_limit` | Максимальное число ранжированных документов в выдаче. |

Индекс должен быть построен по `lemmas`, потому что запрос также ранжируется по `normalized.lemmas`. Режим индекса по исходным `tokens` с текущим поисковым кодом несовместим.

## 7. Четыре основные величины

Для понимания алгоритма нужно различать TF, DF, IDF и N.

### 7.1. TF — term frequency

TF показывает, сколько раз терм встретился в конкретном документе или запросе:

```text
tf(term, document)
```

Например, если `database` встречается в документе пять раз:

```text
tf(database, document) = 5
```

TF уже был подсчитан лингвистическим pipeline и сохранён в `document_terms`. После построения индекса он находится рядом с `docID` в `postings.bin`.

Для запроса TF рассчитывается во время `linguistics_process`. Если пользователь вводит:

```text
cloud cloud database
```

то:

```text
tf(cloud, query) = 2
tf(database, query) = 1
```

### 7.2. DF — document frequency

DF показывает не общее число вхождений, а количество документов, содержащих терм хотя бы один раз:

```text
df(term)
```

Если `database` встретился тысячу раз, но только в десяти документах:

```text
df(database) = 10
```

В проекте DF не хранится отдельной коллекцией или таблицей. Он уже равен длине posting list и находится в:

```cpp
LexiconEntry.postings_count
```

### 7.3. N — размер корпуса

`N` — полное число индексированных документов:

```text
N = IndexHeader.document_count
```

Текущее значение берётся из заголовка `lexicon.bin`.

### 7.4. IDF — inverse document frequency

IDF показывает информативность терма по корпусу:

```text
idf(term) = log10(N / df(term))
```

Редкий терм имеет большой IDF. Терм, присутствующий почти во всех документах, имеет маленький IDF. Если терм встречается во всех документах:

```text
df = N
idf = log10(N / N) = log10(1) = 0
```

Такой терм не помогает различать документы и получает нулевой вес запроса.

## 8. Зачем используется логарифмический TF

Можно было бы использовать сырую частоту напрямую, но тогда сто повторений терма давали бы в сто раз больший вес, чем одно повторение. Для текста это слишком сильная зависимость: первое появление слова важно, а каждое следующее добавляет всё меньше новой информации.

В проекте используется:

```text
ltf(tf) = 0, если tf = 0
ltf(tf) = 1 + log10(tf), если tf > 0
```

Примеры:

| TF | Логарифмический TF |
|---:|---:|
| 0 | 0 |
| 1 | 1 |
| 10 | 2 |
| 100 | 3 |

То есть увеличение частоты с 1 до 100 повышает вес не в сто, а только в три раза.

Код:

```cpp
double logarithmic_term_frequency(uint64_t frequency) {
    return frequency == 0
        ? 0.0
        : 1.0 + std::log10(
                    static_cast<double>(frequency));
}
```

## 9. Как работает IDF

Код IDF:

```cpp
double inverse_document_frequency(
    uint32_t document_count,
    uint32_t document_frequency) {
    if (document_count == 0 ||
        document_frequency == 0 ||
        document_frequency > document_count) {
        return 0.0;
    }
    return std::log10(
        static_cast<double>(document_count) /
        static_cast<double>(document_frequency));
}
```

Для корпуса из ста документов:

| DF | IDF | Смысл |
|---:|---:|---|
| 1 | `log10(100) = 2` | Очень редкий терм. |
| 10 | `log10(10) = 1` | Умеренно редкий терм. |
| 100 | `log10(1) = 0` | Есть во всех документах и не различает их. |

Некорректные значения дают нулевой вес вместо деления на ноль или отрицательного результата.

## 10. Векторная модель

Каждый различный терм словаря можно представить отдельной координатой. Документ является вектором его весов:

```text
               cloud  database  security
document A  = [  1.3,      1.0,      0.0 ]
document B  = [  1.0,      0.0,      1.5 ]
query       = [  0.7,      0.7,      0.0 ]
```

Реальный словарь содержит миллионы координат, но векторы разреженные: документ или запрос использует только небольшую часть термов.

В проекте полный вектор не создаётся как массив по всему словарю. Для запроса хранятся только присутствующие термы, а документы обходятся через posting lists этих термов.

## 11. Зачем нужна нормализация длины

Длинный документ обычно содержит больше слов и может совпасть с большим числом термов просто из-за объёма. Если складывать ненормированные веса, длинные документы получили бы систематическое преимущество.

Для вектора вычисляется L2-норма:

```text
||v|| = sqrt(v1² + v2² + ... + vk²)
```

Затем каждая координата делится на норму:

```text
normalized_weight_i = weight_i / ||v||
```

После нормализации длина вектора равна единице. Важным становится не абсолютный объём текста, а распределение его терминов.

## 12. Cosine similarity

Косинусная близость двух векторов:

```text
cosine(document, query) =
    dot(document, query) /
    (||document|| × ||query||)
```

Скалярное произведение:

```text
dot(document, query) =
    Σ weight(term, document) × weight(term, query)
```

После предварительной нормализации обоих векторов формула упрощается до суммы произведений нормализованных весов общих термов.

Для неотрицательных весов результат находится между нулём и единицей:

- `0` означает отсутствие общих значимых термов;
- значение ближе к `1` означает сходное направление векторов.

Cosine score не является вероятностью. Значение `0.8` не означает «вероятность релевантности 80%». Это геометрическая мера сходства в выбранной модели весов.

## 13. Что означает `lnc.ltc`

Проект использует нотацию SMART:

```text
document: lnc
query:    ltc
```

Каждая буква описывает один этап взвешивания.

### Документ `lnc`

```text
l — logarithmic TF: 1 + log10(tf)
n — no IDF: IDF на стороне документа не применяется
c — cosine normalization
```

Вес терма документа:

```text
w(t, d) = ltf(tf(t, d)) / ||d||
```

### Запрос `ltc`

```text
l — logarithmic TF запроса
t — IDF = log10(N / df)
c — cosine normalization
```

Ненормированный вес запроса:

```text
raw_w(t, q) =
    ltf(tf(t, q)) × idf(t)
```

Нормированный вес:

```text
w(t, q) = raw_w(t, q) / ||q||
```

Итог:

```text
score(d, q) =
    Σ w(t, d) × w(t, q)
```

IDF применяется только на стороне запроса. Это не ошибка, а выбранная стандартная схема SMART `lnc.ltc`. Редкие термы влияют на направление запроса сильнее, а документный вектор нормализуется по логарифмическим TF.

## 14. Почему нормы документов вычисляются заранее

Норма документа зависит только от частот его термов:

```text
||d|| = sqrt(
    Σ [1 + log10(tf(t, d))]²
)
```

Она не зависит от текущего запроса. Поэтому вычислять её при каждом поиске было бы бессмысленно и дорого.

Во время построения индекса функция `add_document_terms` уже читает все пары `[term, frequency]` документа и одновременно накапливает квадрат нормы:

```cpp
const double weight =
    logarithmic_term_frequency(stored_frequency);
squared_norm += weight * weight;
```

После документа:

```cpp
document_norm = std::sqrt(squared_norm);
```

Полученное значение записывается в `norms.bin` в позиции соответствующего внутреннего `docID`.

## 15. Структура `norms.bin`

Файл начинается с 16-байтового заголовка:

```cpp
struct DocumentNormHeader {
    char magic[8];
    uint32_t version;
    uint32_t document_count;
};
```

Magic равен:

```text
MAIIRNRM
```

После заголовка находится по одному `double` на каждый документ:

```text
norm(docID 0)
norm(docID 1)
norm(docID 2)
...
```

Позиция:

```text
offset = 16 + docID × sizeof(double)
```

На текущем индексе:

```text
document_count = 151182
size = 16 + 151182 × 8
     = 1 209 472 байта
```

Файл мал по сравнению с postings и целиком загружается в память при старте `tfidf_search`.

## 16. Открытие ранжированного индекса

Структура ранжированного индекса расширяет базовый булев индекс:

```cpp
struct TfidfIndex {
    BooleanIndex boolean_index;
    std::vector<double> document_norms;
};
```

Сначала `boolean_index_open` открывает и проверяет:

```text
lexicon.bin
terms.bin
postings.bin
documents.bin
```

Затем `tfidf_index_open` открывает `norms.bin` и проверяет:

- magic;
- версию формата;
- совпадение `document_count` с базовым индексом;
- наличие всех значений;
- конечность каждой нормы;
- отсутствие отрицательных норм.

Если `norms.bin` отсутствует или относится к другой сборке индекса, поиск не запускается.

## 17. Где берутся N, DF и TF

Все величины извлекаются из уже существующей структуры индекса:

| Величина | Источник |
|---|---|
| `N` | `IndexHeader.document_count` в `lexicon.bin`. |
| `df(term)` | `LexiconEntry.postings_count`. |
| `tf(term, document)` | Второе Variable Byte-число posting в `postings.bin`. |
| `tf(term, query)` | Частота леммы после `linguistics_process` запроса. |
| `||document||` | `document_norms[docID]` из `norms.bin`. |
| ObjectId | Позиция `docID` в `documents.bin`. |

Отдельный файл IDF не нужен. IDF быстро рассчитывается по двум целым значениям `N` и `df` непосредственно во время запроса.

## 18. Нормализация запроса

Пользовательский запрос проходит тот же pipeline, что и документы:

```cpp
const LinguisticResult normalized = linguistics_process(
    query,
    std::strlen(query),
    maximum_token_length,
    dictionary);
```

Поэтому:

```text
databases → database
queries   → query
C++       → c++
SHA‑256   → sha-256
```

Одинаковая нормализация обязательна. Если индекс хранит ключ `database`, а запрос оставляет `databases`, posting list не будет найден.

В отличие от булева parser, ранжированный поиск принимает многословный естественный запрос без операторов. После pipeline `normalized.lemmas` уже содержит различные леммы и частоту каждой леммы в запросе.

Если строка не содержит ни одного индексируемого терма, возвращается ошибка:

```text
запрос не содержит индексируемых терминов
```

## 19. Вычисление весов запроса

Для каждой леммы запроса выполняется двоичный поиск в лексиконе. Неизвестные термы пропускаются.

Для найденного терма берутся:

```text
N  = document_count
df = postings_count
tf = частота леммы в запросе
```

Ненормированный вес:

```cpp
weight = logarithmic_term_frequency(term.count) *
         inverse_document_frequency(
             document_count,
             entry.postings_count);
```

Одновременно накапливается квадрат нормы запроса:

```cpp
squared_query_norm += weight * weight;
```

После всех термов:

```cpp
query_norm = std::sqrt(squared_query_norm);
```

Каждый вес делится на `query_norm` непосредственно перед обходом posting list.

Термы с `df = N` получают IDF 0 и не добавляются в `query_weights`. Если все известные термы имеют нулевой IDF или все термы неизвестны, результат будет пустым без синтаксической ошибки.

## 20. Как повторение терма влияет на запрос

Запрос

```text
cloud database
```

задаёт одинаковый TF обоих термов: по одному вхождению.

Запрос

```text
cloud cloud database
```

увеличивает логарифмический TF `cloud`:

```text
ltf(cloud) = 1 + log10(2) ≈ 1.30103
ltf(database) = 1
```

После нормализации направление вектора запроса смещается в сторону `cloud`. Документы, сильнее связанные с `cloud`, поднимаются, а документы, совпадающие в основном по `database`, могут опуститься.

## 21. Накопление score

Для всех документов создаётся прямой массив:

```cpp
std::vector<double> scores(document_count, 0.0);
```

Индекс массива является `docID`. Это заменяет хеш-таблицу `docID → score` и обеспечивает доступ за `O(1)`.

Для каждого терма запроса загружается его `WeightedPostingList`. Затем обходятся только документы, содержащие этот терм:

```cpp
const double contribution =
    normalized_query_weight *
    logarithmic_term_frequency(
        posting.term_frequency) /
    document_norm;

scores[posting.document_id] += contribution;
```

Это в точности произведение:

```text
normalized query weight × normalized document weight
```

Вклад всех общих термов суммируется и образует cosine score.

Документы, не входящие ни в один posting list запроса, вообще не обходятся при накоплении вкладов.

## 22. Зачем нужен `touched_documents`

После создания массива `scores` было бы можно пройти по всем `N` документам и выбрать ненулевые значения. Вместо этого при первом положительном вкладе `docID` добавляется в отдельный список:

```cpp
if (scores[posting.document_id] == 0.0) {
    touched_documents.push_back(posting.document_id);
}
```

После ранжирования обходятся только затронутые документы:

```cpp
for (uint32_t document_id : touched_documents) {
    const double score = scores[document_id];
    ...
}
```

Такой список особенно полезен для редкого запроса, когда postings затрагивают небольшую часть корпуса.

Массив `scores` всё равно инициализируется на `N` элементов, но последующая фильтрация не требует второго полного прохода по корпусу.

## 23. Сортировка и ограничение результата

Все документы с положительным конечным score переносятся в:

```cpp
struct RankedDocument {
    uint32_t document_id;
    double score;
};
```

Сортировка выполняется:

```text
1. score по убыванию;
2. при равном score — docID по возрастанию.
```

Второе правило делает результат детерминированным.

Сначала сохраняется полное число совпадений:

```cpp
result.matched_documents = result.documents.size();
```

Только после этого применяется `result_limit`:

```cpp
if (result.documents.size() > result_limit) {
    result.documents.resize(result_limit);
}
```

Поэтому консоль может показать:

```text
Совпало документов: 1534 | показано: 20
```

Ограничение уменьшает выдачу и число запросов метаданных, но текущая реализация всё равно вычисляет и сортирует все документы с положительным score.

## 24. Полный числовой пример

Рассмотрим три документа и три терма:

```text
doc 0: cloud TF=2, database TF=1
doc 1: cloud TF=1, security TF=3
doc 2: database TF=2, security TF=1
```

Запрос:

```text
cloud database
```

### Шаг 1. Логарифмические TF документов

```text
ltf(1) = 1
ltf(2) = 1 + log10(2) ≈ 1.30103
ltf(3) = 1 + log10(3) ≈ 1.47712
```

### Шаг 2. Нормы документов

```text
||doc0|| = sqrt(1.30103² + 1²)
         ≈ 1.64094

||doc1|| = sqrt(1² + 1.47712²)
         ≈ 1.78378

||doc2|| = sqrt(1.30103² + 1²)
         ≈ 1.64094
```

### Шаг 3. IDF запроса

Каждый терм встречается в двух документах:

```text
N = 3
df(cloud) = 2
df(database) = 2

idf = log10(3 / 2) ≈ 0.17609
```

Оба терма запроса встречаются один раз, поэтому их ненормированные веса одинаковы:

```text
raw_w(cloud) = 1 × 0.17609
raw_w(database) = 1 × 0.17609
```

После cosine-нормализации каждый вес равен:

```text
1 / sqrt(2) ≈ 0.70711
```

Общий одинаковый множитель IDF сокращается при нормализации запроса.

### Шаг 4. Score

Документ 0 содержит оба терма:

```text
score(doc0) =
    0.70711 × 1.30103 / 1.64094 +
    0.70711 × 1       / 1.64094
  ≈ 0.99155
```

Документ 2 содержит только `database` с TF=2:

```text
score(doc2) =
    0.70711 × 1.30103 / 1.64094
  ≈ 0.56063
```

Документ 1 содержит только `cloud` с TF=1 и имеет значительный вес другого терма `security` в своей норме:

```text
score(doc1) =
    0.70711 × 1 / 1.78378
  ≈ 0.39641
```

Выдача:

```text
doc 0 → 0.99155
doc 2 → 0.56063
doc 1 → 0.39641
```

Этот пример используется в unit-тесте и показывает сразу три свойства: совпадение по двум термам лучше совпадения по одному, большая TF повышает вклад, а норма компенсирует остальные термы документа.

## 25. Связь с файлами общего индекса

TF-IDF использует каждый файл по конкретному назначению.

### `lexicon.bin`

Из заголовка берётся:

```text
N = document_count
```

Из записи терма берётся:

```text
df = postings_count
postings_offset
```

### `terms.bin`

Используется при двоичном поиске нормализованной строки терма.

### `postings.bin`

После Variable Byte-декодирования предоставляет:

```text
docID
tf(term, document)
```

### `norms.bin`

Предоставляет:

```text
||document||
```

по прямому индексу `document_norms[docID]`.

### `documents.bin`

После ранжирования переводит внутренний `docID` в MongoDB ObjectId для вывода результата.

Таким образом, TF-IDF не создаёт второй словарь или второй posting index. Он добавляет к общему индексу только файл норм и использует сохранённую TF.

## 26. Связь с MongoDB

MongoDB участвует в двух разных моментах.

### Во время построения индекса

`boolean_index` читает из `document_terms` частоты лемм каждого документа. По ним:

- формируются postings с TF;
- вычисляется L2-норма документа;
- сохраняется соответствие ObjectId и внутреннего `docID`.

### Во время поискового запроса

Ранжирование выполняется только по бинарным файлам. После получения верхних `docID` файл `documents.bin` даёт ObjectId, и для показанных результатов из `processed_documents` читаются:

```text
title
source
url
```

Поле `text` для вычисления score не читается. MongoDB не перебирает документы и не выполняет полнотекстовый поиск.

Это разделение важно: бинарный индекс отвечает за скорость и ранжирование, MongoDB — за хранение корпуса и метаданных.

## 27. Что измеряет время в консоли

Перед вызовом `tfidf_search` сохраняется `std::chrono::steady_clock::now()`, а после возврата вычисляется длительность в миллисекундах.

В измерение входят:

- токенизация и лемматизация запроса;
- поиск термов в лексиконе;
- декодирование posting lists;
- вычисление TF-IDF-весов;
- накопление score;
- сортировка и ограничение результата.

В измерение не входят последующие MongoDB-запросы заголовков и URL. Поэтому строка:

```text
поиск: 12.345 мс
```

характеризует поисковый алгоритм, а не сетевое или консольное отображение результатов.

## 28. Сложность алгоритма

Обозначим:

- `N` — число документов;
- `V` — число термов словаря;
- `Q` — число различных лемм запроса;
- `df_i` — длина posting list i-го терма запроса;
- `M` — число документов с положительным score.

### Нормализация запроса

Линейна по длине текста запроса плюс словарные проверки лемматизатора.

### Поиск термов

Для каждого терма выполняется двоичный поиск:

```text
O(Q log V)
```

### Инициализация score

Создание `scores(document_count, 0.0)`:

```text
O(N)
```

### Декодирование и накопление

Каждый posting нужного терма обрабатывается один раз:

```text
O(Σ df_i)
```

Один документ может присутствовать в нескольких списках и получить несколько вкладов, что является необходимой частью скалярного произведения.

### Сортировка

Все документы с ненулевым score сортируются:

```text
O(M log M)
```

### Итоговая оценка

```text
O(N + Q log V + Σdf_i + M log M)
```

Для редкого запроса `Σdf_i` и `M` невелики. Для очень частых термов основными затратами становятся длинные posting lists, инициализация score и сортировка большого числа совпадений.

## 29. Потребление памяти

Постоянно после открытия индекса находятся нормы:

```text
N × sizeof(double)
```

На текущем корпусе это около 1,15 MiB плюс заголовок файла.

На один запрос создаётся:

- `scores`: `N` значений `double`;
- `touched_documents`: до `N` значений `uint32_t`;
- один декодированный `WeightedPostingList` для текущего терма;
- массив результатов для `M` документов;
- небольшой список весов запроса.

Прямой массив score выбран вместо запрещённой хеш-таблицы. Он прост, даёт доступ `O(1)` и при текущих 151 тысячах документов занимает примерно 1,15 MiB.

## 30. Использование STL и требования курса

Реализация использует разрешённые контейнеры:

- `std::vector<double>` для норм и score;
- `std::vector<uint32_t>` для затронутых документов;
- `std::vector<QueryTermWeight>` для запроса;
- `std::vector<RankedDocument>` для результата;
- `std::string` для нормализованных термов.

Готовые хеш-таблицы и деревья не применяются. Соответствие `docID → score` реализовано прямым массивом, а поиск терма — двоичным поиском по дисковому лексикону.

Сортировка результата выполняется `std::sort`, что соответствует разрешению использовать векторы и алгоритмы над последовательностями.

## 31. Поведение особых запросов

### Неизвестный терм

Если терм отсутствует в лексиконе, он пропускается. Если все термы неизвестны, результат пустой:

```text
Совпало документов: 0
```

### Терм во всех документах

Если `df = N`, IDF равен нулю. Терм не влияет на порядок и исключается из весов запроса.

### Пустой или пунктуационный запрос

Если pipeline не создаёт ни одной леммы, возвращается понятная ошибка.

### Повтор терма

Повтор увеличивает логарифмический TF запроса и меняет направление query vector.

### Документ с нулевой нормой

Такой документ не получает вклад. В нормальном индексе принятому документу с термами соответствует положительная норма; нулевое значение возможно для пустого массива.

### Равный score

Документы сортируются по возрастанию `docID`, поэтому порядок воспроизводим.

## 32. Ограничения текущего решения

TF-IDF учитывает термы как независимые признаки. Порядок слов, расстояние между ними и фразы не учитываются. Документ с `distributed` и `database` в разных частях текста получает совпадение по обоим термам.

Нет полевого взвешивания. Совпадение в заголовке не получает больший вес, чем совпадение в основном тексте, потому что индекс хранит общую частоту документа.

Нет семантического поиска: синонимы без общей леммы считаются разными термами.

Не используются BM25, pivoted length normalization или обученная модель ранжирования. Выбрана классическая и объяснимая схема `lnc.ltc`.

Вся выдача с положительным score сортируется перед `resize`. Для очень большого `M` алгоритм top-k через ограниченную кучу был бы экономнее, но текущий вариант проще и детерминирован.

Для каждого терма posting list декодируется целиком в `std::vector`, а не обрабатывается потоково.

Массив `scores` обнуляется для всех `N` документов на каждый запрос. При текущем размере корпуса это недорого; на корпусе в сотни миллионов документов понадобилась бы более разреженная структура.

## 33. Почему TF-IDF является объяснимым ранжированием

Для любого результата можно объяснить score через три причины:

1. какие термы запроса присутствуют в документе;
2. как часто они встречаются в документе;
3. насколько они редки во всём корпусе.

Норма дополнительно показывает, почему длинный документ с большим числом посторонних термов может получить меньший score, чем специализированный документ.

В отличие от нейросетевой модели, здесь нет скрытых параметров. Каждое значение берётся из конкретного поля индекса и участвует в явной формуле.

## 35. Что показать преподавателю

Сначала нужно кратко сравнить модели:

> Булев поиск возвращает точное множество без порядка. TF-IDF принимает обычный многословный запрос и сортирует документы по численной близости.

Затем следует показать формулы:

```text
ltf(tf) = 1 + log10(tf)
idf(t) = log10(N / df(t))

document = lnc
query = ltc

score = cosine(document, query)
```

После этого в структуре индекса нужно показать происхождение данных:

```text
N     ← IndexHeader.document_count
df    ← LexiconEntry.postings_count
TF    ← postings.bin
norm  ← norms.bin
docID ← postings.bin
OID   ← documents.bin
```

Запуск:

```bash
./.build/tfidf_search config.yaml
```

Полезные запросы:

```text
distributed database replication
information retrieval ranking
C++ memory management
cloud database
cloud cloud database
```

Последние два запроса демонстрируют влияние повторной частоты в запросе. Следует обратить внимание на `score`, число совпавших документов, число показанных документов и время в миллисекундах.

В коде нужно последовательно открыть:

1. `weights.cpp` — две основные формулы;
2. `builder.cpp` — предварительный расчёт нормы документа;
3. `ranking_index.cpp` — загрузку `norms.bin`;
4. `search.cpp` — веса запроса, массив score, обход postings и сортировку;
5. `console.cpp` — время поиска и получение метаданных.

## 36. Готовое объяснение для защиты

TF-IDF можно объяснить преподавателю следующим образом:

> TF-IDF нужен для ранжирования обычного многословного запроса. TF показывает частоту терма в конкретном документе, DF — число документов с термом, а IDF равен логарифму отношения полного числа документов к DF и повышает вес редких информативных терминов. В моей реализации используется схема SMART lnc.ltc. Документ получает логарифмический TF без IDF и нормализуется по L2-норме. Запрос получает логарифмический TF, IDF и также нормализуется. Score является скалярным произведением двух нормализованных векторов, то есть cosine similarity. Все данные берутся из общего инвертированного индекса: N находится в заголовке лексикона, DF равен длине posting list, TF хранится рядом с docID в postings.bin, а заранее рассчитанная норма документа находится в norms.bin. Запрос проходит тот же токенизатор и лемматизатор, что и корпус. Для каждого терма обходятся только документы его posting list, вклад добавляется в прямой vector scores по docID, затем затронутые документы сортируются по убыванию score. documents.bin переводит docID в ObjectId, а MongoDB используется только для заголовка, источника и URL верхних результатов.

Главную последовательность удобно запомнить так:

```text
natural language query
→ tokenizer + lemmatizer
→ query TF
→ lexicon: N and DF
→ query IDF and normalization
→ postings: document TF
→ norms.bin: document normalization
→ accumulated cosine score
→ sort by score
→ docID → ObjectId → MongoDB metadata
```

Основные особенности реализации — общая структура индекса с булевым поиском, заранее вычисленные нормы документов, вычисление IDF из лексикона без отдельной таблицы, схема `lnc.ltc`, прямой массив score вместо хеш-таблицы и отделение поискового времени от загрузки метаданных.
