# Токенизатор: выделение термов из технического текста

## 1. Что такое токенизация

Токенизация — это преобразование непрерывного текста в последовательность отдельных единиц, которые далее используются лемматизатором и поисковым индексом. Такие единицы называются токенами. В простом художественном тексте токен часто почти совпадает со словом, но для технического корпуса разделение только по пробелам или пунктуации недостаточно.

Например, следующие конструкции должны по возможности сохраняться целиком:

```text
C++
C#
.NET
node.js
sha-256
std::vector
https://example.com/docs
dev@example.com
/usr/bin/python
@openai/sdk
--threads=8
```

Если механически разделить текст по всем знакам пунктуации, `C++` превратится в `c`, `node.js` — в два несвязанных слова, URL — в большое число фрагментов, а `std::vector` потеряет смысл пространства имён. С другой стороны, нельзя считать любой знак частью токена: в обычной фразе `client/server` косая черта должна разделять два слова, а запятые и скобки вокруг слова не должны попадать в индекс.

Поэтому токенизатор в проекте не является вызовом готовой функции наподобие `split`. Он выполняет собственный последовательный разбор текста, учитывает Unicode и применяет контекстные правила для распространённых технических конструкций.

Общее преобразование выглядит так:

```text
"Use C++ and Node.js with std::vector."
                    │
                    ▼
["use", "c++", "and", "node.js", "with", "std::vector"]
```

Токенизатор отвечает только за нормализацию символов и определение границ токенов. Он не приводит `queries` к `query` и `running` к `run`: это следующий отдельный этап лемматизации.

## 2. Где находится реализация

Основной код находится в каталоге `src/linguistics/language`:

- `tokenizer.hpp` содержит публичный интерфейс и структуры результата;
- `tokenizer.cpp` содержит декодирование UTF-8, нормализацию входа и правила выделения токенов;
- `pipeline.cpp` вызывает токенизатор перед лемматизатором и затем считает частоты.

Публичный интерфейс намеренно небольшой:

```cpp
using TokenList = std::vector<std::string>;

struct TokenizationResult {
    TokenList tokens;
    uint64_t token_characters = 0;
    uint64_t elapsed_nanoseconds = 0;
};

TokenizationResult tokenize_text(
    const char *text,
    size_t text_size,
    size_t maximum_token_length);
```

На вход передаются указатель на текст, точный размер буфера в байтах и максимальная допустимая длина одного токена. На выходе возвращаются токены в исходном порядке, их суммарная длина в Unicode-символах и время выполнения.

Отдельного исполняемого файла только для токенизации нет. Код собирается в библиотеку `linguistics_pipeline`, которую используют обработчик корпуса, булевый поиск и поиск TF-IDF. Благодаря этому документы и поисковые запросы разбираются одной реализацией.

## 3. Почему передаётся размер текста

Функция не полагается на завершающий нулевой байт C-строки. Она получает `text_size` и читает ровно указанное число байтов:

```cpp
TokenizationResult tokenize_text(
    const char *text,
    size_t text_size,
    size_t maximum_token_length);
```

Такой интерфейс имеет несколько преимуществ:

- можно обрабатывать фрагмент большого буфера без создания временной строки;
- функция не прочитает данные за установленной границей;
- встроенный нулевой байт считается разделителем, а не неожиданным концом всего входа;
- пустой буфер с `text == nullptr` и `text_size == 0` обрабатывается безопасно.

Например, если передать буфер `alpha beta`, но указать размер 5, результатом будет только `alpha`. Это поведение отдельно проверяется тестом.

Размер входа измеряется в байтах, потому что UTF-8 кодирует разные символы разным числом байтов. Ограничение `maximum_token_length`, напротив, измеряется в Unicode-символах, а не в байтах. Поэтому русское слово `данные` имеет длину шесть для ограничения токена, хотя в UTF-8 занимает двенадцать байтов.

## 4. Общий порядок работы

Внешняя функция выполняет два основных этапа:

```cpp
const std::string normalized = normalize_input(text, text_size);

TokenizationResult result;
result.tokens = tokenize_normalized(
    normalized, maximum_token_length, &result.token_characters);
```

На первом этапе входной UTF-8 декодируется и приводится к единообразному виду. Нормализуются пробелы, типографские кавычки, разные тире и полноширинные ASCII-символы. Некорректные UTF-8-последовательности заменяются границей между токенами.

На втором этапе нормализованная строка последовательно просматривается слева направо. Программа определяет начало токена, добавляет допустимые символы, обрабатывает технические разделители и завершает токен при первой внешней границе.

После выделения токена удаляется английское притяжательное окончание `'s`, проверяется максимальная длина, а принятый токен добавляется в выходной `std::vector`.

Полный порядок можно представить так:

```text
байты UTF-8
    │
    ▼
проверка и декодирование символов
    │
    ▼
нормализация пробелов, тире, апострофов и fullwidth ASCII
    │
    ▼
поиск начала следующего токена
    │
    ▼
чтение букв, цифр и допустимых внутренних разделителей
    │
    ▼
обработка специальных технических форм
    │
    ▼
удаление притяжательного 's
    │
    ▼
проверка maximum_token_length
    │
    ▼
добавление токена и обновление статистики
```

## 5. Безопасное декодирование UTF-8

UTF-8 представляет ASCII одним байтом, а остальные символы — последовательностями длиной от двух до четырёх байтов. Токенизатору необходимо знать не только байты, но и Unicode code point, то есть числовое значение символа. Иначе невозможно правильно считать длину токена или отличать Unicode-пробел от буквы другого алфавита.

Для одного декодированного символа используется структура:

```cpp
struct DecodedCharacter {
    CodePoint codepoint;
    size_t width;
    bool valid;
};
```

`codepoint` хранит значение символа, `width` — число занятых байтов UTF-8, а `valid` показывает корректность кодировки.

Функция `decode_utf8` распознаёт одно-, двух-, трёх- и четырёхбайтовые последовательности. При этом она проверяет:

- наличие всех необходимых байтов продолжения;
- правильный двоичный префикс байтов продолжения;
- отсутствие избыточной, или overlong, кодировки;
- отсутствие значений из surrogate-диапазона UTF-16;
- непревышение максимального значения Unicode `U+10FFFF`.

Если последовательность некорректна, один ошибочный байт считается прочитанным, а в нормализованный текст добавляется пробел. Это позволяет продолжить обработку следующей корректной части, а не завершать весь документ из-за одного повреждённого символа.

Например, повреждённый фрагмент между `alpha` и `beta` даст два независимых токена:

```text
alpha <некорректные байты> beta
            ↓
["alpha", "beta"]
```

Такое поведение особенно важно для большого корпуса, где единичная ошибка кодировки не должна останавливать обработку сотен тысяч документов.

## 6. Нормализация Unicode перед выделением токенов

Одинаковые по смыслу символы могут иметь разные кодовые точки. Без нормализации визуально одинаковые термы образовали бы разные ключи индекса.

Функция `normalize_input` приводит следующие группы к единому представлению.

### 6.1. Пробельные символы

Обычные пробелы, табуляции, переводы строк, неразрывный пробел, тонкие пробелы, узкий неразрывный пробел и идеографический пробел превращаются в обычный ASCII-пробел.

```text
alpha<TAB>beta
alpha<NBSP>beta
alpha<IDEOGRAPHIC SPACE>beta
              ↓
["alpha", "beta"]
```

### 6.2. Типографские апострофы

Левая и правая типографские одинарные кавычки `‘` и `’` превращаются в обычный апостроф `'`. Благодаря этому формы `model's` и `model’s` обрабатываются одинаково.

### 6.3. Дефисы и тире

Unicode содержит несколько визуально похожих знаков: дефис, неразрывный дефис, figure dash, en dash и em dash. Поддерживаемые варианты нормализуются до ASCII-дефиса `-`.

```text
state-of-the-art
state‑of‑the‑art
state—of—the—art
              ↓
state-of-the-art
```

### 6.4. Полноширинные ASCII-символы

Полноширинные формы, часто встречающиеся в восточноазиатском тексте, преобразуются в обычный ASCII. Например:

```text
ＤＡＴＡＢＡＳＥ，ＮＯＤＥ．ＪＳ Ｃ＋＋ １２３
                       ↓
["database", "node.js", "c++", "123"]
```

Остальные корректные Unicode-символы копируются в исходной UTF-8-кодировке без транслитерации.

## 7. Какие символы считаются частью обычного слова

Для ASCII основными символами слова считаются буквы и цифры, то есть результат `std::isalnum`. Английские ASCII-буквы при добавлении в токен переводятся в нижний регистр:

```text
Database DATABASE DaTaBaSe
            ↓
database database database
```

Это устраняет различия регистра в индексе. Повторения не удаляются: каждое вхождение сохраняется отдельным элементом, потому что позже по ним рассчитывается частота терма.

Для не-ASCII символов правило другое. Символ считается частью слова, если он не относится к поддерживаемым диапазонам Unicode-пунктуации, стрелок, математических знаков и CJK-пунктуации. Благодаря этому сохраняются буквы разных языков:

```text
поиск данные 数据 検索 café
          ↓
["поиск", "данные", "数据", "検索", "café"]
```

Текущая реализация не выполняет полное Unicode-приведение регистра. ASCII-часть переводится в нижний регистр, но регистр кириллицы или других письменностей сохраняется. Для текущего англоязычного технического корпуса это допустимое ограничение.

## 8. Обычная внешняя пунктуация

Пунктуация вокруг слова не входит в токен. Скобки, запятые, точки с запятой, кавычки, восклицательные и вопросительные знаки служат границами:

```text
(database), [retrieval]; {index}! "search"?
                       ↓
["database", "retrieval", "index", "search"]
```

Если подряд встречается несколько внешних разделителей, они просто пропускаются. Токен создаётся только с позиции, на которой начинается буква, цифра или одна из разрешённых технических конструкций.

Unicode-стрелки, математические и графические символы также разделяют соседние слова:

```text
alpha→beta gamma≠delta epsilon✓zeta
                       ↓
["alpha", "beta", "gamma", "delta", "epsilon", "zeta"]
```

## 9. Внутренние разделители составных токенов

Точка, подчёркивание, апостроф и дефис могут быть частью составного токена, но только если после них продолжается слово:

```cpp
bool inner_separator(unsigned char value) {
    return value == '.' || value == '_' ||
           value == '\'' || value == '-';
}
```

За счёт этого сохраняются:

```text
node.js
snake_case
sha-256
state-of-the-art
mother-in-law
package.module.name
rock'n'roll
```

Проверка следующего символа не позволяет оставлять разделитель на конце. В тексте `alpha. beta- gamma_ delta'` результатом будут `alpha`, `beta`, `gamma`, `delta`, а не токены с хвостовой пунктуацией.

Точка отдельно разрешается в начале токена, если за ней идёт слово. Это сохраняет `.NET` и имена скрытых файлов:

```text
.NET .config ..hidden
       ↓
[".net", ".config", ".hidden"]
```

Две начальные точки не сохраняются обе: первая рассматривается как внешняя пунктуация, а вторая становится допустимым префиксом `.hidden`.

## 10. Специальные правила технического корпуса

Особенность реализации состоит не в заранее заданном списке всех возможных терминов, а в правилах, описывающих их структуру. Это позволяет обрабатывать ранее не встречавшиеся имена библиотек, версии, URL и идентификаторы.

### 10.1. `C++` и `C#`

Знаки `++` и `#` разрешаются как суффиксы уже прочитанного слова:

```text
C C++ C# CPP
    ↓
["c", "c++", "c#", "cpp"]
```

Плюс и решётка не считаются произвольными внутренними символами. Поэтому `A+B` разделяется на `a` и `b`, а `#hashtag` — на `hashtag`. Это уменьшает число случайных токенов из обычной пунктуации.

### 10.2. Версии, IP-адреса, домены и идентификаторы

Точка и подчёркивание между буквами или цифрами позволяют сохранять:

```text
v2.1.7
192.168.1.1
api.example.com
x86_64
```

Эти конструкции обрабатываются общими внутренними разделителями и не требуют отдельного списка известных версий или доменов.

### 10.3. Пространства имён C++

Последовательность `::` сохраняется между словами:

```text
std::vector
std::chrono::steady_clock
boost::asio
```

Один символ `:` не считается обычным внутренним разделителем. Два двоеточия добавляются только тогда, когда после них начинается следующая часть имени.

### 10.4. Параметры командной строки

Префикс `--` сохраняется, если он расположен в позиции, где может начинаться новый токен, и после него идёт слово:

```text
--output-dir
--dry-run
--threads=8
```

Знак `=` остаётся внутри option-токена, если после него сразу идёт слово или число. В конструкции `--output-dir=/tmp` после `=` стоит косая черта, поэтому получаются два полезных токена: `--output-dir` и `/tmp`.

Контекст начала нужен, чтобы два дефиса внутри обычной последовательности не превращали произвольный фрагмент в параметр. Префикс разрешён в начале текста или после пробела, открывающей скобки, запятой, точки с запятой, знака равенства и некоторых кавычек.

### 10.5. Абсолютные Unix-пути

Начальный `/` сохраняется в позиции начала токена:

```text
/usr/bin/python
/etc/nginx/nginx.conf
/home/user/my-file.txt
```

После распознанного префикса пути разрешаются следующие косые черты между сегментами. Внешняя пунктуация вокруг пути удаляется.

Обычное выражение `client/server` не считается абсолютным путём, потому что косая черта находится после уже прочитанного слова, а не в позиции начала. Оно превращается в два токена `client` и `server`. Это пример контекстного различия одного и того же символа.

### 10.6. Scoped-пакеты и email

Начальный `@` сохраняется для scoped-пакета, а последующие `@` и `/` разрешаются внутри уже распознанной конструкции:

```text
@angular/core
@types/node
@openai/sdk@17.2
```

Символ `@` между двумя частями обычного токена позволяет сохранить email:

```text
user@example.com
first.last@sub.example.org
```

### 10.7. URL

Если после прочитанной схемы обнаруживается `://`, токен переводится в режим URL. В нём дополнительно разрешаются `/`, `:`, `?`, `&`, `=`, `%`, `#` и `+`, если после разделителя продолжается содержимое:

```text
https://example.com/docs
http://localhost:8080/api/v1
https://example.com/search?q=C%2B%2B&lang=en#section
```

ASCII-буквы внутри URL также переводятся в нижний регистр. Поэтому последний пример сохраняется с `c%2b%2b`. Токенизатор здесь не выполняет полную канонизацию URL и не декодирует percent-encoding; его задача состоит только в сохранении адреса как одной поисковой единицы.

## 11. Удаление английского притяжательного окончания

После построения токена проверяется суффикс `'s`. Он удаляется до передачи слова лемматизатору:

```text
database's → database
model’s    → model
```

Типографский апостроф был заранее нормализован до обычного, поэтому оба варианта обрабатываются одним правилом.

Апострофы внутри сокращений и составных слов не удаляются:

```text
don't
we're
rock'n'roll
```

Удаляется только точный конечный суффикс `'s`. Это позволяет не добавлять притяжательные формы как отдельные ключи индекса и одновременно сохранять другие апострофные конструкции.

## 12. Ограничение максимальной длины

Параметр `maximum_token_length` берётся из секции `linguistics` файла `config.yaml`:

```yaml
linguistics:
  maximum_token_length: 100
```

Ограничение защищает память и индекс от аномально длинных последовательностей, которые могут появиться из минифицированного кода, повреждённой разметки или данных без разделителей. Если длина превышена, токен полностью отбрасывается, но разбор текста продолжается.

Сравнение выполняется после нормализации и измеряется в символах. Все сохранённые технические разделители также считаются символами:

```text
c++  → длина 3
.net → длина 4
```

Если предел равен трём, `c++` принимается, а `.net` отбрасывается. Unicode-токен `данные` принимается при пределе шесть и отбрасывается при пределе пять независимо от числа UTF-8-байтов.

## 13. Что возвращает токенизатор

Результат содержит три поля:

```cpp
struct TokenizationResult {
    TokenList tokens;
    uint64_t token_characters = 0;
    uint64_t elapsed_nanoseconds = 0;
};
```

`tokens` сохраняет исходный порядок и каждое вхождение. Токенизатор не удаляет дубликаты:

```text
one one one → ["one", "one", "one"]
```

`token_characters` является суммой длин всех принятых токенов после нормализации. В приведённом примере значение равно девяти. Отброшенные слишком длинные токены не входят в эту сумму.

`elapsed_nanoseconds` измеряет время всей токенизации, включая нормализацию UTF-8 и выделение токенов. Используется `std::chrono::steady_clock`, поэтому измерение не зависит от изменения системного времени.

В общем pipeline наносекунды переводятся в секунды и сохраняются в статистике документа. Суммарное количество символов вместе с числом токенов используется для расчёта средней длины токена.

## 14. Какие структуры STL используются

Токенизация является разрешённым преподавателем местом применения STL. В реализации используются:

- `std::string` для нормализованного текста и текущего токена;
- `std::vector<std::string>` для последовательности токенов;
- перемещение строки через `std::move`, чтобы не копировать готовый токен при добавлении;
- `reserve`, чтобы заранее уменьшить число перевыделений памяти.

Перед обработкой выходной вектор резервирует приблизительное число элементов:

```cpp
TokenList tokens;
tokens.reserve(text.size() / 6 + 1);
```

Для текущего токена также заранее резервируется небольшой буфер:

```cpp
std::string token;
token.reserve(32);
```

Хеш-таблицы и деревья здесь не используются. Они и не нужны, потому что токенизатор выполняет последовательный проход и сохраняет порядок вхождений, а не ищет токен по ключу.

## 15. Временная и пространственная сложность

Пусть `N` — число байтов входного текста. Нормализация последовательно читает каждый UTF-8-символ один раз. Этап выделения токенов последовательно просматривает нормализованную строку. Контекстные проверки смотрят только на небольшое фиксированное число соседних символов.

Поэтому ожидаемая временная сложность составляет:

```text
O(N)
```

Нормализованная строка и выходные токены требуют память, линейную относительно размера входа:

```text
O(N)
```

Алгоритм не строит регулярное выражение на весь документ, не выполняет возвраты по уже обработанному тексту и не хранит таблицу всех встреченных токенов. Это делает время обработки предсказуемым для больших документов.

## 16. Куда передаётся и сохраняется результат

После токенизации список сразу передаётся лемматизатору:

```cpp
TokenizationResult tokenization =
    tokenize_text(text, text_size, maximum_token_length);

LemmatizationResult lemmatization =
    lemmatize_tokens(&tokenization.tokens, dictionary);
```

Затем pipeline сортирует копию списка токенов и сворачивает одинаковые элементы в пары «токен — частота». Например:

```text
["c++", "query", "c++", "database"]
                    ↓
c++      → 2
database → 1
query    → 1
```

Для понимания токенизатора достаточно знать следующие места результата:

- частоты исходных токенов документа сохраняются в `document_terms.tokens`;
- `token_count`, `token_characters` и `tokenization_seconds` сохраняются в `processed_documents`;
- суммарные частоты корпуса сохраняются в `token_frequencies`;
- список токенов передаётся лемматизатору, а его частоты отдельно сохраняются в `document_terms.lemmas`.

Полная последовательность отдельных токенов после подсчёта частот не сохраняется, потому что для индексации нужны терм и число его вхождений в документ. До подсчёта частот порядок сохраняется и доступен лемматизатору.

## 17. Как токенизируются поисковые запросы

Булевый поиск и поиск TF-IDF вызывают тот же `linguistics_process`, который используется при обработке корпуса. Поэтому один и тот же термин имеет одинаковые границы в документе и в запросе.

Например, `std::vector` сохраняется одним токеном и при построении индекса, и при разборе пользовательского запроса. Если бы запрос разбирался простым разделением по двоеточиям, индекс содержал бы `std::vector`, а поиск запрашивал бы отдельные `std` и `vector`; совпадение не произошло бы.

Единая реализация особенно важна для `C++`, `.NET`, URL, пространств имён и других конструкций, правила которых отличаются от обычного деления по пунктуации.

## 18. Сильные стороны выбранных правил

Основными преимуществами реализации являются:

- линейный последовательный алгоритм без тяжёлых структур данных;
- безопасная проверка UTF-8 и продолжение работы после повреждённых байтов;
- измерение длины Unicode-токена в символах, а не в байтах;
- нормализация визуально эквивалентных тире, апострофов, пробелов и fullwidth ASCII;
- сохранение распространённых технических конструкций без фиксированного списка всех названий;
- сохранение каждого повторного вхождения для правильного подсчёта частот;
- единые правила для документов и запросов;
- отсутствие готовых хеш-таблиц и деревьев.

Особенно важно, что правила учитывают контекст. Косая черта сохраняется внутри абсолютного пути или URL, но разделяет обычное `client/server`. Два дефиса сохраняются в начале параметра командной строки, но не считаются универсальной частью любого слова. Это уменьшает количество ложных объединений.

## 19. Ограничения и потенциально неудачные токены

Любой токенизатор является компромиссом между сохранением составной конструкции и разделением соседних слов. Текущая реализация имеет известные ограничения.

Полное Unicode-приведение регистра не выполняется. Английские ASCII-буквы переводятся в нижний регистр, а регистр кириллицы и других алфавитов сохраняется. Поэтому `Поиск` и `поиск` могут стать разными токенами.

Токенизатор не является полноценным URL-парсером. Он сохраняет распространённые URL-разделители после `://`, но не проверяет корректность схемы, домена или percent-encoding. Это осознанно: задача компонента — выделить поисковую единицу, а не проверить сетевой адрес.

Знаки обычного числа не сохраняются. В строке `-273.15 +7 99% $100` будут токены `273.15`, `7`, `99`, `100`. Для общего технического поиска знак числа и денежное обозначение сейчас считаются внешней пунктуацией.

Начальный `#` не сохраняется как часть hashtag, поэтому `#security` становится `security`. Один `#` поддерживается только как суффикс формы наподобие `C#`.

Дефис между словами сохраняется всегда, если по обе стороны находятся допустимые символы. Это хорошо для `state-of-the-art` и `sha-256`, но некоторые авторские сочетания могут быть объединены сильнее, чем требуется конкретному запросу.

Начальная точка сохраняется перед словом. Поэтому `.NET` и `.config` обрабатываются правильно, но любая аналогичная конструкция также будет считаться токеном с точкой, даже если в конкретном контексте точка была обычной пунктуацией.

Очень длинный осмысленный идентификатор длиннее `maximum_token_length` будет полностью отброшен. Ограничение защищает систему от аномальных данных, но означает потерю редких длинных хэшей, сгенерированных имён или URL.

Эти ограничения следует объяснять не как случайные ошибки, а как принятые правила. Для корпуса Wikipedia, arXiv и Microsoft Learn важнее сохранить названия технологий, кода, версий и адресов, чем идеально разобрать все языки и форматы данных.

## 20. Как собрать и проверить токенизатор

Из корня проекта выполняется сборка:

```bash
cmake -S . -B .build -DCMAKE_BUILD_TYPE=Release
cmake --build .build --parallel
```

Отдельный набор Google Test запускается напрямую:

```bash
./.build/tokenizer_unit_tests
```

Через CTest запускаются только тесты токенизатора:

```bash
ctest --test-dir .build -R 'unit\.tokenizer\.' --output-on-failure
```

В наборе находится 64 теста. Они проверяют:

- обычные слова, регистр, пунктуацию и повторения;
- `C++`, `C#`, `.NET`, `node.js`, `sha-256` и составные идентификаторы;
- разные Unicode-пробелы, тире, апострофы и fullwidth ASCII;
- точную границу максимальной длины;
- длину Unicode в code points;
- URL, email, пространства имён C++, параметры командной строки, Unix-пути и scoped-пакеты;
- числа, версии, IP-адреса и домены;
- неанглийские слова;
- корректные и повреждённые последовательности UTF-8;
- явный размер входного буфера, встроенный нулевой байт и пустой указатель;
- сохранение порядка, всех повторений и суммарной длины;
- большой вход с двумя тысячами повторяющихся технических токенов.

Чтобы увидеть результат на реальном корпусе, запускается общий pipeline:

```bash
./.build/linguistics config.yaml
```

Для защиты удобнее сначала показать несколько тестов с понятными входами и ожидаемыми токенами, а затем открыть частоты реального документа в `document_terms.tokens` и общую производительность в `results/statistics.json`.

## 21. Что показать преподавателю в коде

Разбор лучше вести в порядке фактического выполнения.

Сначала следует открыть `tokenizer.hpp` и показать небольшой публичный интерфейс. Здесь нужно объяснить, что функция принимает буфер с явным размером и возвращает последовательность токенов вместе с метриками.

Затем в `tokenizer.cpp` следует показать `decode_utf8`. Основная мысль состоит в том, что программа самостоятельно получает Unicode code point, проверяет корректность последовательности и умеет продолжить работу после повреждённого байта.

После этого нужно показать `normalize_input`, где разные пробелы, апострофы, тире и полноширинные ASCII-символы приводятся к общему виду.

Далее следует перейти к `tokenize_normalized`. В этой функции наиболее важны четыре части:

1. определение допустимого начала токена;
2. добавление букв, цифр и обычных внутренних разделителей;
3. контекстные правила для URL, `::`, `--`, `/`, `@`, `C++` и `C#`;
4. удаление `'s` и проверка максимальной длины.

В конце нужно открыть `pipeline.cpp` и показать, что список токенов сначала передаётся лемматизатору, а затем отдельно превращается в частоты. Это подтверждает, что токенизатор не подменяет лемматизацию и не удаляет повторения раньше времени.

## 22. Краткое объяснение для защиты

Токенизатор можно объяснить преподавателю следующим образом:

> Токенизация преобразует очищенный текст в последовательность поисковых термов. Моя реализация написана на C++ и выполняет два прохода. Сначала она безопасно декодирует UTF-8 и нормализует пробелы, типографские апострофы, разные тире и полноширинные ASCII-символы. Затем строка просматривается слева направо, выделяются буквы и цифры, а внутренние разделители сохраняются только в допустимом контексте. За счёт отдельных правил `C++`, `C#`, `.NET`, `node.js`, `std::vector`, URL, email, Unix-пути, параметры командной строки и npm-пакеты остаются целыми токенами. ASCII приводится к нижнему регистру, повторения и порядок сохраняются. Слишком длинные токены отбрасываются, причём длина считается в Unicode-символах. Алгоритм линейный, использует строки и векторы, но не использует хеш-таблицы или деревья. После токенизации список передаётся лемматизатору, а частоты исходных токенов сохраняются отдельно.

Главную последовательность удобно запомнить так:

```text
UTF-8
→ нормализация символов
→ поиск границ
→ технические контекстные правила
→ удаление притяжательного окончания
→ проверка длины
→ список токенов
→ лемматизация и подсчёт частот
```

Основная особенность этой реализации — сохранение смысла технических конструкций без превращения любой пунктуации в часть токена.
