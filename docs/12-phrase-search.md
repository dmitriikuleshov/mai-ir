# Цитатный поиск: координатный индекс

Отдельный числовой пример с четырьмя документами, содержимым бинарных файлов и
пошаговым запросом находится в
[`examples/05-phrase-search.md`](examples/05-phrase-search.md).

## 1. Задача

Булев индекс отвечает на вопрос, встречается ли терм в документе, но не хранит
порядок слов. Поэтому запрос `"stanford university"` нельзя корректно выполнить
только по двум обычным posting lists: документ со словами `stanford` и
`university` в разных частях текста дал бы ложное совпадение.

Цитатный поиск возвращает документ только тогда, когда нормализованные термы
запроса находятся рядом и в том же порядке. Для цитаты из трёх термов нужны
координаты:

```text
term0: p
term1: p + 1
term2: p + 2
```

## 2. Почему создан отдельный индекс

Общий булев и TF-IDF-индекс хранит пары `(docID, term_frequency)`. Частота не
позволяет восстановить позиции отдельных вхождений, поэтому координаты нельзя
добавить на этапе поиска. Они вычисляются заранее по полю `text` коллекции
`processed_documents` и сохраняются в `results/positional_index`.

Координатный индекс использует ту же нумерацию документов, что и булев индекс.
Построитель читает принятые документы по возрастанию MongoDB ObjectId и для
каждого документа проверяет соответствующий ObjectId из
`results/boolean_index/documents.bin`. Несовпадение останавливает построение и
требует перестроить индексы. Благодаря этой проверке один `docID` всегда
обозначает один и тот же документ.

## 3. Построение координат

Текст каждого документа проходит тот же токенизатор и лемматизатор, что
основной корпус и поисковый запрос. В отличие от подсчёта частот, порядок лемм
не сортируется:

```text
исходный текст:
Distributed databases improve database availability

последовательность лемм:
[distributed, database, improve, database, availability]

координаты:
distributed -> [0]
database    -> [1, 3]
improve     -> [2]
availability-> [4]
```

Одна временная запись имеет вид:

```text
(term, docID, position)
```

Все координаты корпуса нельзя держать в памяти. Параметр
`block_occurrences` ограничивает буфер 500 тысячами вхождений. Заполненный
буфер сортируется по терму, `docID` и позиции, после чего записывается во
временный файл. Если файлов больше 128, выполняется промежуточное многоходовое
слияние. Поэтому объём оперативной памяти не растёт пропорционально корпусу.

## 4. Итоговая структура

```text
coordinate_lexicon.bin - заголовок, смещения и размеры списков;
coordinate_terms.bin   - строки термов в UTF-8;
coordinates.bin        - docID и позиции в Variable Byte;
documents.bin          - общее соответствие docID и MongoDB ObjectId.
```

Логически posting list выглядит так:

```text
database ->
    doc 0: [1, 3]
    doc 5: [8]
    doc 9: [2, 20, 41]
```

В `coordinates.bin` номера документов и координаты хранятся разностями:

```text
docID-gap, position_count, first_position, position-gap, ...
```

Все числа кодируются Variable Byte. Точный формат записан в
`BINARY_FORMAT.md`.

## 5. Алгоритм поиска цитаты

Пусть введена цитата:

```text
"distributed database system"
```

После токенизации и лемматизации получаются три упорядоченных терма. Для них
загружаются координатные posting lists. Сначала пересекаются `docID`, поэтому
координаты сравниваются только в документах, содержащих оба терма.

Для двух списков позиций используются два указателя. Позиция правого терма
подходит, если она равна позиции уже совпавшей левой последовательности плюс
один:

```text
left_end + 1 == right_position
```

После первого пересечения сохраняются позиции второго терма, завершающие
двухсловную последовательность. Затем они пересекаются с позициями третьего
терма. Такой проход повторяется для всех слов цитаты.

Пример:

```text
distributed: [4, 20]
database:    [5, 12, 21]
system:      [6, 22]

distributed + database -> [5, 21]
[5, 21] + system        -> [6, 22]
начала полной цитаты     -> [4, 20]
```

Алгоритм поддерживает несколько и перекрывающиеся вхождения. Для текста
`cloud cloud cloud cloud` запрос `"cloud cloud cloud"` найдётся с начальных
позиций 0 и 1.

## 6. Сложность

Двоичный поиск терма в лексиконе требует `O(log M)` сравнений, где `M` - число
уникальных термов. Декодирование зависит только от posting lists термов
запроса, а не от полного корпуса. Позиционное пересечение двух отсортированных
списков линейно по сумме их длин. Для цитаты из `k` термов выполняется `k - 1`
таких пересечений.

## 7. Запуск

Сначала построить обычный индекс:

```bash
./.build/boolean_index configs/boolean_index.yaml
```

Затем построить координатный индекс:

```bash
./.build/positional_index configs/positional_index.yaml
```

Запустить консольный поиск:

```bash
./.build/phrase_search configs/search.yaml
```

Пример ввода:

```text
"distributed database"
```

Каждая строка стандартного ввода считается отдельной цитатой. Кавычки можно не
указывать. Для пакетной проверки:

```bash
printf '%s\n' '"machine learning"' '"cloud security"' \
  | ./.build/phrase_search configs/search.yaml
```

## 8. Тестирование

```bash
ctest --test-dir .build \
  -R 'unit\.(positional_index|phrase_search)\.' \
  --output-on-failure
```

Тесты проверяют бинарный формат, сортировку и слияние блоков, точную
последовательность слов, отсутствие совпадения через лишнее слово, порядок
термов, трёхсловную цитату, несколько вхождений, повторяющиеся термы,
неизвестный терм и полный поиск по временному бинарному индексу. MongoDB и
состояние настоящего корпуса для модульных тестов не требуются.

## 10. Почему выбран координатный индекс, а не индекс биграмм

В материалах курса рассматриваются два основных способа выполнять цитатные
запросы: индекс биграмм и координатный индекс.

Биграммный индекс добавляет в словарь каждую соседнюю пару слов. Например, для
текста `distributed database system` пришлось бы создать дополнительные термы
`distributed database` и `database system`. Двухсловная цитата находится
быстро, но число ключей в словаре заметно растёт. Для длинной цитаты всё равно
нужно пересечь несколько биграмм и затем проверить, что они относятся к одной
непрерывной последовательности.

Координатный индекс не создаёт новые текстовые ключи. Для каждого обычного
терма он хранит документы и позиции вхождений:

```text
distributed -> doc 7: [12, 80]
database    -> doc 7: [13, 41, 81]
system      -> doc 7: [14, 82]
```

Такое представление поддерживает цитаты произвольной длины, несколько
вхождений одной цитаты и в дальнейшем может быть расширено до поиска на
заданном расстоянии. Поэтому для проекта выбран координатный индекс.

## 11. Полный путь данных

Цитатный поиск состоит из двух разных этапов: предварительного построения
индекса и обработки пользовательского запроса.

Построение:

```text
MongoDB: processed_documents.text
              │
              ▼
     токенизация документа
              │
              ▼
      лемматизация с сохранением порядка
              │
              ▼
       (term, docID, position)
              │
              ▼
     внешняя сортировка блоками
              │
              ▼
 coordinate_lexicon.bin
 coordinate_terms.bin
 coordinates.bin
```

Поиск:

```text
строка цитаты из stdin
          │
          ▼
токенизация и лемматизация
          │
          ▼
упорядоченный список лемм
          │
          ▼
двоичный поиск каждой леммы в coordinate_lexicon.bin
          │
          ▼
декодирование только нужных диапазонов coordinates.bin
          │
          ▼
пересечение docID и соседних координат
          │
          ▼
docID найденных документов
          │
          ▼
documents.bin: docID -> ObjectId
          │
          ▼
MongoDB: title, source, url
```

Полные тексты MongoDB при выполнении запроса повторно не читаются. Они нужны
только во время построения координатного индекса. Во время поиска MongoDB
используется после нахождения результатов, чтобы вывести метаданные документов.

## 12. Как сохраняется порядок лемм

Обычный `linguistics_process` в конце сортирует термы и превращает их в пары
`(терм, частота)`. Такое представление подходит для булева индекса и TF-IDF,
но уже не содержит порядка слов.

Для координатного индекса добавлена отдельная функция:

```cpp
TokenList linguistics_normalize_sequence(
    const char *text,
    size_t text_size,
    size_t maximum_token_length,
    const LemmaDictionary *dictionary
) {
    TokenizationResult tokenization =
        tokenize_text(text, text_size, maximum_token_length);
    LemmatizationResult lemmatization =
        lemmatize_tokens(&tokenization.tokens, dictionary);
    return std::move(lemmatization.lemmas);
}
```

Здесь нет сортировки и подсчёта частот. Если терм встретился три раза, все три
элемента остаются в последовательности. Номер элемента и становится его
координатой:

```cpp
for (size_t position = 0; position < lemmas.size(); ++position) {
    position_buffer_add(
        &buffer,
        lemmas[position],
        document_id,
        static_cast<uint32_t>(position)
    );
}
```

Координаты отсчитываются от нуля после токенизации. HTML-теги к этому моменту
уже удалены лингвистическим pipeline. Знаки пунктуации сами по себе координату
не занимают, а поддерживаемые технические конструкции, например `C++` или
`node.js`, остаются одним токеном и занимают одну позицию.

## 13. Как обеспечивается одинаковый `docID`

Координатный индекс не назначает независимую нумерацию документов. Он должен
использовать те же `docID`, по которым работают булев поиск и TF-IDF. Для этого
выполняются следующие действия:

1. Открывается `results/boolean_index/documents.bin`.
2. Из MongoDB выбираются только документы с `accepted = true`.
3. Документы сортируются по `_id` по возрастанию.
4. Для каждого очередного документа читается следующий ObjectId из
   `documents.bin`.
5. Два ObjectId сравниваются побайтово.

Ключевая проверка выглядит так:

```cpp
uint8_t expected_oid[12];
if (std::fread(expected_oid, 1, sizeof(expected_oid), documents) !=
        sizeof(expected_oid) ||
    std::memcmp(expected_oid, bson_iter_oid(&id_iterator)->bytes,
                sizeof(expected_oid)) != 0) {
    fail("documents.bin не соответствует processed_documents; "
         "перестройте индексы");
}
```

Если после построения булева индекса в корпус добавили или удалили документ,
координатный индекс не будет молча использовать неправильные номера. Построение
завершится с понятной ошибкой. Правильный порядок восстановления:

```bash
./.build/linguistics configs/linguistics.yaml
./.build/boolean_index configs/boolean_index.yaml
./.build/positional_index configs/positional_index.yaml
```

## 14. Внешняя сортировка координат

Текущий корпус содержит сотни миллионов позиций, поэтому нельзя собрать все
структуры вида `(term, docID, position)` в одном `std::vector`. Индексатор
использует ограниченный рабочий буфер.

При достижении `block_occurrences` выполняется:

1. сортировка по `term`;
2. для одинакового терма сортировка по `docID`;
3. для одинакового документа сортировка по `position`;
4. удаление точных дубликатов;
5. запись блока на диск;
6. очистка оперативного буфера.

Порядок записей в блоке:

```text
cloud,    doc 0, position 5
cloud,    doc 0, position 20
cloud,    doc 3, position 8
database, doc 0, position 6
database, doc 9, position 2
```

Если число блоков превышает `MERGE_FAN_IN = 128`, они объединяются группами.
После промежуточных проходов остаётся не более 128 файлов, которые можно
безопасно открыть одновременно для финального `k-way merge`.

Минимальная куча содержит только номер каждого активного читателя. В памяти
находится по одной текущей записи каждого блока, а не содержимое всех файлов.
После извлечения минимальной записи продвигается только один читатель, затем
свойство кучи восстанавливается. Поэтому финальный поток снова отсортирован по
терму, документу и позиции.

## 15. Точный смысл файлов координатного индекса

### `coordinate_lexicon.bin`

Это оглавление индекса. В заголовке находятся общие размеры:

```text
document_count - число документов;
term_count     - число уникальных термов;
posting_count  - число пар «терм - документ»;
position_count - число отдельных вхождений термов.
```

Для каждого терма хранится фиксированная запись:

```cpp
struct LexiconEntry {
    uint64_t term_offset;
    uint64_t postings_offset;
    uint32_t term_length;
    uint32_t postings_count;
    uint64_t position_count;
};
```

`term_offset` и `term_length` задают строку в `coordinate_terms.bin`.
`postings_offset` задаёт начало координатного списка в `coordinates.bin`.
`postings_count` сообщает, сколько документов нужно декодировать, а
`position_count` позволяет проверить общее число прочитанных координат.

### `coordinate_terms.bin`

Файл содержит UTF-8-байты термов без разделителей. Например:

```text
clouddatabasesecurity...
```

Границы строки известны из записи лексикона. Такое разделение позволяет
оставить записи лексикона фиксированного размера и выполнять по ним двоичный
поиск.

### `coordinates.bin`

Это основные данные координатного индекса. Для одного терма записывается:

```text
VB(docID-gap)
VB(position_count)
VB(first_position)
VB(position-gap)
VB(position-gap)
...
```

Например, терм встречается:

```text
doc 5: positions [3, 10, 11]
doc 9: positions [2, 20]
```

В поток попадут значения:

```text
doc 5:  docID-gap=5, position_count=3, positions=[3, 7, 1]
doc 9:  docID-gap=4, position_count=2, positions=[2, 18]
```

При чтении накоплением восстанавливаются абсолютные значения. Для второго
документа `5 + 4 = 9`, а позиции первого документа восстанавливаются как
`3`, `3 + 7 = 10`, `10 + 1 = 11`.

### `documents.bin`

Файл физически находится в `results/boolean_index`, но используется также
цитатным поиском. Позиция ObjectId в файле определяется напрямую:

```text
offset = 16 + docID * 12
```

Поэтому отдельная таблица или запрос MongoDB для преобразования каждого
`docID` не требуются.

## 16. Декодирование координат

После нахождения терма поисковая программа переходит к `postings_offset` и
читает ровно `postings_count` документов. Для каждого документа сначала
восстанавливается `docID`, затем читается указанное число позиций:

```cpp
variable_byte_read(coordinates, &document_gap);
variable_byte_read(coordinates, &position_count);
document_id += document_gap;

for (uint32_t item = 0; item < position_count; ++item) {
    uint32_t gap = 0;
    variable_byte_read(coordinates, &gap);
    position += gap;
    posting.positions.push_back(position);
}
```

Reader дополнительно проверяет:

- ненулевое число позиций в posting;
- строго возрастающие `docID`;
- положительные gap после первого документа и первой позиции;
- отсутствие переполнения `uint32_t`;
- попадание `docID` в диапазон корпуса;
- совпадение прочитанного количества позиций с `position_count` лексикона.

Повреждённый или несовместимый индекс не выдаётся за корректный пустой
результат: поиск возвращает отдельное сообщение об ошибке чтения.

## 17. Позиционное пересечение по шагам

Пусть пользователь ищет:

```text
"cloud database security"
```

Для одного документа индекс вернул:

```text
cloud:    [2, 10, 30]
database: [3, 20, 31]
security: [4, 21, 32]
```

Сначала сравниваются `cloud` и `database`. Подходят только позиции правого
терма, равные позиции левого плюс один:

```text
cloud 2  + 1 = database 3  -> сохранить 3
cloud 10 + 1 = 11          -> совпадения нет
cloud 30 + 1 = database 31 -> сохранить 31
```

Промежуточный результат `[3, 31]` означает: в этих позициях заканчивается
последовательность `cloud database`.

Затем этот список пересекается с `security`:

```text
3  + 1 = security 4  -> сохранить 4
31 + 1 = security 32 -> сохранить 32
```

Получены конечные позиции `[4, 32]`. Длина цитаты равна трём, поэтому для
вывода начальных позиций вычитается `3 - 1 = 2`:

```text
[4, 32] - 2 = [2, 30]
```

Следовательно, полная цитата начинается в позициях 2 и 30. Слова на позициях
20 и 21 не создают ложного совпадения, потому что перед `database` на позиции
20 нет `cloud` на позиции 19.

## 18. Как устроены два уровня пересечения

Сначала сравниваются списки документов. Они отсортированы, поэтому используются
два указателя:

```cpp
if (left_doc < right_doc) {
    ++left;
} else if (right_doc < left_doc) {
    ++right;
} else {
    // Только здесь сравниваются позиции одного документа.
}
```

Если `docID` совпал, аналогичным линейным проходом сравниваются координаты:

```cpp
const uint32_t expected = left_position + 1;

if (right_position == expected) {
    result.push_back(right_position);
} else if (right_position < expected) {
    ++right;
} else {
    ++left;
}
```

Это важнее полного перебора всех пар позиций. Для списков длины `a` и `b`
линейный алгоритм выполняет `O(a + b)` шагов, тогда как вложенные циклы могли
бы потребовать `O(a * b)` сравнений для частых термов.

## 19. Нормализация цитаты

Запрос проходит ту же функцию `linguistics_normalize_sequence`, что и тексты
при построении координатного индекса. Поэтому словоформы приводятся к общей
лемме:

```text
"distributed databases" -> [distributed, database]
```

Внешние двойные кавычки удаляются до лингвистической обработки. Эти две строки
эквивалентны:

```text
"distributed database"
distributed database
```

Каждая строка стандартного ввода считается одной цельной цитатой. Операторы
`AND`, `OR` и `NOT` здесь не имеют специального смысла: они относятся к
отдельной утилите булева поиска.

Если хотя бы одного терма цитаты нет в словаре координатного индекса, результат
сразу становится пустым. Документы без термов запроса не рассматриваются.

## 20. Повторяющиеся и перекрывающиеся вхождения

Повтор одного терма не удаляется из запроса. Для текста:

```text
cloud cloud cloud cloud
```

posting одного терма равен:

```text
cloud -> [0, 1, 2, 3]
```

Для запроса `"cloud cloud cloud"` один и тот же posting list загружается для
трёх позиций цитаты. После первого пересечения остаются конечные позиции
`[1, 2, 3]`, после второго - `[2, 3]`. Начальные позиции равны `[0, 1]`.

Это два перекрывающихся вхождения:

```text
[cloud cloud cloud] cloud
 cloud [cloud cloud cloud]
```

## 21. Параметры конфигурации

Построитель использует `configs/positional_index.yaml`:

| Параметр | Значение и назначение |
|---|---|
| `db.uri` | Адрес MongoDB. |
| `db.database` | База с обработанным корпусом. |
| `db.processed_collection` | Коллекция с извлечённым полем `text`. |
| `linguistics.maximum_token_length` | Максимальная длина токена в Unicode-символах. |
| `linguistics.lemma_dictionary` | Исключения WordNet. |
| `linguistics.lemma_vocabulary` | Словарь допустимых английских лемм. |
| `linguistics.lemma_overrides` | Дополнительные правила технического корпуса. |
| `positional_index.output_directory` | Каталог трёх файлов координатного индекса. |
| `positional_index.boolean_index_directory` | Каталог общего `documents.bin`. |
| `positional_index.block_occurrences` | Максимум координат в одном рабочем блоке. |
| `positional_index.progress_every_documents` | Период сообщения о прогрессе. |

Поисковая утилита читает `configs/search.yaml`. В секции
`positional_index.output_directory` задаётся готовый индекс, а
`phrase_search.result_limit` ограничивает только число показанных документов.
Полное число найденных документов и вхождений сохраняется и выводится до
применения этого ограничения.

## 22. Что показывает консольная выдача

Пример заголовка ответа:

```text
Цитата: "distributed database"
Найдено документов: 274 | вхождений: 389 | поиск: 4.460 мс
```

`Найдено документов` - число разных `docID`, содержащих цитату. `Вхождений` -
суммарное число начальных позиций во всех найденных документах. Один документ
может содержать цитату несколько раз, поэтому второе число может быть больше
первого.

Для каждого показанного документа выводятся:

- заголовок;
- источник;
- внутренний `docID`;
- MongoDB ObjectId;
- URL;
- начальные позиции цитаты, отсчитываемые от нуля.

Чтобы строка не становилась чрезмерно длинной, показываются первые десять
позиций документа и общее число вхождений, если их больше десяти.

## 23. План демонстрации преподавателю

Сначала показать, что MongoDB работает и индекс уже построен:

```bash
docker compose up -d
ls -lh results/positional_index
```

Объяснить назначение трёх файлов и общего `documents.bin`, затем запустить
поиск:

```bash
./.build/phrase_search configs/search.yaml
```

Последовательно ввести:

```text
"distributed database"
"database distributed"
"cloud security"
```

Первый запрос показывает обычное точное совпадение. Второй демонстрирует, что
порядок термов важен. Третий показывает большое число реальных результатов и
несколько позиций внутри одного документа.

После этого запустить отдельные тесты:

```bash
ctest --test-dir .build \
  -R 'unit\.(positional_index|phrase_search)\.' \
  --output-on-failure
```

Если преподаватель попросит перестроить индекс, используется команда:

```bash
./.build/positional_index configs/positional_index.yaml
```

На полном корпусе эта операция существенно тяжелее поиска, потому что один раз
обрабатывает все документы и все позиции. Быстрые запросы после построения и
являются причиной предварительной индексации.

## 24. Что сказать о реализации кратко

> Для цитатного поиска обычного posting list с `docID` недостаточно, потому что
> он не хранит порядок слов. Поэтому я построил отдельный координатный индекс,
> в котором для каждого терма и документа сохраняется отсортированный список
> позиций. Документы и запрос проходят одинаковые токенизацию и лемматизацию.
> Координаты большого корпуса сортируются внешним блоковым алгоритмом, поэтому
> весь корпус не загружается в память. `docID` и позиции хранятся разностями и
> сжимаются Variable Byte. Во время запроса термы находятся двоичным поиском,
> после чего сначала линейно пересекаются списки документов, а затем списки
> координат с условием `right_position = left_position + 1`. Для длинной цитаты
> промежуточный список последовательно пересекается с каждым следующим термом.
> Результат содержит документы и начальные позиции всех точных вхождений, а
> `documents.bin` переводит внутренний `docID` обратно в MongoDB ObjectId.

## 25. Ограничения текущего решения

Поиск проверяет точную последовательность нормализованных термов. Он не ищет
синонимы, не допускает перестановку слов и не поддерживает запрос вида
`employment /4 place`. Последний вариант можно добавить поверх уже имеющегося
координатного индекса: вместо условия разности ровно в единицу проверять
допустимый диапазон расстояния.

Пунктуация не участвует в координатах, потому что индекс строится после
токенизации. Поэтому цитата означает последовательность индексируемых термов, а
не побайтовое совпадение исходной HTML-строки. Это стандартное поведение
лингвистического полнотекстового поиска.

Координатный индекс больше обычного булева, поскольку хранит каждое вхождение,
а не только одну пару на документ. Для уменьшения размера применяются
`docID-gap`, `position-gap` и Variable Byte; на текущем корпусе это дало 61,1%
экономии относительно выбранного несжатого представления `docID` и координат.
