# Сквозной пример сжатия posting list терма database

Рассмотрим только один терм `database`. Пусть он встретился в четырёх документах:

```text
database -> [0, 5, 10, 15]
```

Во всех четырёх документах терм встретился один раз:

```text
term_frequency -> [1, 1, 1, 1]
```

Ниже один и тот же posting list последовательно проходит все этапы сжатия и
обратного декодирования.

## 1. Данные до сжатия

Для каждого документа нужно хранить два числа:

1. `docID` документа.
2. `term_frequency` - частоту терма `database` в документе.

Логически posting list состоит из четырёх пар:

```text
(docID, term_frequency)

(0,  1)
(5,  1)
(10, 1)
(15, 1)
```

Без сжатия каждое число хранится как `uint32_t` размером 4 байта. Одна пара
занимает 8 байт, а весь posting list:

```text
uncompressed_size = 4 пары × 2 числа × 4 байта = 32 байта
```

## 2. Преобразование `docID` в `docID-gap`

Posting list отсортирован по возрастанию `docID`. Поэтому вместо абсолютных
идентификаторов можно хранить расстояния между соседними документами:

```text
gap[0] = docID[0]
gap[i] = docID[i] - docID[i - 1]
```

Для терма `database` вычисление выглядит так:

```text
gap[0] = 0
gap[1] = 5  - 0  = 5
gap[2] = 10 - 5  = 5
gap[3] = 15 - 10 = 5
```

В результате:

```text
docID:     [0, 5, 10, 15]
docID-gap: [0, 5, 5, 5]
```

Список, который нужно записать в `postings.bin`, теперь состоит из пар:

```text
(docID-gap, term_frequency)

(0, 1)
(5, 1)
(5, 1)
(5, 1)
```

## 3. Как устроен один байт Variable Byte

В каждом байте семь младших битов хранят данные, а старший бит `END` показывает,
закончено ли текущее число:

```text
bit 7     bits 6..0
+-----+-----------------+
| END | 7 битов числа  |
+-----+-----------------+
```

- `END = 1` означает, что это последний байт числа.
- `END = 0` означает, что число продолжается в следующем байте.

Числа от 0 до 127 помещаются в семь битов и занимают один байт. Все значения
из posting list `database` попадают в этот диапазон.

| Число | 7 битов данных | `END` | Двоичный байт | Hex |
|---:|---|---:|---|---|
| 0 | `0000000` | 1 | `10000000` | `0x80` |
| 1 | `0000001` | 1 | `10000001` | `0x81` |
| 5 | `0000101` | 1 | `10000101` | `0x85` |

## 4. Точные байты posting list

Каждая пара `(docID-gap, term_frequency)` кодируется двумя последовательными
Variable Byte-числами:

```text
(0, 1) -> 80 81
(5, 1) -> 85 81
(5, 1) -> 85 81
(5, 1) -> 85 81
```

Итоговое содержимое posting list терма `database` в `postings.bin`:

```text
80 81 | 85 81 | 85 81 | 85 81
```

Вертикальные черты здесь добавлены только для объяснения. В бинарном файле
разделителей нет:

```text
80 81 85 81 85 81 85 81
```

Каждое из восьми чисел заняло один байт, поэтому размер сжатого списка равен
8 байтам.

## 5. Как `lexicon.bin` задаёт границы списка

В упрощённом примере будем считать, что posting list `database` начинается с
нулевого байта `postings.bin`. Тогда его `LexiconEntry` содержит:

```text
postings_offset = 0
postings_count  = 4
```

`postings_offset` указывает, с какого байта начинать чтение. `postings_count`
сообщает, что нужно декодировать ровно четыре пары. Поэтому отдельный заголовок
или разделитель внутри `postings.bin` не требуется.

В настоящем индексе `postings_offset` зависит от размеров списков предыдущих
термов, но принцип чтения остаётся тем же.

## 6. Обратное декодирование

Поиск переходит к `postings_offset` и читает восемь байтов:

```text
80 81 85 81 85 81 85 81
```

У каждого байта старший бит равен 1, поэтому каждый байт является отдельным
Variable Byte-числом. Старший бит удаляется маской `0x7F`:

```text
0x80 & 0x7F = 0
0x81 & 0x7F = 1
0x85 & 0x7F = 5
0x81 & 0x7F = 1
0x85 & 0x7F = 5
0x81 & 0x7F = 1
0x85 & 0x7F = 5
0x81 & 0x7F = 1
```

После группировки снова получаются исходные пары:

```text
(docID-gap, term_frequency)

(0, 1)
(5, 1)
(5, 1)
(5, 1)
```

Абсолютные `docID` восстанавливаются накоплением суммы:

```text
docID[0] = 0
docID[1] = 0  + 5 = 5
docID[2] = 5  + 5 = 10
docID[3] = 10 + 5 = 15
```

Результат декодирования:

```text
docID:          [0, 5, 10, 15]
term_frequency: [1, 1, 1, 1]
```

Булев поиск использует восстановленные `docID`. Значения `term_frequency`
читаются из того же файла, но требуются TF-IDF-поиску.

## 7. Если `docID-gap` больше 127

Основной список `database` содержит только однобайтовые числа. Рассмотрим, что
произойдёт, если следующий документ с термом `database` имеет `docID = 315`.
Предыдущий документ имел `docID = 15`, поэтому:

```text
docID-gap = 315 - 15 = 300
```

Число 300 раскладывается по основанию 128:

```text
300 = 2 × 128 + 44
```

Получаются две семибитные группы:

```text
2  -> 0000010
44 -> 0101100
```

Первая группа не завершает число и получает `END = 0`. Вторая группа
последняя и получает `END = 1`:

```text
0 0000010 = 00000010 = 0x02
1 0101100 = 10101100 = 0xAC

300 -> 02 AC
```

Если `term_frequency = 1`, вся новая пара будет занимать три байта:

```text
(docID-gap = 300, term_frequency = 1) -> 02 AC 81
```

При декодировании выполняется:

```text
result = 2
result = 2 × 128 + 44 = 300
docID  = 15 + 300 = 315
```

Старший бит не входит в значение числа. Он только сообщает, нужно ли читать
следующий байт.

## 8. Расчёт процента сжатия

В исходном posting list `database` находятся четыре пары.

Размер без сжатия:

```text
uncompressed_size = 4 × 2 × sizeof(uint32_t)
                  = 4 × 2 × 4
                  = 32 байта
```

Размер после gap-кодирования и Variable Byte:

```text
compressed_size = 8 байт
```

Экономия вычисляется по формуле, которую использует индексатор:

```text
saved_percent = (1 - compressed_size / uncompressed_size) × 100%
              = (1 - 8 / 32) × 100%
              = 75%
```

Таким образом, posting list терма `database` занимает 8 байт вместо 32.
Экономия составляет 24 байта, или 75%.

## 9. Связь с кодом программы

При построении индекса для каждого документа выполняются действия:

```text
document_gap = current_docID - previous_docID
VariableByte(document_gap)
VariableByte(term_frequency)
```

При булевом поиске выполняются обратные действия:

```text
document_gap   = VariableByteDecode()
term_frequency = VariableByteDecode()
current_docID += document_gap
```

Начальная позиция берётся из `LexiconEntry.postings_offset`, а число пар - из
`LexiconEntry.postings_count`.

## 10. Краткое объяснение для защиты

Для терма `database` исходный posting list равен `[0, 5, 10, 15]`. Сначала
абсолютные `docID` заменяются разностями `[0, 5, 5, 5]`. Затем каждая разность
и каждая частота кодируются Variable Byte. Значения 0, 1 и 5 меньше 128,
поэтому каждое занимает один байт. В результате четыре пары занимают 8 байт
вместо 32, что даёт экономию 75%. При чтении числа декодируются, а абсолютные
`docID` восстанавливаются последовательным сложением разностей.
