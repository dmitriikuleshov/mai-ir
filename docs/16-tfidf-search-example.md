# Сквозной пример работы TF-IDF-поиска

В этом примере показан полный путь запроса: от данных в `document_terms` до
ранжированной выдачи. В проекте используется схема SMART `lnc.ltc`:

```text
документ: lnc - логарифмический TF, без IDF, L2-нормализация;
запрос:   ltc - логарифмический TF, IDF, L2-нормализация.
```

Итоговый `score` является скалярным произведением нормализованных векторов
документа и запроса, то есть их косинусной близостью.

## 1. Исходные документы

Пусть после лингвистической обработки в коллекции MongoDB
`mai_ir.document_terms` находятся три документа. Для краткости оставим только
поля `lemmas`:

```javascript
// Первый документ
{
  _id: ObjectId("671a00000000000000000001"),
  lemmas: [
    ["cloud", 2],
    ["database", 1]
  ]
}

// Второй документ
{
  _id: ObjectId("671a00000000000000000002"),
  lemmas: [
    ["cloud", 1],
    ["security", 3]
  ]
}

// Третий документ
{
  _id: ObjectId("671a00000000000000000003"),
  lemmas: [
    ["database", 2],
    ["security", 1]
  ]
}
```

Число рядом с леммой - это `term_frequency`, то есть количество появлений
леммы в данном документе.

При построении индекса записи сортируются по MongoDB `_id` и получают
последовательные внутренние номера:

| Внутренний номер | MongoDB `_id` | Частоты термов |
|---:|---|---|
| `docID = 0` | `ObjectId("671a00000000000000000001")` | `cloud: 2`, `database: 1` |
| `docID = 1` | `ObjectId("671a00000000000000000002")` | `cloud: 1`, `security: 3` |
| `docID = 2` | `ObjectId("671a00000000000000000003")` | `database: 2`, `security: 1` |

Соответствие между `docID` и настоящим `ObjectId` записывается в
`documents.bin`. Поэтому posting lists могут использовать короткие целые
числа, а после поиска программа всё равно может получить документ из MongoDB.

## 2. Данные общего обратного индекса

После построения индекса термы направлены уже не от документа к словам, а от
слова к документам:

```text
cloud    -> [(docID=0, tf=2), (docID=1, tf=1)]
database -> [(docID=0, tf=1), (docID=2, tf=2)]
security -> [(docID=1, tf=3), (docID=2, tf=1)]
```

Эти пары хранятся в сжатом виде в `postings.bin`. Записи `lexicon.bin`
содержат смещения posting lists и их длины:

| Терм | `postings_count` | Смысл |
|---|---:|---|
| `cloud` | 2 | Терм встречается в двух документах, поэтому `df(cloud) = 2`. |
| `database` | 2 | Терм встречается в двух документах, поэтому `df(database) = 2`. |
| `security` | 2 | Терм встречается в двух документах, поэтому `df(security) = 2`. |

Заголовок `lexicon.bin` содержит:

```text
document_count = 3
```

Следовательно, полное число документов корпуса для этой формулы равно
`N = 3`. Отдельная таблица IDF не нужна: `N` берётся из заголовка индекса, а
`df` равен `postings_count` найденного терма.

## 3. Подготовка норм документов

Сначала обычная частота преобразуется в логарифмический TF:

```text
ltf(tf) = 1 + log10(tf), если tf > 0
ltf(0)  = 0
```

Для частот из примера:

```text
ltf(1) = 1 + log10(1) = 1
ltf(2) = 1 + log10(2) = 1.30103
ltf(3) = 1 + log10(3) = 1.47712
```

При построении индекса для каждого документа вычисляется L2-норма по всем его
термам, а не только по словам будущего запроса:

```text
||d|| = sqrt(ltf(tf1)^2 + ltf(tf2)^2 + ... + ltf(tfk)^2)
```

Здесь `k` - количество разных лемм документа, а `tfi` - частота соответствующей
леммы в этом документе.

Для трёх документов получаются следующие значения:

```text
||doc0|| = sqrt(ltf(cloud=2)^2 + ltf(database=1)^2)
         = sqrt(1.30103^2 + 1^2)
         = 1.64094

||doc1|| = sqrt(ltf(cloud=1)^2 + ltf(security=3)^2)
         = sqrt(1^2 + 1.47712^2)
         = 1.78378

||doc2|| = sqrt(ltf(database=2)^2 + ltf(security=1)^2)
         = sqrt(1.30103^2 + 1^2)
         = 1.64094
```

В `norms.bin` нормы располагаются по внутреннему номеру документа:

| Позиция в `norms.bin` | Значение |
|---:|---:|
| 0 | 1.64094 |
| 1 | 1.78378 |
| 2 | 1.64094 |

Поэтому норму можно получить прямым обращением
`document_norms[docID]`, без поиска по дереву или хеш-таблице.

## 4. Ввод поискового запроса

Пользователь вводит:

```text
cloud database
```

Запрос проходит тот же токенизатор и лемматизатор, что и документы. В этом
примере обе леммы встречаются в запросе по одному разу:

```text
cloud:    query_tf = 1
database: query_tf = 1
```

Поиск находит оба терма в `lexicon.bin`. Для каждого из них известны:

```text
N = 3
df = postings_count = 2
```

## 5. Вычисление весов запроса

Обратная документная частота вычисляется по формуле:

```text
idf(t) = log10(N / df(t))
```

Для обоих термов:

```text
idf(cloud)    = log10(3 / 2) = 0.17609
idf(database) = log10(3 / 2) = 0.17609
```

Ненормированный вес терма запроса:

```text
raw_query_weight(t) = ltf(query_tf(t)) * idf(t)
```

Поэтому:

```text
raw_query_weight(cloud)    = 1 * 0.17609 = 0.17609
raw_query_weight(database) = 1 * 0.17609 = 0.17609
```

Норма запроса равна:

```text
||q|| = sqrt(0.17609^2 + 0.17609^2) = 0.24903
```

После деления каждого веса на норму запроса:

```text
query_weight(cloud)    = 0.17609 / 0.24903 = 0.70711
query_weight(database) = 0.17609 / 0.24903 = 0.70711
```

Одинаковый IDF здесь сокращается только потому, что оба терма имеют одинаковые
`query_tf` и `df`. Если один терм встречается в меньшем числе документов, после
нормализации его вес будет больше.

## 6. Обход posting list терма `cloud`

Из `postings.bin` декодируется только диапазон, принадлежащий терму `cloud`:

```text
cloud -> [(docID=0, tf=2), (docID=1, tf=1)]
```

Вклад одного терма в документ вычисляется так:

```text
contribution(t, d) =
    query_weight(t) * ltf(tf(t, d)) / ||d||
```

Для `cloud`:

```text
doc0: 0.70711 * 1.30103 / 1.64094 = 0.56063
doc1: 0.70711 * 1       / 1.78378 = 0.39641
```

После первого posting list массив накопленных оценок имеет вид:

```text
scores[0] = 0.56063
scores[1] = 0.39641
scores[2] = 0
```

## 7. Обход posting list терма `database`

Затем читается диапазон `database`:

```text
database -> [(docID=0, tf=1), (docID=2, tf=2)]
```

Вклады равны:

```text
doc0: 0.70711 * 1       / 1.64094 = 0.43092
doc2: 0.70711 * 1.30103 / 1.64094 = 0.56063
```

Новые значения прибавляются к уже накопленным:

```text
scores[0] = 0.56063 + 0.43092 = 0.99155
scores[1] = 0.39641           = 0.39641
scores[2] = 0       + 0.56063 = 0.56063
```

В программе `scores` является обычным массивом, индексируемым по `docID`.
Хеш-таблица для накопления результатов не используется.

## 8. Сортировка результатов

Документы сортируются по убыванию `score`:

| Место | `docID` | `score` | Почему документ получил такой результат |
|---:|---:|---:|---|
| 1 | 0 | 0.99155 | Содержит оба терма запроса. |
| 2 | 2 | 0.56063 | Содержит только `database`, но с частотой 2. |
| 3 | 1 | 0.39641 | Содержит только `cloud` с частотой 1; частый `security` увеличивает норму документа. |

`doc0` находится на первом месте не просто потому, что содержит больше слов, а
потому, что направление его нормализованного вектора почти совпадает с
направлением запроса.

После ранжирования `documents.bin` переводит внутренние номера обратно в
MongoDB `ObjectId`:

```text
docID 0 -> ObjectId("671a00000000000000000001")
docID 2 -> ObjectId("671a00000000000000000003")
docID 1 -> ObjectId("671a00000000000000000002")
```

По этим идентификаторам из коллекции исходных документов загружаются заголовок,
источник и URL для отображения результата. MongoDB не участвует в вычислении
`score`: она нужна на этом этапе только для получения отображаемых метаданных.

## 9. Какие файлы использованы в примере

| Файл | Что TF-IDF берёт из него |
|---|---|
| `lexicon.bin` | `N`, `df`, смещение и длину posting list каждого терма. |
| `terms.bin` | Строки термов для двоичного поиска по лексикону. |
| `postings.bin` | Пары `(docID, term_frequency)` для термов запроса. |
| `norms.bin` | Готовую L2-норму по позиции `docID`. |
| `documents.bin` | Соответствие итогового `docID` идентификатору MongoDB `ObjectId`. |

Файл `skips.bin` в TF-IDF-поиске не используется. Для вычисления оценок всё
равно требуется пройти каждую запись posting list терма запроса и добавить её
вклад в `scores`.

## 10. Краткая последовательность работы

```text
запрос
  -> токенизация и лемматизация
  -> поиск термов в lexicon.bin и terms.bin
  -> вычисление IDF и нормализованных весов запроса
  -> чтение нужных posting lists из postings.bin
  -> получение норм документов из norms.bin
  -> накопление cosine score в scores[docID]
  -> сортировка затронутых документов
  -> перевод docID в ObjectId через documents.bin
  -> получение метаданных результата из MongoDB
```

Запустить ранжированный поиск можно командой:

```bash
./.build/tfidf_search configs/search.yaml
```

После запуска ввести:

```text
cloud database
```
