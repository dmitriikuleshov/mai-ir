# Лингвистический пайплайн: общий порядок обработки корпуса

## 1. Назначение этого компонента

Лингвистический пайплайн является связующим звеном между поисковым роботом и индексатором. Поисковый робот сохраняет в MongoDB сырые HTML-документы, но сам по себе HTML ещё нельзя напрямую использовать для полнотекстового поиска: в нём присутствуют теги, навигация, служебные блоки и разные словоформы одного слова. Пайплайн превращает каждый такой документ в нормализованное текстовое представление и сохраняет результаты, на основе которых далее строятся булев индекс и ранжированный индекс TF-IDF.

Весь компонент реализован на C++. Python в этой части системы не используется. Для разбора HTML применяется библиотека `libxml2`, а для взаимодействия с MongoDB — официальный C-драйвер `libmongoc` вместе с форматом BSON. Собственные алгоритмы токенизации, лемматизации и подсчёта частот находятся в C++-коде проекта.

В общем виде поток данных выглядит так:

```text
MongoDB: documents
сырые HTML-документы crawler
        │
        ▼
проверка content_hash и parser_version
        │
        ├── документ уже актуален ──► пропуск
        │
        ▼
извлечение содержательного текста из HTML
        │
        ▼
токенизация текста
        │
        ▼
лемматизация токенов
        │
        ▼
подсчёт частот токенов и лемм внутри документа
        │
        ▼
проверка минимального объёма документа
        │
        ▼
MongoDB: processed_documents + document_terms
        │
        ▼
MongoDB: token_frequencies + lemma_frequencies
        │
        ▼
results/statistics.json + results/zipf.svg
```

Этот документ описывает пайплайн целиком и нужен для понимания порядка обработки. Детальные правила токенизатора, устройство лемматизатора, словари исключений и построение закона Ципфа рассматриваются отдельно, потому что каждый из этих пунктов является самостоятельной частью лабораторной работы.

## 2. Что является входом и результатом работы

Входом служит коллекция `documents` базы `mai_ir`. Её заполняет crawler. Каждая запись содержит источник, идентификатор документа, URL, заголовок, сырой HTML и SHA-256-хэш этого HTML. Пайплайн не обращается к Wikipedia, arXiv или Microsoft Learn по сети и ничего повторно не скачивает. Он работает только с уже собранным корпусом в локальной MongoDB.

Для обработки из исходного документа читаются только необходимые поля:

```javascript
{
  _id: ObjectId("..."),
  source: "arxiv",
  source_id: "2601.00001",
  url: "https://arxiv.org/html/2601.00001v2",
  title: "Example technical paper",
  raw_html: "<!doctype html>...",
  content_hash: "..."
}
```

Результат распределяется между несколькими коллекциями. Такое разделение нужно потому, что очищенный текст, частоты конкретного документа и частоты всего корпуса используются по-разному.

| Коллекция | Что в ней хранится | Для чего она нужна |
|---|---|---|
| `documents` | Исходный HTML и метаданные crawler. | Вход пайплайна и возможность повторной обработки без скачивания; crawler может обновить запись при изменении страницы. |
| `processed_documents` | Извлечённый текст, признаки принятия, размеры, времена и версия обработчика. | Готовое текстовое представление документа и статистика обработки. |
| `document_terms` | Частоты токенов и лемм отдельно для каждого принятого документа. | Источник данных для построения поискового индекса и восстановления глобальных частот. |
| `token_frequencies` | Суммарная частота каждого токена во всём принятом корпусе. | Анализ словаря до лемматизации и формирование отчёта. |
| `lemma_frequencies` | Суммарная частота каждой леммы во всём принятом корпусе. | Анализ нормализованного словаря и построение графика Ципфа. |
| `linguistics_state` | Блокировка процесса и признак согласованности частот. | Защита от параллельного запуска и восстановление после прерывания. |

Кроме данных в MongoDB программа создаёт два файла в каталоге `results`:

- `statistics.json` содержит численные результаты: число документов и токенов, среднюю длину токена, скорость токенизации, размер словарей, популярные токены и леммы, показатели лемматизации и параметры аппроксимации распределения;
- `zipf.svg` содержит график распределения частот лемм в логарифмическом масштабе и аппроксимацию Мандельброта.

Файлы булева индекса, находящиеся в `results/boolean_index`, лингвистический пайплайн не создаёт. Их формирует следующий самостоятельный исполняемый файл `boolean_index`, который читает уже подготовленные записи `document_terms`.

## 3. Как запустить пайплайн

### 3.1. Предварительные условия

Перед запуском в MongoDB должны находиться документы, полученные crawler. Сначала необходимо запустить контейнер базы:

```bash
docker compose up -d
```

Состояние контейнера можно проверить командой:

```bash
docker compose ps
```

Если корпус ещё не собран, crawler запускается отдельно:

```bash
uv run python src/crawler/main.py config.yaml
```

Для самой лингвистической обработки `uv` не требуется, поскольку это C++-программа.

### 3.2. Сборка C++-компонента

Конфигурация проекта выполняется из корня репозитория:

```bash
cmake -S . -B .build -DCMAKE_BUILD_TYPE=Release
```

Затем проект собирается:

```bash
cmake --build .build --parallel
```

Режим `Release` важен для экспериментов с производительностью. Он включает оптимизации компилятора, поэтому измеренная скорость токенизации лучше соответствует реальной скорости рабочего компонента, чем при отладочной сборке.

После сборки исполняемый файл находится по пути `.build/linguistics`.

### 3.3. Полный запуск

Пайплайн получает единственный обязательный аргумент — путь к конфигурации:

```bash
./.build/linguistics config.yaml
```

Если аргумент не передан, программа выводит правильный формат команды:

```text
Использование: ./.build/linguistics config.yaml
```

Во время работы в терминале периодически выводятся число обработанных, принятых, отклонённых и пропущенных документов. Период вывода задаётся параметром `progress_every_documents`. После завершения программа печатает итоговую таблицу по источникам и пути к созданным файлам статистики.

### 3.4. Пробный запуск на ограниченном числе документов

Для проверки на небольшом подмножестве можно временно задать в `config.yaml`:

```yaml
linguistics:
  max_documents: 1000
```

После эксперимента для обработки всего корпуса параметр следует вернуть в состояние:

```yaml
linguistics:
  max_documents: null
```

Значение `null` означает отсутствие программного ограничения. При этом уже актуальные документы не обрабатываются повторно, поэтому повторный запуск на полном корпусе обычно завершается значительно быстрее первого.

### 3.5. Остановка программы

Пайплайн можно остановить сочетанием `Ctrl+C`. Обработчик сигнала не обрывает запись посередине текущего пакета. Он отмечает запрос на остановку, позволяет завершить пакет, сохраняет согласованные данные, освобождает блокировку и только после этого завершает процесс с кодом `130`.

Поэтому обычная ручная остановка не требует удаления коллекций или запуска специального восстановления. При следующем запуске программа продолжит работу: актуальные документы будут пропущены, а необработанные будут обработаны.

### 3.6. Запуск проверок

Все тесты проекта запускаются так:

```bash
ctest --test-dir .build --output-on-failure
```

Для проверки только базовых лингвистических частей можно отфильтровать тесты токенизации и лемматизации:

```bash
ctest --test-dir .build -R 'tokenizer|lemmatization' --output-on-failure
```

Отдельно проверяется извлечение текста из HTML:

```bash
ctest --test-dir .build -R 'html_extraction' --output-on-failure
```

## 4. Какие параметры конфигурации относятся к пайплайну

Параметры подключения и имена коллекций находятся в секции `db`, а алгоритмические параметры — в секции `linguistics`.

```yaml
db:
  uri: mongodb://localhost:27017
  database: mai_ir
  documents_collection: documents
  processed_collection: processed_documents
  document_terms_collection: document_terms
  token_frequencies_collection: token_frequencies
  lemma_frequencies_collection: lemma_frequencies
  linguistics_state_collection: linguistics_state

linguistics:
  batch_size: 100
  minimum_words: 200
  maximum_token_length: 100
  max_documents: null
  parser_version: 8
  lemma_dictionary: resources/wordnet_exceptions.tsv
  lemma_vocabulary: resources/wordnet_lemmas.txt
  lemma_overrides: resources/technical_lemma_overrides.tsv
  progress_every_documents: 100
  zipf_max_terms: 100000
  zipf_fit_terms: 10000
  top_terms: 30
  lock_lease_seconds: 600
  output_directory: results
```

Смысл параметров следующий.

| Параметр | Назначение |
|---|---|
| `uri` | Адрес локальной MongoDB. |
| `database` | Имя базы, в которой crawler и пайплайн обмениваются данными. |
| `*_collection` | Имена входной, выходных и служебной коллекций. |
| `batch_size` | Число исходных документов, обрабатываемых одним пакетом. |
| `minimum_words` | Минимальное число полученных токенов для принятия документа. |
| `maximum_token_length` | Максимальная допустимая длина одного токена. |
| `max_documents` | Максимальное число документов, реально переработанных за текущий запуск; `null` снимает ограничение. |
| `parser_version` | Ручная версия правил обработки, используемая для инвалидирования старого результата. |
| `lemma_dictionary` | Таблица исключений WordNet вида «словоформа → лемма». |
| `lemma_vocabulary` | Словарь допустимых базовых форм WordNet. |
| `lemma_overrides` | Дополнительные исключения для технического корпуса. |
| `progress_every_documents` | Через сколько обработанных документов печатать прогресс. |
| `zipf_max_terms` | Сколько наиболее частых лемм использовать при построении графика. |
| `zipf_fit_terms` | По скольким первым рангам подбирать параметры аппроксимации Мандельброта. |
| `top_terms` | Сколько популярных токенов и лемм записать в JSON-отчёт. |
| `lock_lease_seconds` | Срок действия блокировки одного экземпляра обработчика. |
| `output_directory` | Каталог для `statistics.json` и `zipf.svg`. |

Название `minimum_words` исторически говорит о словах, но технически программа сравнивает его со значением `token_count`, то есть с количеством токенов после токенизации. В большинстве обычных текстов эти величины близки, однако это не одно и то же: например, технические конструкции `C++`, `std::vector` и URL обрабатываются правилами токенизатора, а не простым разделением строки по пробелам.

Относительные пути к словарям и результатам вычисляются относительно файла конфигурации. Поэтому команда с конфигурацией из корня проекта использует ресурсы из `resources`, а результаты записывает в `results`, даже если исполняемый файл находится в `.build`.

## 5. Порядок действий при запуске программы

Точка входа намеренно остаётся маленькой. Она проверяет количество аргументов, загружает конфигурацию и передаёт управление приложению:

```cpp
int main(int argc, char **argv) {
    if (argc != 2) {
        std::fprintf(stderr, "Использование: %s config.yaml\n", argv[0]);
        return EXIT_FAILURE;
    }
    return run_linguistics(load_config(argv[1]));
}
```

Далее `run_linguistics` выполняет этапы в следующем порядке:

1. Запускает общий таймер программы и устанавливает обработчики `SIGINT` и `SIGTERM`.
2. Инициализирует драйвер MongoDB и библиотеку `libxml2`.
3. Подключается к базе и выполняет команду `ping`, чтобы обнаружить проблему подключения до начала длительной обработки.
4. Открывает все необходимые коллекции.
5. Загружает словари лемматизатора в память.
6. Получает блокировку в `linguistics_state`, запрещающую второй одновременный запуск.
7. Проверяет согласованность глобальных частот и при необходимости восстанавливает их из `document_terms`.
8. Создаёт индексы MongoDB, необходимые для уникальности и быстрых выборок.
9. Последовательно читает исходные документы пакетами и запускает их обработку.
10. После окончания помечает частотные коллекции согласованными.
11. Собирает статистику по всему принятому корпусу и создаёт отчётные файлы.
12. Освобождает блокировку и корректно завершает работу библиотек.

Ключевая последовательность видна непосредственно в функции приложения:

```cpp
ProcessingLock lock = acquire_processing_lock(
    collections.state, config.lock_lease_seconds);
prepare_frequencies(collections, config.parser_version);
create_indexes(collections);

const Counters counters =
    process_documents(collections, &lock, config, dictionary);

set_frequency_state(collections.state, false, config.parser_version);
write_report(config, counters, collections, dictionary,
             monotonic_seconds() - program_started);
release_processing_lock(collections.state, &lock);
```

Такой порядок важен. Нельзя сначала формировать отчёт, а затем завершать обновление частот, поскольку статистика оказалась бы построена по промежуточному состоянию корпуса. Нельзя и начинать обработку до получения блокировки, иначе два процесса могли бы одновременно прибавить частоты одного документа.

## 6. Обработка корпуса пакетами

Исходные документы читаются из `documents` в порядке `_id`. MongoDB возвращает не весь документ целиком, а только проекцию полей, нужных пайплайну: `_id`, `source`, `source_id`, `url`, `title`, `raw_html` и `content_hash`. Это не уменьшает объём самого HTML, но не переносит из базы ненужные crawler-метаданные.

Прочитанные записи накапливаются в `std::vector<Document>` размером `batch_size`. Для текущего значения `100` обработка и запись происходят группами до ста документов. Пакетный режим уменьшает число отдельных обращений к MongoDB и одновременно ограничивает объём оперативной памяти. В память не загружается весь корпус из сотен тысяч документов.

Для записи используются неупорядоченные bulk-операции MongoDB (`ordered: false`). База получает группу однотипных обновлений и может выполнять независимые операции без остановки на первой неудачной записи. Однако логический порядок между разными коллекциями контролируется самой программой и описан далее.

После каждого законченного пакета программа продлевает аренду блокировки. Значение `lock_lease_seconds` должно быть достаточно большим, чтобы один пакет успевал завершиться до истечения блокировки; текущее значение 600 секунд имеет большой запас относительно обычного времени обработки ста документов.

## 7. Как определяется, нужно ли обрабатывать документ повторно

Перед обработкой пакета программа одним запросом загружает из `processed_documents` существующие результаты для тех же `_id`. Документ считается актуальным только при одновременном выполнении двух условий:

```cpp
return existing.parser_version == config.parser_version &&
       existing.content_hash == raw_document.content_hash;
```

Первое условие подтверждает, что результат был получен текущей версией правил. Второе условие подтверждает, что crawler с того момента не сохранил изменённый HTML.

Возможны три основных случая:

| Состояние | Действие пайплайна |
|---|---|
| В `processed_documents` ещё нет записи с таким `_id`. | Документ обрабатывается впервые. |
| `content_hash` и `parser_version` совпадают. | Документ считается актуальным и пропускается. |
| Изменился хэш или версия парсера. | Старый результат заменяется новым, а частоты корректируются. |

Благодаря такой проверке повторный запуск является инкрементальным. Программа всё равно просматривает идентификаторы входного корпуса, но дорогие операции разбора HTML, токенизации и лемматизации выполняются только для новых или устаревших документов.

`parser_version` представляет собой не номер версии программы вообще, а ручную версию формата лингвистического результата. Её необходимо увеличить, если изменилось что-либо, способное повлиять на сохранённый текст, токены, леммы или решение о принятии документа. К таким изменениям относятся:

- новые правила извлечения текста из HTML;
- изменение правил токенизации;
- изменение алгоритма или файлов словаря лемматизации;
- изменение `maximum_token_length`;
- изменение `minimum_words`;
- изменение структуры сохраняемого результата.

Например, если заменить `minimum_words: 500` на `minimum_words: 200`, но оставить тот же `parser_version`, ранее отклонённые документы будут считаться актуальными и не пройдут новую проверку. Поэтому после такого изменения нужно увеличить `parser_version`, например с `8` до `9`, и снова запустить пайплайн. Это осознанный механизм инвалидирования кэша: программа не пытается автоматически вычислять хэш всех правил и словарных файлов.

## 8. Извлечение содержательного текста из HTML

Для документа, требующего обработки, сначала вызывается `extract_text(raw_html, source)`. Библиотека `libxml2` строит HTML-дерево даже для частично некорректной разметки. Флаг `HTML_PARSE_NONET` запрещает парсеру самостоятельно обращаться к внешним сетевым ресурсам, поэтому обработка остаётся локальной и воспроизводимой.

Разные источники имеют разную структуру страниц, поэтому корневой содержательный блок выбирается по имени источника:

| Источник | Основной узел содержимого |
|---|---|
| Wikipedia | Элемент с `id="mw-content-text"`. |
| arXiv HTML | Элемент `article` с классом `ltx_document`. |
| Microsoft Learn | Элемент `main`. |

Если ожидаемый узел Wikipedia или arXiv не найден, используется `main`, а затем корень HTML-документа. Такой резервный путь позволяет не получить пустой результат только из-за изменения внешней вёрстки.

Из выбранного поддерева удаляются общие служебные элементы: `script`, `style`, `nav`, `aside`, `footer`, `header`, `form`, `svg`, `noscript`, `template` и `button`. Затем применяются правила конкретного источника. Например, из Wikipedia убираются блоки редактирования, навигационные таблицы, содержание и список ссылок; из arXiv — библиография и служебный footer; из Microsoft Learn — отзывы, список участников, рекомендации и метаданные.

После удаления шума текст узла извлекается и все варианты пробельных символов Unicode нормализуются до одиночного обычного пробела. Результатом этапа является одна строка UTF-8 без HTML-тегов. Глубокий разбор XPath-правил и примеры страниц каждого источника будут приведены в отдельном документе об извлечении текста.

## 9. Внутренняя лингвистическая обработка текста

Очищенная строка передаётся функции `linguistics_process`. На этом уровне порядок строго фиксирован:

```cpp
TokenizationResult tokenization =
    tokenize_text(text, text_size, maximum_token_length);

LemmatizationResult lemmatization =
    lemmatize_tokens(&tokenization.tokens, dictionary);

result.tokens = make_frequencies(std::move(tokenization.tokens));
result.lemmas = make_frequencies(std::move(lemmatization.lemmas));
```

Сначала токенизатор выделяет последовательность токенов. Лемматизатор не читает исходный HTML и не разбирает текст повторно: он получает уже готовый список токенов и для каждого токена определяет нормальную форму. Поэтому правила токенизации напрямую влияют на лемматизацию. Если технический термин был неверно разделён на части, лемматизатор уже не сможет восстановить его исходную структуру.

Кроме самих списков, измеряются:

- общее количество токенов;
- суммарное количество символов в токенах;
- количество токенов, форма которых изменилась при лемматизации;
- время токенизации в наносекундах;
- время лемматизации в наносекундах.

Время измеряется монотонными часами `std::chrono::steady_clock`. Они подходят для измерения длительности, потому что не зависят от перевода системного времени. При сохранении в MongoDB наносекунды переводятся в секунды типа `double`.

Для получения частот список строк сортируется, после чего одинаковые соседние элементы сворачиваются в пары «терм — количество». В результате вместо длинного списка вида

```text
search, index, search, document, index, search
```

сохраняется компактное представление:

```text
document → 1
index    → 2
search   → 3
```

В этой части не используется `std::unordered_map` или `std::map`. Частоты строятся через `std::vector`, сортировку и линейный проход по отсортированному массиву. Это соответствует уточнённому ограничению курса: строки и векторы можно применять, но готовые хеш-таблицы и деревья не должны заменять собственные структуры ключа поисковой системы.

Конкретные правила распознавания `C++`, `C#`, `.NET`, `node.js`, URL, пространств имён и других конструкций, а также правила словарной и эвристической лемматизации будут разобраны в отдельных документах.

## 10. Проверка минимального объёма документа

После токенизации программа сравнивает число токенов с `minimum_words`:

```cpp
const bool accepted =
    result.token_count >= config.minimum_words;
```

При текущем значении `200` документ принимается, если из его содержательного текста удалось получить не менее 200 токенов. Эта проверка выполняется после очистки HTML, поэтому большой объём навигации или JavaScript не помогает странице пройти фильтр.

Для принятого документа в `processed_documents` сохраняется очищенный текст, а в `document_terms` — частоты его токенов и лемм. Для слишком короткого документа сохраняются диагностические поля и причина `too_short`, но поле `text` удаляется, а запись `document_terms` отсутствует. Таким образом, отклонённая страница остаётся видимой для анализа, но не попадает в словари и поисковый индекс.

## 11. Что сохраняется для одного обработанного документа

Упрощённая запись принятого документа в `processed_documents` выглядит так:

```javascript
{
  _id: ObjectId("тот же _id, что и в documents"),
  source: "wikipedia",
  source_id: 123456,
  url: "https://en.wikipedia.org/wiki/Information_retrieval",
  title: "Information retrieval",
  content_hash: "...",
  parser_version: 8,
  accepted: true,
  text: "Information retrieval is ...",
  text_size: 42137,
  word_count: 6021,
  token_count: 6021,
  token_characters: 46320,
  changed_token_count: 1732,
  extraction_seconds: 0.0041,
  tokenization_seconds: 0.0028,
  lemmatization_seconds: 0.0034,
  processed_at: 1790000000,
  rejection_reason: null
}
```

`text_size` измеряется в байтах UTF-8, а не в символах. Поля времени хранят длительность в секундах. `token_characters` — суммарное число символов во всех токенах; оно используется вместе с `token_count` для расчёта средней длины токена. В текущей реализации `word_count` и `token_count` получают одно и то же значение, потому что единицей дальнейшего анализа является токен.

Запись того же документа в `document_terms` содержит не полный текст, а частотные массивы:

```javascript
{
  _id: ObjectId("тот же _id"),
  source: "wikipedia",
  source_id: 123456,
  content_hash: "...",
  tokens: [
    ["indexes", 4],
    ["retrieval", 17],
    ["systems", 8]
  ],
  lemmas: [
    ["index", 4],
    ["retrieval", 17],
    ["system", 8]
  ]
}
```

Каждый элемент массива является парой `[терм, частота_в_документе]`. Именно `document_terms` читает построитель булева индекса. По умолчанию индекс строится по массиву `lemmas`, поэтому разные словоформы получают общий поисковый ключ.

## 12. Как обновляются глобальные частоты

Коллекции `token_frequencies` и `lemma_frequencies` содержат по одной записи на терм:

```javascript
{ _id: "retrieval", count: 183245 }
```

Поле `_id` является самим токеном или леммой, а `count` — суммой частот по всем принятым документам. При первой обработке документа его локальные частоты прибавляются к глобальным.

При повторной обработке нельзя просто прибавить новый результат, иначе один документ будет учтён дважды. Поэтому программа сначала читает старую запись `document_terms`, добавляет её частоты в пакет с отрицательным знаком, а новые частоты — с положительным:

```text
изменение глобальной частоты = новая частота документа − старая частота документа
```

Если документ раньше был принят, а после изменения правил стал слишком коротким, старые частоты вычитаются, новые не добавляются, а запись `document_terms` удаляется. Если документ раньше был отклонён, а теперь принят, происходит обратное. После завершения корпуса записи с нулевой или отрицательной итоговой частотой удаляются.

Дельты одного пакета сортируются по терму и объединяются до отправки в MongoDB. Это уменьшает число операций: если один и тот же термин встретился во многих документах пакета, база получает одно суммарное изменение вместо большого числа отдельных прибавлений.

## 13. Согласованность данных и восстановление после ошибки

Пайплайн не использует одну большую транзакцию на весь корпус, поскольку она была бы слишком долгой и тяжёлой. Вместо этого используется восстанавливаемый протокол записи.

В начале запуска в `linguistics_state` для записи `_id: "frequencies"` устанавливается `dirty: true`. Это означает, что глобальные частоты могут находиться в процессе изменения. После успешного завершения обработки значение меняется на `dirty: false`.

Внутри пакета данные записываются в таком порядке:

1. применяются дельты к `token_frequencies` и `lemma_frequencies`;
2. сохраняются новые локальные частоты в `document_terms`;
3. последней записывается версия документа в `processed_documents`.

Последний шаг играет роль маркера фиксации. Проверка актуальности смотрит именно на `processed_documents`, поэтому документ не будет ошибочно считаться завершённым до записи его локальных частот.

`document_terms` является восстанавливаемым источником истины для глобальных частот. Если предыдущий процесс аварийно завершился, оставив состояние `dirty: true`, следующий запуск выполняет MongoDB-агрегацию по всем массивам `tokens` и `lemmas`, заново суммирует частоты и заменяет глобальные коллекции. Такое же восстановление выполняется, если локальные частоты существуют, а одна из глобальных коллекций пуста, или наоборот.

Отдельная запись `_id: "processor_lock"` защищает от одновременного запуска двух экземпляров. В ней хранится случайный идентификатор владельца и время `lock_until`. Если блокировка ещё действует, второй процесс завершится с понятным сообщением. После каждого пакета первый процесс продлевает блокировку, а при штатном завершении освобождает её.

## 14. Индексы MongoDB, создаваемые пайплайном

Индексы создаются автоматически при запуске, поэтому вручную подготавливать схему базы не требуется.

| Коллекция | Индекс | Назначение |
|---|---|---|
| `processed_documents` | `{source: 1, source_id: 1}`, уникальный | Защищает от двух результатов одного логического документа источника. |
| `processed_documents` | `{accepted: 1, source: 1}` | Ускоряет статистику и выборки принятого корпуса по источникам. |
| `processed_documents` | `{content_hash: 1}` | Ускоряет анализ результатов по версии содержимого. |
| `document_terms` | `{source: 1}` | Ускоряет выборки терминов по источнику. |
| `token_frequencies` | `{count: -1}` | Быстро получает наиболее частые токены. |
| `lemma_frequencies` | `{count: -1}` | Быстро получает наиболее частые леммы и ранги для графика. |

Идентификатор `_id` во всех коллекциях уже индексируется MongoDB автоматически. В `processed_documents` и `document_terms` используется тот же `ObjectId`, что и у исходного документа. Благодаря этому связанные данные одного документа можно получить без дополнительной таблицы соответствий.

## 15. Формирование итоговой статистики

После обработки программа не ограничивается счётчиками текущего запуска. Она выполняет агрегации MongoDB по всем записям `processed_documents` с `accepted: true`, поэтому итоговый отчёт характеризует весь актуальный принятый корпус, а не только документы, изменённые в этот раз.

В `statistics.json` записываются:

- счётчики текущего запуска: просмотрено, пропущено, обработано, принято и отклонено;
- число документов и токенов всего корпуса;
- размер очищенного текста в байтах;
- средняя длина токена в символах;
- суммарное время токенизации и пропускная способность в KiB/s;
- те же показатели отдельно для Wikipedia, arXiv и Microsoft Learn;
- зависимость производительности от размера текста, разбитая на восемь диапазонов;
- число различных токенов и различных лемм;
- наиболее частые токены и леммы;
- параметры аппроксимации Мандельброта;
- результаты встроенной проверки качества лемматизации;
- полное время текущего запуска программы.

Пропускная способность рассчитывается как отношение суммарного размера очищенного текста в KiB к суммарному времени токенизации в секундах:

```text
KiB/s = text_bytes / 1024 / tokenization_seconds
```

Время извлечения HTML и лемматизации хранится у каждого документа, но показатель KiB/s в отчёте относится именно к токенизации, как требуется в задании преподавателя.

График `zipf.svg` строится по глобальной коллекции `lemma_frequencies`. Термы сортируются по убыванию частоты, порядковый номер становится рангом, а обе оси переводятся в логарифмический масштаб. На тот же график наносится подобранная к фактическим данным кривая Мандельброта. Это позволяет не только визуально показать закон Ципфа, но и численно оценить отличие наблюдаемого распределения от модели.

## 16. Жизненный цикл одного документа на примере

Предположим, crawler сохранил новую статью Wikipedia. Для неё ещё нет записей в выходных коллекциях.

1. Пайплайн читает `_id`, `source`, `raw_html` и `content_hash` статьи.
2. В `processed_documents` не находится результата с тем же `_id`, поэтому статья помечается как требующая обработки.
3. HTML разбирается `libxml2`; выбирается блок `mw-content-text`, из которого удаляются навигация, список литературы и служебные элементы.
4. Пробельные символы нормализуются, и получается очищенная строка.
5. Токенизатор выделяет токены и измеряет свою длительность.
6. Лемматизатор строит нормальные формы и измеряет свою длительность.
7. Отдельно подсчитываются частоты исходных токенов и лемм.
8. Если токенов не меньше 200, документ принимается.
9. Его частоты прибавляются к глобальным словарям.
10. Частотные массивы записываются в `document_terms`.
11. Очищенный текст и метрики записываются в `processed_documents`. На этом документ считается зафиксированным.

При следующем запуске совпадут и `content_hash`, и `parser_version`, поэтому статья будет пропущена. Если crawler позднее скачает изменившийся HTML, хэш станет другим. Тогда пайплайн вычтет старые частоты статьи, обработает новую версию и прибавит новые частоты. Если изменится собственный алгоритм, тот же эффект достигается увеличением `parser_version`.

## 17. Что показать преподавателю при общей демонстрации

Сначала следует показать, что MongoDB запущена и в коллекции `documents` уже находится сырой корпус. Затем из корня проекта нужно собрать и запустить компонент:

```bash
cmake -S . -B .build -DCMAKE_BUILD_TYPE=Release
cmake --build .build --parallel
./.build/linguistics config.yaml
```

Во время запуска можно объяснить следующее:

> Программа читает сырой HTML из MongoDB пакетами. Для каждого документа она проверяет хэш содержимого и версию парсера, поэтому повторно обрабатываются только новые или устаревшие документы. Затем из HTML выделяется содержательный текст, выполняются токенизация и лемматизация, а частоты токенов и лемм сохраняются как для отдельного документа, так и для корпуса целиком. После завершения строятся статистика и график Ципфа.

После запуска в MongoDB Compass удобно последовательно открыть:

1. `documents` и показать исходный `raw_html` вместе с `content_hash`;
2. `processed_documents` и показать соответствующий очищенный `text`, `parser_version`, `accepted` и времена обработки;
3. `document_terms` и показать массивы `tokens` и `lemmas` одного документа;
4. `token_frequencies` или `lemma_frequencies`, отсортировав записи по `count` по убыванию;
5. `linguistics_state` и показать состояние частот и служебную блокировку.

Затем следует открыть `results/statistics.json` и `results/zipf.svg`. В JSON нужно обратить внимание на размер корпуса, среднюю длину токена, скорость в KiB/s, размеры словарей и популярные термы. На SVG нужно показать логарифмические оси, фактическое распределение частот и аппроксимацию.

Если преподаватель спросит, почему повторный запуск почти ничего не обрабатывает, это является ожидаемым поведением: совпадающие `content_hash` и `parser_version` означают, что сохранённый результат актуален. Для демонстрации полного повторного прохода можно увеличить `parser_version`, но на большом корпусе это запустит переработку всех документов и займёт значительное время.

## 18. Границы этого обзорного документа

На уровне всей системы важно запомнить основную причинно-следственную цепочку:

```text
сырой HTML
→ содержательный текст
→ токены
→ леммы
→ локальные частоты документа
→ глобальные частоты корпуса
→ статистика и данные для индексации
```

Токенизация выполняется раньше лемматизации, потому что лемматизатор работает с готовыми токенами. Локальные частоты сохраняются отдельно от глобальных, потому что они нужны для построения индекса, инкрементального обновления и восстановления после ошибки. `processed_documents` записывается последней и служит признаком успешно завершённой обработки документа. `parser_version` связывает сохранённый результат с текущими правилами и позволяет осознанно запустить повторную обработку корпуса.

В следующих отдельных документах можно подробно разобрать:

- извлечение текста из HTML для каждого из трёх источников;
- правила и пограничные случаи токенизатора;
- словарную и эвристическую части лемматизатора;
- устройство частотных словарей и анализ закона Ципфа;
- результаты тестов и измерение производительности.

Для общего понимания пайплайна достаточно видеть не набор разрозненных файлов, а последовательное преобразование одного документа и причины, по которым каждый промежуточный результат сохраняется отдельно.
