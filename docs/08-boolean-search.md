# Булев поиск: разбор запроса и операции над posting lists

## 1. Что такое булев поиск

Булев поиск выбирает документы, которые удовлетворяют логическому выражению из поисковых термов. Пользователь явно задаёт условия операторами:

```text
AND — документ должен содержать оба выражения;
OR  — документ должен содержать хотя бы одно выражение;
NOT — документ не должен входить в результат выражения.
```

Поддерживаются круглые скобки, поэтому можно управлять порядком вычисления:

```text
database AND security
cloud OR distributed
retrieval AND NOT neural
(database OR storage) AND replication
NOT (cloud OR security)
```

Булев поиск не вычисляет степень релевантности и не сортирует документы по score. Каждый документ либо удовлетворяет выражению, либо нет. Результатом является возрастающий список внутренних `docID` без повторов.

В проекте поиск работает не по полным текстам и не обращается к каждому документу. Он использует заранее построенный инвертированный индекс:

```text
терм → отсортированный список docID
```

Например:

```text
cloud    → [0, 1, 5]
database → [1, 2, 5]
security → [1, 4, 5]
```

Запрос `cloud AND database` сводится к пересечению двух списков и возвращает `[1, 5]`. Текст документов при этом не читается.

## 2. Место компонента в системе

Полный путь запроса выглядит так:

```text
строка пользователя
        │
        ▼
лексемы TERM / AND / OR / NOT / ( / )
        │
        ▼
рекурсивный спуск с приоритетами операторов
        │
        ▼
токенизация и лемматизация каждого TERM
        │
        ▼
двоичный поиск терма в lexicon.bin
        │
        ▼
Variable Byte-декодирование posting list
        │
        ▼
AND / OR / NOT над отсортированными docID
        │
        ▼
documents.bin: docID → MongoDB ObjectId
        │
        ▼
processed_documents: title, source, url
```

Само множество подходящих документов полностью определяется бинарным индексом. MongoDB используется после поиска только для получения человекочитаемых метаданных ограниченного числа результатов.

## 3. Где находится реализация

Код расположен в `src/boolean_search` и разделён по ответственности.

| Часть | Назначение |
|---|---|
| `app` | Загрузка конфигурации, запуск консольного интерфейса и вывод документов. |
| `index` | Открытие бинарных файлов, двоичный поиск терма, декодирование postings и чтение ObjectId. |
| `query/query_parser.cpp` | Лексический разбор, рекурсивный спуск, нормализация термов и вычисление выражения. |
| `query/posting_operations.cpp` | Линейные алгоритмы пересечения, объединения и дополнения списков. |

Публичная функция поиска имеет следующий интерфейс:

```cpp
BooleanResult boolean_search(
    BooleanIndex *index,
    const char *query,
    size_t maximum_token_length,
    const LemmaDictionary *dictionary,
    char *error,
    size_t error_size);
```

`BooleanResult` является обычным отсортированным вектором внутренних идентификаторов:

```cpp
using BooleanResult = std::vector<uint32_t>;
```

При успешном запросе функция возвращает список `docID`, а строка `error` остаётся пустой. При синтаксической или нормализационной ошибке возвращается пустой список и понятное сообщение.

## 4. Как запустить поиск

Перед поиском должны существовать готовые файлы индекса. Полная последовательность команд из корня проекта:

```bash
docker compose up -d
cmake -S . -B .build -DCMAKE_BUILD_TYPE=Release
cmake --build .build --parallel
./.build/linguistics config.yaml
./.build/boolean_index config.yaml
./.build/boolean_search config.yaml
```

Если лингвистический результат и индекс уже построены, первые две рабочие команды повторять не нужно. Достаточно запустить MongoDB и консоль поиска:

```bash
docker compose up -d
./.build/boolean_search config.yaml
```

В интерактивном терминале программа выводит приглашение:

```text
Введите запрос с AND, OR, NOT и скобками. Ctrl+D — выход.
>
```

Каждая строка является отдельным запросом. Завершение ввода `Ctrl+D` закрывает программу.

Утилита также читает стандартный ввод без интерактивной подсказки, поэтому один запрос можно передать конвейером:

```bash
echo 'database AND security' | ./.build/boolean_search config.yaml
```

Несколько запросов можно записать по одному в строке файла и выполнить:

```bash
./.build/boolean_search config.yaml < queries.txt
```

Такой интерфейс соответствует требованию курса о консольной утилите, принимающей запросы со стандартного ввода и выдающей результат в стандартный вывод.

## 5. Параметры конфигурации

Поиск использует несколько секций общего `config.yaml`:

```yaml
db:
  uri: mongodb://localhost:27017
  database: mai_ir
  processed_collection: processed_documents

linguistics:
  maximum_token_length: 100
  lemma_dictionary: resources/wordnet_exceptions.tsv
  lemma_vocabulary: resources/wordnet_lemmas.txt
  lemma_overrides: resources/technical_lemma_overrides.tsv

boolean_index:
  output_directory: results/boolean_index
  term_field: lemmas

boolean_search:
  result_limit: 20
```

| Параметр | Назначение |
|---|---|
| `uri`, `database` | Подключение к MongoDB для метаданных результатов. |
| `processed_collection` | Коллекция с `title`, `source` и `url`. |
| `maximum_token_length` | То же ограничение токена, которое использовалось при обработке корпуса. |
| `lemma_dictionary` | Исключения WordNet. |
| `lemma_vocabulary` | Словарь допустимых лемм. |
| `lemma_overrides` | Исключения технического корпуса. |
| `output_directory` | Каталог бинарного индекса. |
| `result_limit` | Максимальное число документов, для которых печатаются метаданные. |

`result_limit` не ограничивает само логическое вычисление. Программа сначала получает полное множество совпавших `docID` и выводит его размер, а затем обращается за метаданными только для первых `result_limit` элементов.

Текущая реализация запроса всегда использует леммы. Поэтому рабочий индекс должен быть построен с `boolean_index.term_field: lemmas`. Построитель технически умеет создать индекс по `tokens`, но query parser всё равно обращается к `normalized.lemmas`; смешивать эти режимы нельзя без отдельного изменения поискового кода.

## 6. Какие файлы индекса открываются

При запуске булев поиск открывает четыре файла:

```text
lexicon.bin
terms.bin
postings.bin
documents.bin
```

`norms.bin` не требуется, потому что булев поиск не вычисляет TF-IDF и cosine score.

Открытые файлы и общий заголовок хранятся в структуре:

```cpp
struct BooleanIndex {
    void *lexicon_file;
    void *terms_file;
    void *postings_file;
    void *documents_file;
    boolean_index_format::IndexHeader header;
};
```

До запуска консольного цикла проверяются:

- наличие всех четырёх файлов;
- magic `MAIIRIDX` в лексиконе;
- версия бинарного формата;
- magic `MAIIRDOC` в таблице документов;
- совпадение версии;
- совпадение `document_count` в лексиконе и `documents.bin`.

Если каталог отсутствует, заголовок повреждён или таблица ObjectId относится к другой сборке индекса, программа завершается с ошибкой, а не выполняет поиск по несогласованным данным.

## 7. Лексический разбор строки запроса

Первым уровнем query parser является функция `next_token`. Она преобразует строку в последовательность лексем:

```cpp
enum class TokenType {
    END,
    TERM,
    AND,
    OR,
    NOT,
    LEFT,
    RIGHT,
    INVALID
};
```

Пробельные символы пропускаются. Открывающая и закрывающая скобки являются самостоятельными лексемами даже без пробелов:

```text
(cloud OR database)AND security
```

Остальные символы читаются до пробела или скобки и образуют одно слово. Точные слова `AND`, `OR`, `NOT` распознаются как операторы без учёта регистра ASCII:

```text
AND
and
And
aNd
```

Все варианты означают один оператор. Слово `android` не становится `AND`, потому что сравнение требует полного совпадения длины и символов.

Любое другое непробельное слово становится лексемой `TERM`. На этом уровне терм ещё не токенизирован и не лемматизирован.

## 8. Формальная грамматика

Грамматику можно записать следующим образом:

```text
expression = or_expression

or_expression = and_expression
                { OR and_expression }

and_expression = unary_expression
                 { AND unary_expression }

unary_expression = NOT unary_expression
                   | primary

primary = TERM
          | "(" or_expression ")"
```

Фигурные скобки здесь означают повторение, а не символы запроса. Такая структура задаёт приоритеты:

```text
1. скобки
2. NOT
3. AND
4. OR
```

`NOT` является унарным оператором и применяется к следующему унарному выражению. Поэтому поддерживаются цепочки:

```text
NOT NOT cloud
NOT NOT NOT cloud
```

Двойное отрицание возвращает исходное множество, тройное — его дополнение.

## 9. Почему рекурсивный спуск задаёт приоритеты

Разбор организован цепочкой функций:

```text
parse_or
  └── parse_and
        └── parse_unary
              └── parse_primary
```

`parse_or` не читает непосредственный терм. Сначала он обязан получить целое `and_expression`. Аналогично `parse_and` сначала получает `unary_expression`, а `parse_unary` передаёт управление `parse_primary`.

Из-за этой вложенности более глубокий уровень вычисляется раньше. Поэтому запрос

```text
cloud OR database AND security
```

понимается как:

```text
cloud OR (database AND security)
```

а не как:

```text
(cloud OR database) AND security
```

Скобки в `parse_primary` рекурсивно вызывают `parse_or`, то есть внутри них можно записать полное выражение с любыми поддерживаемыми операторами.

## 10. Разбор сразу вычисляет результат

Парсер не строит отдельное абстрактное синтаксическое дерево. Каждая функция сразу возвращает `BooleanResult` — отсортированный список документов для уже разобранной части выражения.

Упрощённо:

```cpp
BooleanResult parse_and(Parser *parser, bool *ok) {
    BooleanResult left = parse_unary(parser, ok);
    while (*ok && parser->current.type == TokenType::AND) {
        advance(parser);
        BooleanResult right = parse_unary(parser, ok);
        left = intersect_postings(left, right);
    }
    return left;
}
```

Для запроса

```text
cloud AND database AND security
```

сначала получается posting list `cloud`, затем он пересекается с `database`, после чего промежуточный результат пересекается с `security`.

Преимущества такого подхода:

- не требуется отдельная иерархия узлов AST;
- логика приоритетов видна непосредственно из функций;
- промежуточное выражение сразу превращается в полезный список;
- память расходуется на posting lists, а не на дополнительное дерево.

Ограничение состоит в том, что после разбора нельзя отдельно оптимизировать всё дерево, например заранее переставить операнды `AND` по возрастанию длины posting list. Текущая реализация вычисляет операторы слева направо внутри одного уровня приоритета.

## 11. Нормализация поискового терма

Когда `parse_primary` получает лексему `TERM`, она проходит тот же `linguistics_process`, что и документы корпуса:

```cpp
LinguisticResult normalized = linguistics_process(
    parser->current.text.data(),
    parser->current.text.size(),
    parser->maximum_token_length,
    parser->dictionary);
```

Таким образом, применяются:

- нормализация UTF-8;
- правила технического токенизатора;
- приведение ASCII к нижнему регистру;
- лемматизация WordNet;
- технические исключения.

Примеры:

```text
QUERIES  → query
databases → database
SHA‑256  → sha-256
Node.js  → node.js
C++      → c++
```

Это обеспечивает симметрию: документ и запрос получают одинаковый ключ индекса.

После pipeline терм должен дать ровно одну различную лемму. Если лемм нет или их несколько, запрос отклоняется как неоднозначный:

```text
...             → 0 лемм → ошибка
cloud/database  → cloud, database → ошибка
```

Внутри `LinguisticResult` одинаковые леммы уже объединены с частотой. Поэтому формально проверяется число различных лемм, а не исходное число токенов. Для обычной лексемы эти величины совпадают.

Ограничение `maximum_token_length` также действует на запрос. Если термин длиннее допустимого предела и токенизатор его отбрасывает, parser сообщает, что термин не удалось однозначно нормализовать.

## 12. Поиск терма в бинарном лексиконе

После нормализации вызывается `load_postings`. Сначала функция `boolean_index_find_term` выполняет двоичный поиск по фиксированным записям `lexicon.bin`.

Для средней записи вычисляется адрес:

```text
sizeof(IndexHeader) + middle × sizeof(LexiconEntry)
```

Из `LexiconEntry` читаются:

- `term_offset`;
- `term_length`;
- `postings_offset`;
- `postings_count`.

По `term_offset` и `term_length` читается соответствующая UTF-8-строка из `terms.bin` и сравнивается с искомым ключом. В зависимости от результата поиск продолжает левую или правую половину.

Сложность нахождения терма составляет `O(log V)` сравнений, где `V` — число различных термов в индексе. Словарь не загружается в `std::map` или `std::unordered_map`.

Если терм отсутствует, возвращается пустой posting list. Это не синтаксическая ошибка: корректный запрос может просто не иметь совпадений.

## 13. Чтение сжатого posting list

После нахождения терма reader переходит к `postings_offset` и читает ровно `postings_count` пар:

```text
VariableByte(docID-gap)
VariableByte(term_frequency)
```

Абсолютный `docID` восстанавливается накоплением gaps:

```cpp
document_id += document_gap;
```

Полный reader сначала создаёт `WeightedPostingList`, где сохраняются и `docID`, и TF. Булевому поиску частота не нужна, поэтому `load_postings` оставляет только идентификаторы:

```cpp
for (const WeightedPosting &posting : weighted) {
    result.push_back(posting.document_id);
}
```

Такой общий reader используется также TF-IDF-поиском, которому TF необходима для веса терма.

На этапе чтения проверяются положительная TF, отсутствие нулевого gap после первого документа и отсутствие переполнения `uint32_t`.

## 14. Инвариант BooleanResult

Все операции полагаются на важный инвариант:

```text
BooleanResult всегда отсортирован по возрастанию
и не содержит повторяющихся docID.
```

Индекс создаёт posting lists в возрастающем порядке. `load_postings` сохраняет этот порядок. Пересечение, объединение и дополнение также возвращают отсортированный уникальный результат.

Благодаря этому операции выполняются двумя указателями без хеш-таблиц и деревьев.

## 15. Операция AND

`AND` соответствует пересечению множеств документов. Пусть:

```text
A = [0, 1, 5]
B = [1, 2, 5]
```

Два указателя начинают с первых элементов. Если значения равны, документ добавляется в результат и оба указателя продвигаются. Если одно значение меньше, продвигается только соответствующий указатель.

```text
0 < 1 → продвинуть A
1 = 1 → добавить 1
5 > 2 → продвинуть B
5 = 5 → добавить 5
```

Результат:

```text
A AND B = [1, 5]
```

Код:

```cpp
while (first < left.size() && second < right.size()) {
    const uint32_t a = left[first];
    const uint32_t b = right[second];
    if (a == b) {
        output.push_back(a);
        ++first;
        ++second;
    } else if (a < b) {
        ++first;
    } else {
        ++second;
    }
}
```

Сложность — `O(|A| + |B|)`, дополнительная память результата не превышает меньший входной список.

## 16. Операция OR

`OR` соответствует объединению. Для тех же списков:

```text
A = [0, 1, 5]
B = [1, 2, 5]
```

На каждом шаге добавляется меньшее значение. При равенстве документ добавляется один раз, а оба указателя продвигаются.

```text
A OR B = [0, 1, 2, 5]
```

Алгоритм похож на слияние двух отсортированных массивов. Сложность — `O(|A| + |B|)`, а максимальный размер результата равен сумме размеров входов.

## 17. Операция NOT

`NOT` строит дополнение относительно всех документов индекса. Универсальным множеством считается диапазон:

```text
[0, document_count)
```

Если индекс содержит документы `0...5`, а

```text
cloud = [0, 1, 5]
```

то:

```text
NOT cloud = [2, 3, 4]
```

Алгоритм последовательно перебирает все `docID` корпуса и пропускает значения, присутствующие во входном списке:

```cpp
for (uint32_t document = 0;
     document < document_count;
     ++document) {
    if (position < input.size() &&
        input[position] == document) {
        ++position;
    } else {
        output.push_back(document);
    }
}
```

Сложность `NOT` равна `O(N)`, где `N` — число документов, потому что дополнение потенциально содержит почти весь корпус. Это наиболее дорогая базовая булева операция по времени и памяти.

## 18. Подробный пример приоритета

Для тестового индекса:

```text
cloud    → [0, 1, 5]
database → [1, 2, 5]
security → [1, 4, 5]
```

Запрос:

```text
cloud OR database AND security
```

Сначала выполняется `AND`:

```text
database AND security = [1, 5]
```

Затем `OR`:

```text
cloud OR [1, 5]
= [0, 1, 5] OR [1, 5]
= [0, 1, 5]
```

Если добавить скобки:

```text
(cloud OR database) AND security
```

порядок меняется:

```text
cloud OR database = [0, 1, 2, 5]

[0, 1, 2, 5] AND security
= [0, 1, 2, 5] AND [1, 4, 5]
= [1, 5]
```

Пример показывает, что скобки не являются косметическими: они меняют множество результатов.

## 19. Поведение неизвестного терма

Неизвестный терм имеет пустой posting list:

```text
unknown = ∅
```

Из обычных законов множеств следуют результаты:

```text
unknown AND cloud = ∅
unknown OR cloud  = cloud
NOT unknown       = все документы индекса
```

Это не считается ошибкой запроса. Ошибка возникает только при неправильном синтаксисе или неоднозначной нормализации лексемы.

## 20. Идемпотентность и повторный NOT

Поскольку операции работают как операции над множествами:

```text
cloud AND cloud = cloud
cloud OR cloud  = cloud
```

Объединение не создаёт дубликатов, а пересечение добавляет совпавший `docID` один раз.

Рекурсивное правило `NOT unary_expression` поддерживает любое число отрицаний:

```text
NOT NOT cloud     = cloud
NOT NOT NOT cloud = NOT cloud
```

Каждый `NOT` материализует новое дополнение. Для длинной цепочки это корректно, но может многократно пройти по диапазону всех документов.

## 21. Синтаксические ошибки

Парсер не пытается молча исправлять неправильный запрос. Отклоняются:

- пустая строка;
- пустые скобки `()`;
- оператор без операнда `NOT`;
- незавершённое выражение `cloud AND`;
- оператор в начале `AND cloud`;
- отсутствующая закрывающая скобка;
- два терма без оператора `cloud database`;
- два бинарных оператора подряд `cloud OR OR database`;
- лишняя закрывающая скобка `cloud)`;
- запись `cloud NOT database` без `AND`.

Основные сообщения:

```text
пустой запрос
ожидался поисковый термин
ожидалась закрывающая скобка
после выражения остались лишние данные
термин не удалось однозначно нормализовать
```

Ошибка записывается в предоставленный буфер и выводится консольным интерфейсом без завершения программы. Пользователь может ввести следующий запрос.

## 22. Почему не поддерживается неявный AND

Запись

```text
cloud database
```

не трактуется как `cloud AND database`. После разбора первого терма остаётся лишняя лексема, поэтому возникает ошибка.

Явные операторы делают грамматику однозначной и позволяют объяснить точный порядок выполнения. Для лабораторного булева поиска это предпочтительнее скрытых правил, которые пользователь может понять иначе.

## 23. Преобразование docID в документ

Логическое вычисление возвращает внутренние `docID`. Для вывода результата выполняются два перехода.

Сначала `documents.bin` читается по прямому смещению:

```text
offset = sizeof(DocumentHeader) + docID × 12
```

Из файла получается 12-байтовый MongoDB ObjectId.

Затем по `_id` из `processed_documents` запрашиваются только:

```text
title
url
source
```

Консоль печатает:

```text
1. Заголовок документа
   Источник: wikipedia | doc=123 | oid=...
   https://...
```

Если метаданные не найдены, `docID` и ObjectId всё равно выводятся с диагностикой. Это позволяет отличить корректное поисковое совпадение от проблемы связи с MongoDB.

## 24. Порядок результатов

Булевый результат отсортирован по возрастанию внутреннего `docID`. Это технический порядок, определённый ObjectId во время построения индекса. Он не является порядком релевантности, популярности или даты.

Для ранжирования по степени соответствия используется отдельный `tfidf_search`. Булевый поиск отвечает на другой вопрос: какие документы точно удовлетворяют логическому условию.

`result_limit` ограничивает только число напечатанных документов. Строка `Найдено документов` показывает полный размер множества до ограничения.

## 25. Интерактивный и конвейерный режимы

Консоль проверяет `isatty(STDIN_FILENO)`.

В интерактивном режиме печатаются подсказка и символ `>`. В конвейерном режиме подсказки скрываются, чтобы стандартный вывод было удобно анализировать скриптом или сохранять в файл.

Цикл работает до EOF:

```cpp
while (std::getline(std::cin, query)) {
    ...
}
```

Пустые строки пропускаются. Пробелы и переводы строк по краям запроса удаляются, но пробелы внутри выражения участвуют в разделении лексем.

## 26. Использование STL и ограничения курса

Основной контейнер — `std::vector<uint32_t>`. Он естественно представляет отсортированный posting list и разрешён преподавателем.

Используются также `std::string` для текста лексемы и временного буфера терма. Готовые ассоциативные структуры не применяются:

- нет `std::map`;
- нет `std::unordered_map`;
- нет `std::set`;
- нет `std::unordered_set`.

Поиск ключа выполняется собственным двоичным проходом по дисковому лексикону. Множественные операции реализованы линейными проходами по отсортированным векторам. Рекурсивный parser написан вручную и не использует генератор грамматик.

## 27. Оценка сложности запроса

Пусть `V` — число термов словаря, `df(t)` — длина posting list терма, а `N` — число документов.

Нахождение терма:

```text
O(log V) сравнений лексикона
```

Декодирование его списка:

```text
O(df(t))
```

Операции:

```text
AND(A, B) = O(|A| + |B|)
OR(A, B)  = O(|A| + |B|)
NOT(A)    = O(N)
```

Память определяется текущими декодированными posting lists и промежуточными результатами. Reader сейчас загружает список терма целиком в `std::vector`, после чего выполняет операцию. Потоковое пересечение непосредственно во время Variable Byte-декодирования не реализовано.

Для выражения из нескольких операторов стоимость зависит от порядка и размеров промежуточных списков. Например, раннее пересечение редких термов уменьшает следующий промежуточный результат. Текущий parser сохраняет порядок пользователя и не переставляет операнды автоматически.

## 28. Особенности и ограничения реализации

Поддерживаются только отдельные термы, `AND`, `OR`, `NOT` и круглые скобки. Нет фразового поиска в кавычках, wildcard, proximity search и автоматического ранжирования.

Лексема запроса ограничена пробелом или скобкой. Если пользователь пытается поместить внутрь одного TERM конструкцию, которую токенизатор делит на несколько разных лемм, запрос отклоняется. Нужно явно записать логическую связь:

```text
неправильно: cloud/database
правильно:   cloud AND database
```

Парсер вычисляет выражение сразу и не строит AST. Это делает реализацию компактной, но исключает глобальную оптимизацию порядка операций.

`NOT` материализует дополнение для всего корпуса. Запросы с большим числом отрицаний могут создавать крупные временные векторы.

При чтении терма отсутствие ключа и ошибка чтения posting list на уровне `load_postings` приводят к пустому результату. При открытии проверяются основные заголовки, а Variable Byte-reader проверяет структуру чисел, но отдельного контрольного хэша каждого posting list нет.

Булев поиск зависит от соответствия лингвистических ресурсов тем, которые использовались для корпуса. Если словари или правила были изменены, необходимо увеличить `parser_version`, повторно обработать корпус и перестроить индекс.

## 30. Что показать преподавателю

Сначала следует запустить:

```bash
./.build/boolean_search config.yaml
```

Для демонстрации полезен такой порядок запросов:

```text
queries
C++ AND Node.js
cloud AND database
cloud OR security
NOT cloud
cloud OR database AND security
(cloud OR database) AND security
NOT (cloud OR security)
```

На `queries` нужно объяснить, что запрос лемматизируется до `query`. На техническом запросе — что применяется тот же токенизатор. На простых операторах показываются пересечение, объединение и дополнение. Последние три запроса демонстрируют приоритеты и скобки.

Затем в коде нужно последовательно показать:

1. `next_token` — выделение операторов, скобок и термов;
2. цепочку `parse_or → parse_and → parse_unary → parse_primary`;
3. вызов `linguistics_process` в `parse_primary`;
4. двоичный поиск `boolean_index_find_term`;
5. Variable Byte-декодирование в `load_weighted_postings`;
6. два указателя в `intersect_postings` и `unite_postings`;
7. полный диапазон документов в `complement_postings`;
8. переход `docID → ObjectId → title/url/source` в консоли.

Также полезно ввести неправильный запрос:

```text
cloud database
```

и показать, что parser требует явный оператор и возвращает понятную ошибку, а не угадывает намерение пользователя.

## 31. Краткое объяснение для защиты

Булев поиск можно объяснить преподавателю следующим образом:

> Утилита читает по одному выражению из стандартного ввода. Сначала строка разбивается на термы, операторы AND, OR, NOT и скобки. Затем рекурсивный спуск сразу вычисляет выражение. Уровни функций задают приоритет NOT выше AND, а AND выше OR; скобки рекурсивно разбирают полное вложенное выражение. Каждый поисковый терм проходит тот же токенизатор и лемматизатор, что и корпус, поэтому queries находит ключ query, а C++ сохраняется целиком. Нормализованный терм ищется двоичным поиском в дисковом лексиконе, после чего из postings.bin декодируется возрастающий список docID. AND является пересечением двумя указателями, OR — объединением, NOT — дополнением относительно всех документов. Все результаты остаются отсортированными и уникальными, поэтому готовые set или hash table не нужны. После вычисления documents.bin переводит docID в MongoDB ObjectId, а из базы загружаются только заголовок, источник и URL для показа пользователю.

Главную последовательность удобно запомнить так:

```text
query string
→ lexer
→ recursive descent
→ tokenizer + lemmatizer
→ binary search in lexicon
→ Variable Byte postings
→ AND / OR / NOT
→ docID → ObjectId
→ result metadata
```

Основные особенности реализации — единая нормализация документов и запросов, рекурсивный спуск без готового parser framework, линейные операции над отсортированными векторами и прямое чтение собственного бинарного индекса.
